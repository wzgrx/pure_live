## 做法

- **接口和输出沿用 v3**：`LiveSite`、`LiveRoom` 等模型和 3.x 的 JSON 不变。v3 实现过的可选能力全部保留：刷新（`LiveSiteRoomRefresher`）、录制详情（`LiveSiteRecordRoomResolver`）、分区目录分页（`LiveSiteCategoryDirectoryProvider`，每页 30 条，满页才有下一页）。另加 `LivePlayUrlResolver`（线路要带请求头）和 `LiveSiteLinks`。
- **请求照 v3**：
  - 分类：大神（Dashen）的游戏表和直播配置，两个请求改为并行；
  - 分区、推荐：`api/category/{gametype}/`、`api/category/live/`，条数照调用方给的（热门页要 100 条）；
  - 搜索：`search/anchor/`，每页 1～50 条；
  - 详情：`activitylives` 拿频道号，再 `live/channel` 拿直播间。第二个请求不再带 v3 多加的 `anchor_ccid`（录制的样本没有它，接口不需要）。
  - 所有请求都带桌面 Chrome 140 的 UA 和 `Referer: https://cc.163.com/`；v3 的推荐、搜索和频道请求什么都不带，发的是 dio 的默认 UA。
- **画质和取流照 v3**（见下一节）：画质来自直播间的 `stream_list`，地址是跳转播放列表加各档签名，进房时就算好，取流不再请求。`video_play_url` 只作兜底。
- **v3 什么都给不出的地方，用归档 v4 的做法兜底**：
  - 没有直播频道的主播是未开播（v3 在这里报错）。进房时读房间页补全信息，并区分“不存在”；关注刷新和录制只标未开播，不多发请求。
  - 没有档位表的房间（未开播、没有详情的卡片）走 `video_play_url` 取画质和线路；未开播在取流时报 `StreamUnavailable`。
- **房间号保持请求时的号码**。v3 用的是响应里的 `ccid`。
- **`link` 是房间页** `https://cc.163.com/{ccid}/`。v3 把跳转播放列表存在 `link` 里，只为拼流地址用；现在它和档位表放在 `CcRoomData`（不存储）。
- **`userId` 仍是频道号**（`cid`），外部打开 CC App 的 `cc://join-room/{ccid}/{cid}/` 要用。
- **没有 Cookie、没有登录、没有弹幕**：v3 的 CC 全部匿名，弹幕是 `EmptyDanmaku`，所以没有弹幕参数类，也不注入 `CookieVault`。
- **线路带请求头**：从 v3 的 `PlaybackHeaderResolver` 搬来：UA、`Origin`、房间页作 `Referer`。

## 画质：保持 v3 用户实际看到的

对照笔记说 v3 的画质选择实际不起作用，本模块核实过（2026-09-28，两个在播房间逐档逐线路请求）：

- v3 的每档地址都是同一个跳转播放列表 `cgi.v.cc.163.com/redirect/video/{ccid}.m3u8?secret=…`，后面拼上该档 `CDN_FMT` 里的签名（`cc_site.dart:201-216`）；
- 服务端忽略拼上的签名，4 档 × 各线路全部 302 到同一个 `…tc2.m3u8`，也就是 1 Mbps 的那一档（`stream_list` 里叫 `medium`）；
- 跳转后的 HLS 地址带 `auth_key`，300 秒后过期；播放列表刷新用的是跳转后的地址。
- 这条路至今能播：跳转后的播放列表和分片都是 200。
- `video_play_url` 每档是不同的流（`original`、`ultra` 2 Mbps `tc1`、`high` 1 Mbps `tc2`、`standard` 600 kbps `tc4`），FLV，两个 CDN。

两者的差别用户看得见：

| | v3（现在的默认） | `video_play_url`（兜底） |
|---|---|---|
| 画质名称 | 原画、高清、标准、低清 | 原画、超清、高清、标清（站点自己的叫法） |
| 选哪档 | 都是同一路 1 Mbps | 各是各的 |
| 播放方式 | HLS，经跳转 | FLV，两个 CDN，带有效期 |

按“修好后用户看到的内容会变，就保持用户实际得到的样子”的规则：画质名称、可选项、播放地址都照 v3（和 v3 的冻结输出逐字节一致）；`video_play_url` 只在房间没有档位表时使用。换成 `video_play_url` 列为后续升级候选，代码已经写好并测过。

## 样本与 v3 的冻结输出

归档没有 CC 的 `expected.json`：归档的旧版对照工具只做了前五个平台，v3 应用现在也构建不了。本模块用 `fixtures/cc/legacy_expected.dart` 生成：

- 把 v3 的 CC 解析代码（`cc_site.dart`、`cc_catalog.dart`）原样搬进一个纯 Dart 脚本，只把网络换成按主机和路径读样本（同旧版的 `FixtureAdapter`），没有样本的请求抛 StateError；
- v3 `LiveRoom` 用到的部分（构造默认值、`copyWith`、`getLiveRoomWithError`、`toJson`）一并搬入；
- 输出格式同旧版工具（`roomProjection`、`errorProjection`、`{generator, value}`）；
- 重新生成：在仓库根目录运行 `dart run fixtures/cc/legacy_expected.dart`。

14 个样本有 `expected.json`：分类、分区 3 个、推荐 3 个、搜索 3 个、详情 4 个（在播、重播、未开播、不存在）。

v3 不请求的样本没有 `expected.json`：
- `S01-cate-*`：移动端分类接口，归档 v4 用的，留作升级候选的依据；
- `S05-page-*`：房间页；
- `S06-play-*`：`video_play_url`。

## 保持 v3 行为、没有采用归档 v4 或上游做法的地方

- **画质名称、可选项和播放地址照 v3**（见“画质”一节）。归档 v4 用 `video_play_url`，会改变名称、档位的实际画质和播放方式。
- **分类照 v3 读大神配置**：“直播分类”20 个分区加“官方房间/专题”。归档 v4 改读移动端接口，得到 4 个一级分类共 106 个分区，但没有官方入口，分类页会完全不同。
- **“【重播】”开头的官方重播频道仍是直播中**。归档 v4 标成回放。
- **推荐卡片没有分区名**（问题 6），同 v3。
- **搜索卡片用头像作封面，人数是粉丝数**。归档 v4 给在播主播用直播封面和热度。
- **分区目录满 30 条才有下一页**。归档 v4 只以空页结束（REG-CC-006），代价是每个分区多一次请求；样本里没有“不满一页但还有下一页”的情况。
- **推荐和搜索的条数照调用方给的**（热门页要 100 条，搜索限制在 1～50）。归档 v4 固定 30 和 20。
- **详情的人数没有热度和在线时用粉丝数**，`followers` 仍是 `'0'`。归档 v4 不给人数。
- **平台名“网易CC直播”**。归档 v4 是“网易CC”，上游改成了多语言文字。
- **没有弹幕参数**。归档 v4 记了频道号、房间号和 gametype，但协议没接通；v3 没有 CC 弹幕。

## 后续升级候选（2026-09-28 用户已采用，编号 9-1～9-7，落地见文末“升级落地（T02.U）”）

1. **画质改用 `video_play_url`**（REG-CC-004、005）：每档是真正不同的流，名称用站点的叫法（原画、超清、高清、标清），FLV 两个 CDN，地址带有效期，没有 5 分钟的 HLS 过期问题。代码已写好并测过，切换只需让 `getPlayQualities` 优先走它。
2. **推荐卡片显示分区名**（读 `gamename`）。
3. **“【重播】”频道单独标出**：标为回放，或在界面上标“重播”。
4. **分类改用移动端接口**：4 个一级分类共 106 个分区，比大神配置的 20 个全；但没有官方入口，分类页的样子会变。样本 `S01-cate-*` 已在。
5. **搜索卡片**：在播主播用直播封面和热度。
6. **详情的粉丝数**：填 `follower_num`（现在只在没有热度和在线时作人数）。
7. **关注刷新区分“不存在”**：现在刷新时没有频道的主播一律按未开播，因为 `activitylives` 对未开播和不存在的回答相同，区分要多请求约 110 KB 的房间页；只有进房时才区分。

### CC 弹幕的调查（没有接上）

依据：CC 网页房间（`cc.163.com/{ccid}/?open=blizzardtv&from=8382&platform=ds`，也是大神 `ds.163.com/glive/` 内嵌的页面）当前加载的脚本：`cclink` 2.3.4（`cc.res.netease.com/act/webcc/cclink/v2.3.4/cclink.js`，SharedWorker `cc.163.com/act/webcc/cclink/worker.js`）、旧版 `act/common/cclink/v0.4.3/cclink.js`、`room_core` 1.131.1、`chat_screen` 1.80.2。版本与归档规格 §7 记录的相同。

| 步骤 | 网页的做法 | 实测（匿名、直连） |
|---|---|---|
| 连接 | `wss://weblink.cc.163.com/`，二进制帧：`u16 LE sid`、`u16 LE cid`、`u32` 压缩标志（0 时后面直接是 msgpack，否则 `u32` 长度 + zlib） | 能连上 |
| 取设备令牌 `{6144, 32}` | 没有 `VISITOR` Cookie 时才发；有时用 `VISITOR` 作设备号 | 回答 `result 0`，`data.token = "<uuid>@web.cc.163.com"` |
| 注册设备 `{6144, 2}` | `web-cc`、`macAdd`/`device_token`、`page_uuid`、`update_req_info`（22 屏高、23 屏宽、24 `web`、25 系统、29 `163_cc`、30 空、31 UA、39 来源）、`client_type` 4000 等 | 回答 `result 0, reason ok` |
| 心跳 `{6144, 5}` | 每 30 秒 | 回答带服务器时间 |
| 登录 `{2, 2}` | 先 `GET https://cc.163.com/token/`（带 Cookie）；未登录回答 `{"status": false}`，网页就不登录，直接算“登录完成” | 未登录时同网页，不发 |
| 加入房间 `{512, 1}` | `roomId`、`cid`（频道号）、`gametype`、`hall_version` 1、`motive`、`account_id`（`<访客>@web.cc.163.com`）、`recom_token`、`client_type` 4000、`client_source`、`room_sessid` | **没有任何回答**：`live/channel` 给出的房间号、频道号、`gametype` 正确，30～40 秒内除心跳回答外什么都没有 |

另外试过、同样没有回答的做法：
- 旧版 `cclink` 0.4.3 的 RC4 加密：它先发 `{6144, 1}` 取密钥（之后整帧 RC4），服务端对 `{6144, 1}` 不回答，说明当前服务端不走这条路；
- 先 `GET /token/` 拿网页的 `VISITOR` Cookie，WebSocket 带上这个 Cookie，并以它作设备号和 `account_id`（网页有 `VISITOR` 时就是这样）。

结论：设备注册、心跳匿名都通，卡在“加入房间”这一步——服务端对匿名访客的加入不回应，与归档 v4（2026-09-27）的结果相同。网页里加入前唯一的前置条件是 `/token/` 的登录，所以很可能要登录用户（`{2, 2}` 用 `/token/` 给的 `urs`、`token` 登录）才能进房收弹幕。本平台没有登录和 Cookie，按任务要求不硬做，弹幕仍是 `EmptyDanmaku`（显示“不支持”），不加 `CcDanmakuArgs`，没有 M5.30 文档。
