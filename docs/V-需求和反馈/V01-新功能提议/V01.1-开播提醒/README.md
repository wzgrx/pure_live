## 目标

用户想知道关注的主播什么时候开播，现在只能打开应用看关注页（或开着“关注自动刷新”放着）。提议：给关注的直播间加“开播提醒”，主播从没开播变成开播时发一条系统通知，点通知直接进直播间。

本文件是**评估初稿**：写清现状、几种做法、代价和建议，供执行者补完、出图、发评审页，**由用户决定做不做、做哪种**（D-026）。

## 方案（评估初稿）

### 三种做法

| 做法 | 怎么做 | 能提醒到的时候 | 代价 |
|---|---|---|---|
| A 应用活着时提醒（建议先做） | 关注刷新（启动、下拉、定时、回前台）每轮结束后，比较这一轮和上一轮的 `effectiveLiveStatus`：从 offline/unknown 变成 live 的、开了提醒的房间发通知；定时刷新的间隔照用户设的 | 应用在前台、或在后台但进程没被系统冻结（开着后台播放、录制时一定活着） | 小：不加后台服务；只在用户已经开着“关注自动刷新”时才真的“及时” |
| B 系统定时唤醒检查 | Android 用 WorkManager 周期任务（最短 15 分钟，系统决定实际时间），只查开了提醒的房间 | 应用不在后台时也能查，但 HyperOS、ColorOS 等会延后或不执行，最多晚几十分钟 | 中：新插件和原生代码；要处理电池优化、自启动；耗流量和电 |
| C 常驻前台服务 | 像录制一样开前台服务，常驻通知栏，按间隔查 | 最及时 | 大：常驻通知、耗电；用户多半不接受；不建议 |

建议：**先做 A**（改动小、和 3.x 的关注刷新同一套），把“需要应用活着”在设置说明里写清；B 等 A 用一段时间、用户还想要更及时时再提议。

### A 的改动清单（确认后在目标组开任务）

| 编号 | 改什么 | 目标组 |
|---|---|---|
| c1 | 每个关注一个“开播提醒”开关（存储新加字段或单独一张表，不改 3.x 的关注格式；备份和设备同步带上） | I04（逻辑）、J03（备份） |
| c2 | 关注刷新每轮结束后找出“刚开播”的房间：上一轮是 offline/unknown、这一轮 live，且开了提醒；同一场直播只提醒一次（按开播时间或场次去重）；应用在前台、正在看这个直播间时不提醒 | I04 |
| c3 | 新通知类别“开播提醒”（`IMPORTANCE_DEFAULT`），标题“主播名 开播了”，正文直播标题；点通知进直播间；几个同时开播合并成一条 | O01（原生）、A14（样子） |
| c4 | 设置：总开关“开播提醒”（默认关）；说明写“需要打开关注自动刷新，应用在后台被系统清理后收不到”；打开时要通知权限、建议打开关注自动刷新 | A11（设置界面）、I04 |
| c5 | 入口：关注卡片长按菜单、直播间关注按钮的小菜单加“开播提醒”开关；关注页卡片上开了提醒的加小铃铛 | A09、A07（界面，要出图） |
| c6 | （可选）和录制的“等开播”共用检测：同一个房间正在被录制任务轮询时，用它的结果 | H04 |

### 规模

做法 A：中（逻辑约半天，界面要出图和评审，原生通知半天）；涉及 I04、O01、A07、A09、A11、A14、J03。做法 B 另算：中到大。

## 验证（做了以后怎么验证）

- 自动测试：关注刷新前后状态比较的单元测试（offline → live 发、live → live 不发、unknown → live 发、失败冷却中的不发、同一场只发一次）；通知文字的测试（照 `apps/pure_live/test/platform/system_surfaces_test.dart` 的写法）。
- 真机：K90 上开关注自动刷新（5 分钟）和开播提醒，关注一个快开播的主播，应用退到后台（开着后台播放保活和不开各一次），看通知、点通知进房；HyperOS 不保活时收不到要在说明里写。
