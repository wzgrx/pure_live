# 功能任务：每个任务的做法

第 1 版（2026-10-02）。照界面任务的流程（`docs/ui/PROCESS.md`）改写，对象是功能。每个任务（[TASKS.md](TASKS.md) 的一行）按下面的步骤走；任务文件夹 `docs/features/<编号>/README.md` 随每一步更新状态。

## 总览

| 步 | 做什么 | 产出 | 放在哪 | 谁 |
|---|---|---|---|---|
| 1 | 清点 | 功能点和现状 | [INVENTORY.md](INVENTORY.md)（已完成，任务开始时只核对本任务的几行） | 我 |
| 2 | 功能对比页 | v3 行为、v4 现状、差别和根因、改动 c1…、要选的 A/B、测试和验证方法 | `docs/features/<编号>/page.json`，README 同步 | 我 |
| 3 | 发布评审页 | claude.ai 私有页面（同一个地址出新版本） | 地址写进 README | 我 |
| 4 | 确认 | 每条“满意 / 不满意 / 再想想”、每个选择 | 页面数据库 `review` 集合，或聊天里说 | 用户（或按已授权直接继续，见第 4 步） |
| 5 | 开发任务书 | 任务书 | 发给开发代理（不进 git；模板 [templates/dev_brief.md](templates/dev_brief.md)） | 我 |
| 6 | 开发和测试 | 代码、测试、记录 | worktree 分支；记录 `docs/features/records/<编号>.md` | 开发代理 |
| 7 | 合并、门禁、推送 | master 上的提交 | `tools/gate/gate.sh --all` 的日志 | 我 |
| 8 | 真机验证 | K90 上照 TASKS 第 5 节逐条做 | 结果写进 TASKS 第 5 节和记录 | 我（装机、操作）；用户需要时看一眼 |
| 9 | 写回 | 任务状态、清点现状 | TASKS 第 2 节、INVENTORY 对应行 | 我 |

小任务（规模“小”、只是把 v3 的行为补回来、没有要选的）可以跳过第 2～4 步：在 README 里写清改动清单，直接开发，合并时在 TASKS 里写一句改了什么。

## 1 清点

- 读 INVENTORY 里本任务的功能点：v3 位置（`~/ref/v3ref/lib/`，标签 `v3.2.11`）、v4 依据、备注。
- 打开 v3 的代码把行为读全：入口、触发时机、设置项和默认值、出错时怎么办、各种状态。功能有多种状态的先把状态列全（录制任务就有 9 种）。
- 读 v4 现在的实现和相关记录（`docs/modules/M*.md`、`docs/ui/records/U.*.md`）的“没做的”“没验证的”；有半成品分支的先读分支（只读，不合并）。
- 发现清点写错的，直接改 INVENTORY 那一行，在 README 的“经过”里记一句。

## 2 功能对比页

写 `docs/features/<编号>/page.json`（模板 [templates/page.json](templates/page.json)，格式同 `tools/ui/mock/page.py`），章节固定：

1. **说明**：这个任务管哪些功能点，用户在哪里会用到；改版时写“这一版改了什么、上一版为什么不行”。
2. **v3 的行为**：逐条写，带 `文件:行`。
3. **v4 现在**：做到哪了、哪里不对，带 v4 的 `文件:行`。
4. **差别和根因**（`problems`）：编号 P1、P2…，每条写根因和位置。
5. **要做的改动**（`changes`）：编号 c1、c2…，类型用“补上 / 修复 / 保留 / 增强”，每条对应 P 编号或 v3 行为；有界面的写“照 `docs/ui/compare/<U.x>/` 的 cN”，不重新画图。
6. **需要你选的**（`choices`）：每处 A 是建议、B 是另一种，写清各自的后果（例如 3.x 的设置会不会变）。
7. **测试和验证**（`list`）：单元测试测什么；K90 上怎么验证（引用 TASKS 第 5 节的条目，或写新条目）。
8. **风险和性能**（`list`）：会不会多常驻任务、多耗电、多占内存；会不会影响 3.x 数据。

有界面的功能：评审页里只放链接到已确认的设计，或把那张图引进来（`figs`，路径指向 `docs/ui/compare/<U.x>/`）。确实缺界面的（例如一个新的说明对话框）按界面流程补一张图，或在“需要你选的”里给文字方案。

## 3 发布评审页

1. `python3 tools/ui/mock/page.py docs/features/<编号>/page.json --out ~/ref/design/features/<编号>.html`
2. 发布成 claude.ai 页面，声明 `db` 能力（评审按钮要用）；第一次发布记下地址写进 README，以后每一版都更新同一个地址。
3. 几个相关的小任务可以合在一个页面（`id` 写第一个任务编号，说明里列出全部）。

## 4 确认

- 用户在页面上逐条表态，或在聊天里说；两边都算。没表态的按建议做，README 里注明。
- **可以不等确认直接开发的**（用户 2026-10-01 已授权“界面和操作可以改进”“没有什么绝对不能修改的”，前提是 3.x 数据能迁移）：只是把 v3 的行为补回来或修成和 v3 一样、没有要选的、不改设置的含义。这类任务在 README 写“按授权直接开发”，评审页照样发，供事后看。
- **必须等确认的**：有“需要你选的”；去掉或改变 v3 的一个功能、一个设置的含义；新增 v3 没有的行为。
- 用户指出的通用问题写进 FEATURE_PLAN 第 3 节。

## 5 开发任务书

照 [templates/dev_brief.md](templates/dev_brief.md) 写，要写清：

- 范围：任务 README、page.json 的改动清单（确认结果）、INVENTORY 的几行；v3 和 v4 的文件。
- 逐条改动，每条做到什么样；有界面的写明照哪个 `U.x` 的哪一条。
- 能改的目录、不能动的（别的任务的目录、版本号、用户的 3.x 安装）。
- 测试要求、记录要求、门禁规则（AGENTS.md 的“加速”一节）。

## 6 开发和测试（开发代理，在独立的 git worktree 里）

- 开始前 `git merge --ff-only master`；worktree 里先 `bash tools/ffmpeg_kit/fetch.sh`，再在根目录 `flutter pub get`。
- 有半成品分支的：按文件对照把它的改动搬到现在的目录（`lib/pages/` → `lib/features/`），不直接合并旧分支；分支的测试照搬并跑通。
- 测试只写主要路径（AGENTS.md“加速”）：改动的每条 c 至少一个测试；修 bug 的先写一个在改之前会失败的测试。
- 改了 Android 原生部分的，后台跑一次 `flutter build apk --debug`，结束后停掉 Gradle 守护进程。
- 提交前：改过的包跑 analyze 和测试；`apps/pure_live` 跑 `flutter analyze` 和相关测试（改动面大就跑全部）；`python3 tools/gate/check_ui_structure.py`。不跑完整门禁。
- 记录 `docs/features/records/<编号>.md`：逐条对照表（c 编号、做了没有、偏差和原因）、根因、v3 文件 → v4 文件、新设置和 3.x 迁移、测试数量、没验证的部分、合并时注意的冲突点。
- 只提交到 worktree 分支，不推送；提交信息英文，结尾加 `Co-Authored-By`。不往手机安装。

## 7 合并、门禁、推送

- 合并开发分支（几个分支可以一起合并），照 FEATURE_PLAN 第 8 节的验收标准逐条看。
- `bash tools/gate/gate.sh --all`，日志里出现 `gate: passed` 才推送；门禁基线只减不增。
- 更新 TASKS 状态为“待验证”。

## 8 真机验证（K90）

- 几个任务合并后装一次：在 WSL 构建 `flutter build apk --debug`（包名 `com.mystyle.purelive.v4dev`），用 adb 装到 K90（`192.168.1.2:5555`）。**每次向手机发送输入前先确认前台应用**；不碰 3.x（`com.mystyle.purelive`）和它的数据。
- 照 TASKS 第 5 节本任务涉及的条目逐条做；需要用户操作的（扫码、登录、投屏到电视、开代理）先问用户什么时候方便。
- 有问题的：抓 `adb logcat`（只看开发版的进程）和截图，先找根因；属于本任务的回到第 6 步，不属于的归到对应任务或在 TASKS 加一行。
- 结果写进 TASKS 第 5 节的“结果”一列和记录的“真机验证”一节。

## 9 写回

- TASKS 第 2 节：状态改为“完成（日期）”或“验证有问题（现象）”。
- INVENTORY：对应功能点的现状改为“完成”，依据写上记录和验证日期；统计表重算。
- `docs/PLAN.md` 第 6 节的进度、`docs/UPGRADES.md` 的状态列（涉及时），由合并的人在推送时更新。

## 怎么更快

- **并行**：TASKS 第 3 节同一档的任务改的目录不重叠时，同时开开发代理；合并后一起装机验证。
- **小任务合并做**：F.1c、F.1d 这类几项小改动可以一个代理做完，一个评审页。
- **验证批量做**：一次装机把能验证的条目都做了，按 TASKS 第 5 节的顺序（先“必须”的批次）。
- **不重画界面**：有界面的功能一律引用 `docs/ui/compare/` 已确认的设计。
