# HLS 预取停止冻结合同修订（2026-09-09）

起点 `7f1f30d1`，代码 `4e7a63d19d74242c6b3044237123e2c3ccdd4b9b`，承接[预取调度原生证明](HLS_PREFETCH_SCHEDULER_AUDIT_2026_09_09.md)。上一轮属于实际进展：调度器与原生证据已提交；本轮审查仍未启用的生产接入边界，先修复发现的两个可复现停止缺陷。

## 红测与来源

来源 **fork-regression**：新调度器由 `fc0fa50e` 引入，以下缺陷存在于其冻结 API；不是声称已部署的 APK 上复现了同样故障。

1. 池只有两个名额、预留另一路后，第二段已被清单要求但尚未准入。先调用 acquire，再 freeze。freeze 禁止继续 pump，却未唤醒正在等容量的 acquire；旧逻辑会继续消耗按 bodyIdleTimeout 计算的网络等待预算。200 ms 红测超时，finally 才通过 close 唤醒原 Future；未遗弃挂起请求。
2. 发布序号 0–2，然后等待后台刷新确实下载了序号 3，但不向客户端发布新清单。freeze 后再次 publish，旧实现重新渲染最新 window、重新调用资源 URL 回调，有机会把停止前未发布的序号 3 暴露出去。红测的 URL 回调观察直接失败。不是靠 sleep 假设刷新已经完成：先取得并释放序号 3 的完整缓存租约，证明刷新已合并。

有效首轮 `red` 为 **93 通过 / 2 失败**，三项无关网络/时间预算没有调整，也没有删掉红测。

## 修订

- publish 保存最后一次返回给调用者的渲染文本，包括那次实际生成的本地 URI。freeze 一次性把它变为 ENDLIST；已经 ENDLIST 的文本保留，未发布过的 feed 只提供合法空 ENDLIST，不生成新 URL。
- 冻结后 publish 直接返回锁定文本，不再访问较新的后台 window、不调用资源映射函数；既有最后成功清单也可用于刷新失败后的停止收尾。close 后仍按关闭状态报错。
- 对已发布 feed，将 wanted 资源收紧到最后发布的依赖，并继续保留两代清单内尚需的资源和活跃租约。没有对外发布的后续预取会被退休，而不是跟随最新窗口延长录制。先前完全未发布的 feed 保留已完整缓存，供已持有身份的调用者排空；它仍不会生成新的停止清单资源。
- freeze 立即通知等待者。某资源尚未准入且调度已经冻结时 acquire 返回空；已经准入的最后已发布体仍有机会在现有排空期限内完成。没有扩大网络预算，也没有硬改 PTS 或丢掉损坏提示。
- 每路增加最后渲染文本和冻结文本引用，最多两个 feed，受已有渲染大小上限约束；这不等于媒体体池的字节预算。feed 关闭后随所有权表清理。
- 原生实验适配层现在调用 scheduler 自己的冻结发布，不再单独拼接 ENDLIST。仍是实验适配层在原生产 relay 之前，默认生产启用、混合标签回退和全局资源预算接线尚待完成。
