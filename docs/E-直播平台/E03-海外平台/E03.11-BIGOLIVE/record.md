## 做法

- **接口和输出沿用 v3**：`LiveSite` 和 v3 实现过的全部可选能力——目录分页（`LiveSiteDirectoryPager`）、目录说明（`LiveDirectoryNotice`，键 `bigo_directory_scope`）、可取消的搜索（`LiveCancellableSearch`）、关注刷新（`LiveSiteRoomRefresher`）、录制详情（`LiveSiteRecordRoomResolver`）、取流（`LivePlayUrlResolver`）、恢复（`LivePlayRecoveryResolver`），外加 `LiveSiteLinks`。3.x 的 JSON 不变。
- **请求照 v3**：
  - 所有请求都以 `bigo` 的名义发出（代理路由由应用按平台注入），带 v3 的请求头 `Origin: https://www.bigo.tv`、`Referer: https://www.bigo.tv/`、`User-Agent: Mozilla/5.0`，**不跟随跳转**，不带 Cookie（v3 的 BIGO 没有账号）；
  - 分类、目录、推荐和搜索的筛选都来自同一个公开列表 `ta.bigo.tv/official_website/OInterfaceWeb/vedioList/72?tabType=00&fetchNum=10&lang=en&countryCode=US`（`fetchNum=10` 实际给 20 个），在本地分页；
  - 直播间：先取匿名网页令牌（`sec.bigo.sg/v1/webjs/t` 取服务器时间 → `webjs/status?data=<加密请求>` 取令牌），再 `POST getInternalStudioInfo?siteId=<号>&verify=&token=<令牌>`（空正文，同 v3）。进房、刷新、录制详情、开播状态都是这三个请求，令牌每次重新取（v3）；
  - 一次列表请求、一次“令牌加直播间”共用一个 20 秒的总时限（v3 的 `_scope`），超时是 `NetworkFailure`，调用方取消原样抛出取消。
- **列表的复用照 v3**：不带取消令牌的调用（推荐、分区房间、`searchRooms`）共用一份列表 30 秒；带令牌的调用（v3 的目录页和搜索页总是带）每次都重新请求，不碰共用的那份。v3 在第一份回答到达前，每个调用各发一次请求；现在共用进行中的那一次（只减少请求）。失败的请求不缓存。
- **目录照 v3**：
  - 一个分类 `Bigo Live`（id `bigo`），一个分区“公开推荐”（`areaType: public`，`areaId: 72`），只在第 1 页、每页条数至少 1 时给出，不发请求；
  - 原生目录每页 20 个，`page × 20 < 总数` 时还有下一页；
  - `getRecommendRooms`、`getCategoryRooms` 按 v3 的 `_page` 切片：页码或条数小于 1、条数超过 100 都给空（现在不发请求）；
  - 列表按 v3 严格检查：`code`、`resCode`、每行的 `bigo_id`、`owner`、`room_id`、`sid`、`room_topic`、`nick_name`、`cover_m`、`user_count`、`is_locked`、`room_flag`，Bigo 号或主播重复，任何一处不对整个列表 `ApiChanged`（v3 的测试固定了这一点）。加锁的房间照样列出（v3）。
- **卡片照 v3**：房间号是列表的 `bigo_id`；标题是 `room_topic`，空时用昵称；封面是 `cover_m`，头像也用它；分区写 `Bigo Live`；`user_count` 作为在线人数（`onlineViewers`，口径 `onlineViewers`）；公告是 3.x 的聊天说明；`link` 是 `https://www.bigo.tv/<号>`；房间带 v3 的请求头 `httpHeaders`（3.x 的 JSON 里有）。
- **搜索照 v3**（Bigo 的网页搜索接口什么都不给，v3 改成这套规则）：只有第 1 页；房间链接按链接里的号查直播间；像号码的关键词（Bigo 号并含数字、`_`、`.`、`-`）先查直播间，查到就返回；否则取列表，按昵称和标题筛选（忽略大小写，同号只留一个）；纯字母的词若正好是列表里的号，或筛不到任何房间，就当作号去查直播间。查直播间是上面的三个请求，平台不认识的号（404）算没有结果。空白、超过 100 个字符、带控制字符、别的站点的网址不发请求。
- **房间照 v3**：
  - **房间号是平台写法的 `clientBigoId`**：v3 的详情总是返回它，用数字号请求也一样（样本对照：用 `414439909` 请求，`roomId` 是 `qashia305`）。3.x 从房间页关注时存下的就是它；
  - 标题是 `roomTopic`，空时用昵称；头像是 `avatar`，封面也用它；分区是 `gameTitle`，空时写 `Bigo Live`；没有人数（直播间接口不给，同 v3）；
  - 状态照 v3：公开、`alive` 为 1、有媒体列表是直播中；公开、`alive` 为 0 是未开播；要求登录、密码房、付费秀、直播中却没有媒体列表都是“未知”，公告分别写 3.x 的“要求登录”“受密码或付费限制”；
  - 房间带 `BigoRoomData`：平台写法的号、主播 `uid`、本场 `roomId`、访问权限、`alive`、是否给了媒体列表。不含媒体地址和令牌（不存进 JSON，也不留在房间里）。界面按它显示自己语言的公告（M13），弹幕以后用 `uid`、`roomId`（D01）。
- **取流是会话型输入，照 v3 用“配方”，不是线路**：
  - 媒体列表（`https://<十六进制>.cubetecn.com:1451/list_…m3u8`）的每个分片前两个 TS 包被加扰，播放器直接打开基本失败（归档规格 §5：ffmpeg 直连 11 次只成 1 次；经中继解扰 2/2 成功）。v3 因此不给 URL，由播放和录制各自的输入（`BigoHlsInput`）取令牌、读直播间、开本地 HLS 中继、在转发分片时解扰。线路的一组固定请求头表达不了“分片要先解扰”，所以本平台不给 `LivePlayUrlResolution.lines`；地址本身没有有效期，也没有 `PlayLease`；
  - 画质只有一档：`直播自动`（id `live`），不发请求；
  - 取流：返回 `LivePlayUrlResolution.owned(BigoInputRecipe(号))`，身份 `bigo:<号>:live`，确认的画质就是 `live`，不发请求；恢复相同；
  - 播放和录制按配方调用 `BigoSite.resolveInput`：每次都重新取令牌、读直播间，得到媒体列表的线路（v3 的请求头、HLS、线路编号是 CDN 主机），再用 `BigoHlsProtection` 解扰每个分片（G、H01.1）。
- **解扰**（`BigoHlsProtection`，3.x 的同名类）：种子在媒体列表 `#EXT-X-BIGO-WEB-PROTECTION:` 标签的属性里（`SEED=<十进制>`）；变换与 v3 逐字节相同（每个分片前两个 188 字节 TS 包的前 16 字节，按种子的 xorshift 流异或，做两次还原），不足 376 字节、种子越界是 `FormatException`。
- **网页令牌**：`BigoApi.tokenData` 是 v3 `BigoTokenCodec.buildData` 的移植：明文 `{"dr":<32 位十六进制>,"business":"bigolive-video","scene":"","at_time":<服务器时间>,"ver":"2.0"}`，OpenSSL 的 `Salted__` + 8 字节盐 + AES-256-CBC，密钥和 IV 由 EVP_BytesToKey（md5，一轮）从网站公开的口令导出，Base64。v3 用 PointyCastle，这里用 `live_core` 自己的 AES（见“新增的通用能力”），与 v3、OpenSSL 的输出逐字节相同。JSONP 照 v3 要求回调名完全一致，回调名默认是 v3 的 `jsonpcallback_<毫秒>_<微秒>`。
- **没有弹幕参数、没有登录**：v3 的 BIGO 是 `EmptyDanmaku`，没有账号和 Cookie 设置，所以不注入 `CookieVault`，也不输出弹幕参数。

## 样本与 v3 的冻结输出

归档没有 BIGO 的 `expected.json`（归档的旧版对照工具只做了前五个平台，规格 §11 也写明没有旧版期望值）。本模块用 `fixtures/bigo/legacy_expected.dart` 生成，做法同 SHOWROOM、niconico：

- 把 v3 的 `BigoApi`、`BigoSite`、`BigoLink`、`BigoTokenCodec`、`BigoHlsProtection`、`BigoInputRecipe` 原样搬进一个 Dart 脚本。v3 本来就把传输、令牌数据和 JSONP 回调名做成可注入的，所以只换了这三样：
  - 传输按方法、主机、路径和查询参数读样本（令牌请求随机的 `callback`、`data` 和直播间请求的 `token` 不参与比较，样本里已脱敏），状态码不是 200 时正文为空（同 v3）；没有样本的请求抛 StateError，v3 的 `_scope` 把它记为 `transport`，脚本另记在 `unmatched` 里；
  - 回调名用样本录制时的 `jsonp_purelive_t`、`jsonp_purelive_s`（能通过 v3 的检查）；
  - 令牌数据用 v3 的 `BigoTokenCodec.buildData`，盐和随机数固定，输出每次相同。
- `withRequestCancellation` 照抄，Dio 的取消令牌换成桩；`kIsWeb` 为 false；只在网络路径上的 `_defaultRequest`、`readBody` 没有搬；`i18n` 返回 3.x `zh.json` 的文字；v3 的 `LiveRoom` 等模型只搬用到的部分（`toJson` 里有 v3 的 `HttpHeaderPolicy.normalize`）。
- 录下的直播间头像是 http，v3 在它上面全部失败；为了也能比较其他字段，`S03-studio-live` 另记一份“只把头像改成 https”时 v3 的输出（`avatarHttps`）。`S03-studio-notoken` 记 v3 `studioStatus` 的表单请求（样本录的正是它）、`parseStudioRoom`，以及把它当作带令牌请求的回答时 v3 给出的房间（`asTokenAnswer`）。
- `BigoTokenCodec` 要用 PointyCastle，工作区不依赖它，所以脚本用临时的包配置运行（命令写在脚本开头，`pointycastle: 4.0.0`、`crypto: 3.0.7` 是 v3 解析到的版本，只用于生成期望值）。
- 输出格式同旧版工具（`roomProjection`、`errorProjection`、`{generator, value}`），每个入口另记请求。

6 个样本都有 `expected.json`：

| 样本 | 内容 |
|---|---|
| `S01-list` | 分类（第 1、2 页，条数 0）；原生目录（推荐第 1～3 页、分区第 1 页、别的分区、第 0 页）；推荐的 10 种切片；分区的 2 种切片和别的平台；12 个关键词的搜索（名字、标题、大小写、无结果、按号、两种房间链接、纯字母的无结果词、别的网址、空白），第 2 页、超长、不带令牌；按号搜索在 https 头像下的结果；30 秒缓存；23 个链接的 `BigoLink.parse`、`parseOrSiteId`、`url` |
| `S03-studio-live` | 与 `S02-*` 一起，录下的回答和 https 头像两份：三种深度的详情、开播状态、`studioRoom` 的解析结果、画质、配方、恢复、`getPlayUrls` 和别的画质；非法号、别的平台 |
| `S03-studio-notoken` | `studioStatus` 的表单请求；`parseStudioRoom`；当作带令牌请求的回答时的三种深度、开播状态、画质和配方 |
| `S02-time-live`、`S02-status-live` | JSONP 的读取（录制的回调名和别的回调名）；v3 的令牌数据：三个服务器时间、另一组盐、三种参数错误 |
| `S04-playlist` | 种子：录下的列表、v3 认得的旧写法、越界；解扰：录下的一个加扰包、一段计数数据、不足 376 字节、种子越界 |

令牌数据另用 OpenSSL 核对过：`openssl enc -aes-256-cbc -md md5 -pass pass:undefinedval0x01 -S 0001020304050607` 加密同一段明文，密文与 v3、新代码逐字节相同。

## 与 v3 输出的对照

对照方式：用同一份录下的响应跑新代码，逐键比较 `toJson`（加 `link`）和 v3 的冻结输出；另比较请求。

| 样本 | 结果 |

## 保持 v3 行为、没有采用归档 v4 或上游做法的地方

- **房间号是平台写法的 `clientBigoId`**（上游 TV 同）。归档 v4 保留请求时的号码，同一主播可能关注成两条（对照笔记 `sub_C.md`）；3.x 从房间页存下的关注用的是平台写法。卡片仍用列表的 `bigo_id`（v3），与进房后的号可能不同，3.x 的关注刷新按请求时的身份合并（见“放到其他模块的部分”）。
- **有分类、有分区“公开推荐”**。归档 v4 没有分类，分区房间报 `NotFound`。
- **有搜索**（链接和号查直播间 + 列表筛选，同 v3 和上游 TV）。归档 v4 没有搜索。
- **加锁的房间照样列出**。归档 v4 跳过 `is_locked == 1`；列为升级候选 2。
- **列表严格校验**：归档 v4 跳过坏行。
- **封面用头像**。归档 v4 用 `snapshot`（直播截图）；列为升级候选 1。
- **画质名称 `直播自动`、id `live`**。归档 v4 是 `hls`“自动”，会改变画质菜单和已存的画质 id。
- **取流是配方**（v3 的所有权模型：每个播放、录制各自取令牌和媒体列表）。归档 v4 给出带 `HlsRelayRecipe(restore: …)` 的线路，需要改动 E05.1 的线路模型；这里不改模型，解扰函数和 `resolveInput` 由平台层提供，G、H01.1 按配方使用。
- **请求头照 v3**（`Mozilla/5.0`，没有 `Accept`）。归档 v4 用 Chrome 140 UA 和 `Accept: application/json, text/plain, */*`，直播间请求还带表单的 `Content-Type`（录制样本如此）。
- **JSONP 要求回调名完全一致**（v3、上游 TV）。归档 v4 取第一个括号到最后一个括号之间，更宽松。
- **解扰的输入不足 376 字节报错**（v3）。归档 v4 不足一包就停。
- **链接规则照 v3**：只认 `bigo.tv`、`www.bigo.tv`，保留路径是 v3 的 7 个。归档 v4 还认其他 `*.bigo.tv` 子域，并把 `show`、`user` 当作站点页面。
- **分区名、公告、画质名用 3.x 的中文**。归档 v4 没有公告。
- 上游 pure_live_TV 与 v3 相同，没有要采用的修复。

## 回归条目的覆盖

归档规格没有 REG-BIGO 条目。§10“踩过的坑”和 `spec/regressions.md` 里涉及本平台的通用条目，属于平台层的部分都有测试：

- **探针说要登录**（§10）：直播间请求之前先取网页令牌，令牌放在查询参数里，不用表单；不带令牌的表单请求得到 `needLogin`（样本 S03-studio-notoken），这种回答的房间状态未知、取流报 `NeedsLogin`。
- **解扰失效**（§10）：在属性列表里找 `SEED=`，录下的 `VERSION=1,SEED=…` 列表得到种子；录下的一个加扰包还原成 PAT。
- REG-LEASE-005（恢复重新获取身份和令牌）：恢复给出同一个配方，不含地址；每次 `resolveInput` 都重新取令牌、读直播间。
- REG-LEASE-007（每个会话独立签名）：两次 `resolveInput` 各发三个请求，各用自己的取消令牌，互不共享。
- REG-LEASE-017（会话型输入不导出私有地址）：取流结果没有 URL（`urls` 为空，`inputRecipe` 是 `BigoInputRecipe`），房间 JSON 里没有媒体地址和令牌，`BigoRoomData` 也不含媒体地址。
