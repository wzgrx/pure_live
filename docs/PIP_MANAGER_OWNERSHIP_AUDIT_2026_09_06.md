## 红测确定的首个错误状态

1. `close` 与 idle native hard-dispose 没有释放 `_pipSubscription`，只有整个管理器
   dispose 才取消。原生解码器已释放但管理器仍持有监听，插件仍认为有消费者。
2. `enablePip` 等待系统状态后未核对房间/关闭意图，用户退出后仍调用 native enable。
3. native enable 请求发出后关闭房间，迟到的 enabled 回复又把 `isInPip` 写为 true。
4. native 状态流已依次报告 enabled、disabled（系统恢复），旧 enable 回复仍覆盖最新状态。

真实 PlayerManager 配合可注入的 Floating 桥和现有 FakePlayer 复现，生产默认平台选择不变。
四项测试使用原状态机，未先加入取消/代次修复。`20260905T170406835Z-quality-focused.json`
为 32 通过、4 个目标失败：残留监听 true、退出后 native 调用 1 次、关闭后状态 true、
系统恢复后状态重新变 true。
第一轮 `20260905T170124213Z-quality-focused.json` 中后两项因夹具少推进一帧而提前断言，
不计作这两项根因证据；修正帧推进后四项均到达目标断言再失败。

## 修复合同

- 显式开始/停止 Android PiP 观察；关闭意图发出就取消，原生 hard-dispose 和整个 dispose
  也兜底取消。观察代次拒绝旧监听回调。
- 复用尚未释放的播放器重新打开房间时恢复观察，不重复订阅，也不重建原生播放器。
- PiP 进入事务保存会话、播放意图、播放器实例与请求代次，每个异步边界重新核对。
- 关闭立即完成取消信号；状态查询、帧等待、native enable 返回均与取消信号竞争。
  已撤销的操作不必等待系统回复才结束，不增加刷新或重试定时器。
- 已发布的新系统状态优先于旧进入请求的返回值；旧 finally 不清理新请求的 busy 状态。
- 退出 PiP 撤销旧几何更新，native update 返回后再次核对代次，避免污染下一次比例去重缓存。
- Windows 原生小窗路径保持不变；Android 测试桥仅作为显式构造依赖注入，不是用户配置开关。

## 验收边界

测试覆盖管理器与插件协议调用，不操作手机；没有把假的系统回复当作真实 Surface 首帧。
发给 Android 的原生进入命令本身没有可撤回 API：已交给系统处理的请求可能仍产生系统级
切换，本补丁撤销本地等待和迟到写入，不声称能取消系统已经执行的动画。
