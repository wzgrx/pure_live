# 斗鱼实际画质与线路一致性审计

## 结论与来源

应用基线 `fa6ed9240f9fee60dc1b718581811628e3f2b983`（该提交仅整理规则/发布脚本）。
冻结上游 `c6c9bd70aedc503c003110dae10a83ad0bb891d8` 中也有相同的画质信息丢失，归类为 `upstream-existing`；本轮只读比较，没有合并。

首次错误状态在 `DouyuSite.getPlayUrl`：H5 响应经 `parsePlayResponse` 后只保留 URL，丢弃服务器 `rate`。
普通播放没有实现 `LivePlayUrlResolver`，统一扩展因此将请求档位当成实际档位；录制游标也直接回填 `quality.selectionId`。
此外，普通播放依次请求不同 CDN 后把所有 URL 混在一个列表里，即使它们确认的档位不同。

UI 的 `resolveAppliedQualityIndex` 和录制服务的 `_appliedQuality` 已经支持读取实际档位，问题是斗鱼适配器没有把证据传给它们。
这不是渲染器清晰度、窗口比例、暂停或虎牙服务端的修复；没有修改这些路径。

## Issue 与实网边界

- [上游 #853](https://github.com/liuchuancong/pure_live/issues/853) 报告 Windows 3.1.2 斗鱼原画在运动时模糊，未提供房间、码率、日志或画面。本次再次读取报告，仍按 `not-reproduced` 跟踪其完整现象，不直接关闭或宣称唯一根因已确认。
- 用当前生产签名字段的 Python 对照请求推荐页实时返回的房间 `474669`：请求 `-1 / 0 / 2`，响应实际 `rate=0 / 0 / 2`，均有 URL。接口当时列出的原画1080P30、超清、高清代码为 `0 / 3 / 2`，说明这些代码不是可用于数值高低排序的码率。
- 该正常样本证明实际 `rate` 字段仍存在，也说明并非所有匿名原画请求都会被降档；它没有复现投诉中的动态模糊，没有解码/视觉验收。
- 最初选用旧报告的房间 `71415`，三档均返回 API `error=-5`，没有有效播放数据；未据此改写签名或判定整个平台故障。
- 脱敏证据保存在 `local-artifacts/douyu-quality-ack-live-sample.json` 和 `local-artifacts/douyu-quality-ack-sample.json`。只保存房间、时间、响应键名和档位；不保存 Cookie、签名、媒体 URL 或客户端 IP。

## 修复设计

1. 单 CDN 统一返回 URL 与服务端档位；保留旧 `getPlayUrl` 字符串接口作兼容包装。
2. 普通播放实现 `LivePlayUrlResolver`，各 CDN 按确认档位分组：优先匹配请求档位，否则保持平台线路顺序选择第一组有确认的档位。不对 `rate` 做大小排序。
3. 一个返回列表只包含同档位的 URL，避免后续切线路时仍显示旧画质却播放不同档位的流。未知档位单独分组，有明确档位时优先明确组。
4. 录制游标只签名/请求当前 CDN，不提前解析全部线路；返回真实档位，让录制中心显示实际画质，同时保留“请求档位 + 线路索引”用于下一次重试。
5. 空、非法、负值、非整数 `rate` 返回未知，不截断小数伪造原画。缺少确认信息仍保留播放能力，沿用共享接口的请求档位展示回退，不宣称已确认。
6. 沿用原有每 CDN 一次重试上限、签名缓存和异常传播。没有增加轮询、缓冲、固定延时、自动暂停或播放器重建。
