# 播放恢复事务审计：等待期间恢复与取消

## 实施前根因与来源

- 本仓库基线：`f04297ed36dd40f5aaa07504566776240f4a9a31`。
- 上游只读参照：`baab0eb46a3dd5fe1b5f6a75cda65f53f692aadb`（本地冻结引用）；
  本轮再次通过 GitHub API 核对最新 master 为 `c6c9bd70aedc503c003110dae10a83ad0bb891d8`，
  仅更新发布索引。本轮不合并。
- 分类：`fork-regression`。自动续签、停帧恢复和 Windows 候选播放器交接是维护分支路径，
  不是上游原生 WUP 取流修复本身造成的问题。

前轮修复了错误任务**排队期间**失效的情况；继续沿异步调用审查发现三处遗漏：

1. 超时任务已进入恢复、等待平台新地址时，原连接可能自行解除缓冲或开始出帧。
   `_tryRefreshSignedPlaybackSource` 只复核源代次及用户意图，未复核超时观察是否仍成立，
   因而对已经恢复的源执行替换。获取地址失败时也可能继续切线路/内核。
2. Windows 候选播放器预热期间用户暂停，成功返回路径会丢弃候选；但候选报错或超时的
   catch 返回 `false`，调用者继而进入 `_playInternal`，把用户已暂停的旧源重新打开。
   交接中 `await oldPlayer.pause()` / `candidate.setVolume()` 后也需要重新核对意图。
3. 候选的错误流可能先于 `setDataSource` 返回。原实现对尚未开始等待的 `ready` Future
   调用 `completeError`，异常会逃逸到 Zone，而不是留在恢复事务中。
   实际异步夹具已复现该异常。改为传递错误结果，等事务接收后再抛出并处理；
   首帧后、提交前的错误也保留，首帧就绪不是永久健康凭证。

第一处错误状态是恢复事务越过异步边界后继续使用过期依据，不是“线程不足”或缓冲太小。
采用同一恢复事务的所有权和观察有效性检查，分别覆盖等待地址、候选准备、交接提交和失败
分支。播放结束/明确原生错误与推断超时分开：已收到 EOF 时，残留缓存帧不撤销断流恢复。

## 设计不变量

- 正常原生虎牙 FLV 保持既有连接，仅预取凭据，不新增固定间隔重开。
- 超时依据被新的原生缓冲/播放/出帧事件推翻后，撤销旧恢复；新故障仍有新的恢复机会。
- 手动暂停、后台暂停、关闭或更换房间发生后，旧任务的成功与失败结果均不得夺回播放权。
- 丢弃未安装候选时释放其订阅与原生实例；已由交接暂时暂停的旧源只按**当前**意图恢复。
- 退还被撤销事务占用的本次恢复预算，保留之前真实失败计数；短时间多次自行恢复后，
  后续实际 EOF 仍可申请凭据。取消的交接日志标记为取消，而非提交成功。
- 撤销恢复时恢复真实原生状态，避免遗留恢复流程自己写入的转圈状态；保留当前几何及纹理。
- 普通、横屏、小窗、音频模式共用源事务；不改变任何直播识别、裁剪或录制算法。

## 外部合同核对

- [mpv 缓冲与暂停说明](https://mpv.io/manual/stable/#options-cache-pause)：缓冲暂停可由内核自行恢复；
  `pause`、`core-idle`、`paused-for-cache` 表示不同层次的状态，不以一个播放布尔值代替出帧事实。

  取流凭据修复与本分支恢复事务分层对照，保留已验证的 WUP 适配，不整文件覆盖播放器。
