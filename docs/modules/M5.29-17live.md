## 做法

- **建在 M5.0 的 WebSocket 运行时上**（`DanmakuSocketConnection`）。平台代码只写 `target`（检查房间号，给出地址和请求头）、`onOpen`（新 socket 的状态清零）、`onData`（解一帧并处理）；换地址、退避、最多 8 次、无消息检测、加入超时、停止后不再有事件，都由框架和 `LiveSocket` 负责。框架没有改。
- **令牌在握手里取**（同 M5.11 TwitCasting、M5.21 PandaTV 的做法，`connector` 参数本来就允许替换握手）：
  - `connect` 后的第一次握手先 `POST https://api-dsa.17app.co/api/v1/messenger/auth`（正文 `{}`，平台层的目录请求头 `SeventeenLiveApi.catalogHeaders` 加 `content-type: application/json`，不跟随跳转，以 `17live` 的名义发出，超时同握手 10 s），读 `provider` 为 1（Ably）的 `token`；
  - 之后的握手（重连、换地址）一直用这个令牌，直到服务端拒绝它（令牌错误，见下），才在下一次握手前重新取。ably-js 也是一直用同一个令牌，只在令牌错误时才调 `authCallback`；
  - 请求失败（网络错误、状态码、不是 JSON、没有令牌）就是这次握手失败，走框架的退避和 8 次上限；`provider` 不是 1（网站的枚举：2 是 PubNub）说明这个平台换了推送服务，以 `DanmakuClosed(connectionFailed, 'messenger/auth: provider 2')` 结束，不再重试；
  - 一次 `connect` 里的请求绑定一个 `CancelToken`，`close` 或换房间时取消；
  - 令牌放在地址的查询参数里（Ably 的做法），`dart:io` 握手失败的错误文字里会带着整个地址，所以握手包装把错误文字里的令牌（原样和编码后的）换成 `<token>` 再抛给框架，框架把它写进重连和关闭事件的详情时就不会泄露令牌。
- **四个地址**：`wss://17media.realtime.ably.net/?access_token=<令牌>&format=json&heartbeats=true&v=3`（ably-js 的 `environment: "17media"`），失败时依次换网站配置的三个备用主机 `17-media-{a,b,c}-fallback.ably-realtime.com`（2026-09-30 实测三个都能用同一个令牌连上、加入、收到消息）。握手请求头是 `Origin: https://17.live` 和平台层的桌面 UA，和两次录制、v4 相同；服务端不在乎大小写，用默认的 `dart:io` 握手，不需要 `connectExactWebSocket`。
- **加入照 ably-js**：服务端先发 `CONNECTED`（4），收到后才发 `{"action":10,"channel":"<房间号>"}`（`ATTACH`），回 `ATTACHED`（11）就算加入，报 `DanmakuReady`；重复的 `ATTACHED` 不再报。打开后 10 s 内没有加入就换连接（框架的加入计时器，ably-js 的 `realtimeRequestTimeout`）。
- **心跳是服务端发的**：`heartbeats=true` 时服务端每 15 s 发 `{"action":0}`（`CONNECTED` 的 `maxIdleInterval` 15000；S06 里 14 个心跳的间隔是 14 998～15 002 ms），客户端什么都不发，手动 `heartbeat()` 也不发。框架的心跳间隔设成 15 s 只当作无消息检测的检查点；25 s 没有任何消息就换连接（ably-js 的空闲判定：`maxIdleInterval` + `realtimeRequestTimeout`）。检查点是 15 s，所以实际在 25～30 s 之间发现。
- **拒绝和异常照 ably-js**：
  - 令牌错误（`ERROR` 或 `DISCONNECTED` 带 40140～40149，如 40142 令牌过期）：丢掉令牌和这个 socket，下一次握手取新令牌（走框架的退避，换下一个地址）。令牌错误和服务端发的 `DETACHED` 都算一次“拒绝”，连续第 4 次（中间没有加入成功过）以 `DanmakuClosed(connectionFailed, 'Token refused: <code> <message>')`（或 `Channel detached: …`）结束，加入成功一次就重新计数。收到拒绝也算收到消息，框架的 8 次上限管不到这种循环，所以要自己计数（同 M5.21）。ably-js 同样是遇到令牌错误就取新令牌重连，新令牌也被拒才放弃。
  - 其他连接级的 `ERROR`（没有 `channel`，如编造的令牌 40101、编造的应用 40400）：ably-js 让连接失败（FAILED），这里以 `connectionFailed` 结束，详情是 `Ably error <code> <message>`。
  - 房间频道的 `ERROR`：ably-js 让频道失败，这里以 `connectionFailed` 结束，详情 `Channel refused: …`；别的频道的 `ERROR` 不管。
  - 不带令牌错误的 `DISCONNECTED`（服务端要换节点等）：沿用令牌重连。
  - 服务端发的 `DETACHED`（房间频道）：和 ably-js 一样在同一个 socket 上重新 `ATTACH`，房间一直算已加入，不提示；重新 `ATTACH` 还没回答又来一个 `DETACHED`，或 10 s 内没回答，就换连接（ably-js 这时把频道挂起、15 s 后再试）。每个 `DETACHED` 都计入上一条的拒绝次数。
  - 服务端发的 `AUTH`（17，要求换令牌）：和 ably-js 一样取新令牌，在同一个 socket 上发 `{"action":17,"auth":{"accessToken":"<新令牌>"}}`，之后的握手也用新令牌；取不到就什么都不发，等服务端以令牌错误断开时再换。实测 90 分钟里服务端没有发过 `AUTH`（见“实测”），这一条照 ably-js 实现，用合成帧测试。
  - `CLOSED`（7）、`SYNC`（16）等其他消息不管；socket 本身断开时由框架重连。
- **只上报聊天和在线人数**：
  - 评论（`type` 3，`commentMsg`）是白色或平台给的颜色的聊天；网站隐藏的评论（`isDirty`、`isDirtyWord`、`isDirtyUser` 为真，网站只对发言者本人显示）不报；弹幕付费版（`barrageStyle`、`barrage`，网页上另外在画面上飞过）也当作普通聊天；
  - `LIVE`（`type` 38）的 `liveinfo.liveViewerCount` 是网页显示的在线人数，报成 `LiveAudienceUpdate(onlineViewers)`；
  - 礼物（13）、福袋（32）、入场（18，只给主播看）、点赞分享等反应（28）、下播（5）、直播信息（6）、排行（54）、奖励（79）、任务提醒（80）、74 等都不报（和 M5.1～M5.21 的范围一致，见差异 3）。

## 协议

**令牌**：`POST https://api-dsa.17app.co/api/v1/messenger/auth`，正文 `{}`，回答 `{"provider":1,"token":"<应用 id>.<…>","permissions":["*"]}`（S05、S06 第 0 行）。只取 `token`：1～4096 个可打印 ASCII（不含空白）。令牌是匿名的，同一时间段里所有人拿到的是同一个（2026-09-28 相隔 1.5 分钟的 4 次请求相同；2026-09-30 12:02～12:58 每 5 分钟一次的 12 次请求相同，13:03 那次换了新的，旧的仍然有效，见“实测”）。令牌的到期时间读不出来，本实现也不需要：过期的令牌会被服务端以令牌错误拒绝，这时再取新的。

**socket**：Ably 的 JSON 实时协议（`format=json`、协议版本 `v=3`），每个文本帧是一个协议消息，按 `action` 区分：

| 方向 | `action` | 内容 | 本实现 | 归档 v4 |
|---|---|---|---|---|
| 收 | 4 `CONNECTED` | `connectionId`、`connectionDetails`（`connectionKey`、`maxIdleInterval` 15000、`connectionStateTtl` 120000、`serverId` 等） | 发 `ATTACH` | 不管（打开就发了 `ATTACH`） |
| 发 | 10 `ATTACH` | `{"action":10,"channel":"<房间号>"}` | 收到 `CONNECTED` 后发，与两次录制逐字节相同 | 打开就发 |
| 收 | 11 `ATTACHED` | `channel`、`channelSerial`、`flags`（786432 = 订阅 + 在线订阅） | 房间频道的算加入 | 同 |
| 收 | 0 `HEARTBEAT` | `{"action":0}`，每 15 s | 只让连接保持活着 | 同 |
| 收 | 15 `MESSAGE` | `channel`、`id`、`channelSerial`、`timestamp`、`messages[]`（`id`、`data`、`serial`、`version`） | 房间频道的读消息（见下） | 同 |
| 收 | 16 `SYNC` | 在线成员（实测：不存在的房间号也能加入，随后收到空的 `presence`） | 不管 | 不管 |
| 收 | 9 `ERROR` | `error`（`code`、`statusCode`、`message`、`href`）；带 `channel` 的是频道错误 | 见“做法”：令牌错误换令牌，其他结束 | 带 `error` 就换令牌重连，不分连接和频道，不分哪个频道 |
| 收 | 6 `DISCONNECTED` | 可能带 `error` | 令牌错误换令牌，否则沿用令牌重连 | 带 `error` 就换令牌 |
| 收 | 13 `DETACHED` | 可能带 `error` | 同一 socket 重新 `ATTACH` | 带 `error` 就换令牌重连，不带就不管 |
| 收 / 发 | 17 `AUTH` | 服务端要求换令牌；客户端回 `{"action":17,"auth":{"accessToken":…}}` | 取新令牌原地发送 | 不管 |
| 收 | 7 `CLOSED` | 服务端关闭 | 不管（socket 断开由框架处理） | 不管 |

**消息载荷**：`messages[].data` 是 JSON 经 gzip 后的 base64（`H4sI` 开头），网页按 `gzip_base64` 解（`atob` → `ungzip` → UTF-8 → `JSON.parse`，失败就当没有内容），再和 Ably 消息的其他字段合在一起。本实现只认这种形式：解不开、不是 JSON 对象、UTF-8 坏了都跳过这一条消息。消息的 `encoding` 字段不看（录制里没有）。消息 id 用 Ably 的 `messages[].id`（`<帧 id>:<序号>`），没有时照 Ably 的规则用帧的 `id` 加序号。

载荷的 `type` 是网站的消息枚举（节选）：

| type | 名称 | 内容 | 本实现 | 归档 v4 |
|---|---|---|---|---|
| 3 | COMMENT | `commentMsg`：`content`、`comment`（`text`、`textColor`、`textSize`、`shadowColor`、`tagColor`）、`sendTime`（毫秒）、`displayUser`（`userID`、`displayName`、`picture`、`level`、徽章等）、`isDirty`、`isDirtyUser`（`isDirtyWord` 网页也看）、`isFraud`、`barrage`、`barrageStyle`、`marquee`、`name`（名字的颜色）、`level`、`rank`、`backgroundColor`、徽章等 | 聊天（见下） | 聊天 |
| 38 | LIVE | `liveinfo`：`liveViewerCount`（在线）、`achievementValue`（积分）、`mute`、`giftRankOne` 等 | 在线人数 | 在线人数 |
| 13 | NEW_GIFT | `giftMsg`：`giftID`、`displayUser`、`giftMetas[].combo` 等 | 不报（差异 3） | 礼物（名称用 `giftID`，每条 1 个） |
| 32 | NEW_LUCKYBAG | `giftMsg`（`extID` 是福袋） | 不报 | 不报 |
| 18 | JOIN_ROOM | `commentMsg`（“が参加しました！”），网页只给主播显示 | 不报 | 不报 |
| 28 | REACT_MSG | 关注、分享、点赞 | 不报 | 不报 |
| 5、6、54、74、79、80 等 | 下播、直播信息、排行、`ROCKVIEWER_UPDATE`、奖励、任务提醒 | | 不报 | 不报 |

评论解成聊天：

| `LiveMessage` | 取值 | 与归档 v4 |
|---|---|---|
| 显示哪些 | `isDirty`、`isDirtyWord`、`isDirtyUser` 都不为真（网页 `receiveChatEpic` 的过滤；`isFraud` 网页不看，这里也不看） | v4 不过滤（差异 4） |
| 文本 | `content`（网页显示的）去首尾空白；为空时取 `comment.text`；都不是文字或为空就不报。弹幕付费版照样是聊天 | v4 先取 `comment.text`，把数字也转成文字（差异 5）；录制里两者总是相同 |
| 用户名 | `displayUser.displayName`，没有时 `displayUser.openID` | 同 |
| 用户 id | `displayUser.userID` | 同 |
| 等级 | `displayUser.level`（大于 0），没有时 `commentMsg.level` | v4 不填（差异 2） |
| 颜色 | `comment.textColor`：`#AARRGGBB`（网页把前两位当透明度）或 `#RRGGBB`，`#` 可有可无，不透明度不管；其他为白色（网页的默认）。录制里全是 `#FFFFFFFF` | v4 不填（差异 2） |
| 时间 | `sendTime`（毫秒）；不大于 0、不是整数或超出 `DateTime` 范围时为空 | 超出范围时 v4 抛 `RangeError`，整帧丢失（差异 7） |
| 消息 id | Ably 的消息 id；没有时帧 id + 序号 | v4 加 `17live:` 前缀（差异 1），没有时为空（差异 6） |

在线人数：`LiveMessage(type: online, data: LiveAudienceUpdate(onlineViewers, liveViewerCount))`；不是非负整数就不报。S06 里 225 s 来了 9 次，间隔 5～46 s 不等，数值 1048～1235，同时段房间接口的 `liveViewerCount` 是 1117～1200，是同一个口径。

帧的解法：文本帧，或 UTF-8 字节（坏字节换成 U+FFFD）；不是 JSON 对象就什么都不做；`channel` 必须等于房间号（字符串）。

## 连接和时序

| 项目 | 本实现 | 归档 v4 | 网页（ably-js 2.21.0） | 依据 |
|---|---|---|---|---|
| 令牌 | 第一次握手前请求；之后沿用，令牌错误后的下一次握手、服务端 `AUTH` 时再请求；请求失败按握手失败重试 | 开始时请求一次，失败即终态 `credentials`；每次“拒绝”后再请求 | `authCallback` 调 `messenger/auth`；令牌错误或 `AUTH` 时再调 | 差异 9 |
| 令牌请求 | POST `{}`，平台层目录请求头 + JSON 内容类型，不跟随跳转，超时 10 s | POST `{}`，只带 Origin、UA、`Accept: application/json`、内容类型、Referer | 网站的 API 客户端 | 差异 10 |
| 地址 | 主机和三个备用主机，失败依次换 | 只有主机 | 主机，失败时换备用主机 | 差异 12；实测 |
| 握手请求头 | Origin、桌面 UA；默认握手 | 同 | 浏览器 | 录制 |
| 加入 | 收到 `CONNECTED` 后发 `ATTACH`，`ATTACHED` 就绪；每次重新加入都报 `DanmakuReady`（框架） | 打开就发 `ATTACH` | 连接 `CONNECTED` 后再挂频道 | 差异 11 |
| 加入超时 | 10 s，超时换连接（框架默认，不单独提示） | 8 s | `realtimeRequestTimeout` 10 s | 差异 14 |
| 心跳 | 客户端不发；服务端每 15 s 发 | 同 | 同 | 录制 |
| 无消息超时 | 25 s（15 s 一个检查点） | 90 s | `maxIdleInterval` + 10 s = 25 s | 差异 14 |
| 断线重连 | 框架默认：四个地址轮换，间隔 1、1、1、2、2、2、2、3 s，第 9 次失败结束；收到任何消息清零；一轮只提示一次；沿用令牌 | 退避相同，一个地址，沿用令牌 | 立即重连，`resume` 接上 2 分钟内漏掉的消息 | M5.0；见“与网页的差异” |
| 令牌错误 | 取新令牌重连；和 `DETACHED` 一起计数，连续第 4 次结束（`connectionFailed`），加入成功就重新计数 | 连续第 4 次“拒绝”结束（`rejected`），从不清零 | 取新令牌重试；新令牌也被拒才失败 | 差异 13 |
| 其他错误 | 连接和频道的 `ERROR` 结束（`connectionFailed`）；`DISCONNECTED` 沿用令牌重连；`DETACHED` 原地重新挂 | 带 `error` 的 6、9、13 一律换令牌重连 | 同本实现（FAILED / 重连 / 重新挂） | 差异 13 |
| `AUTH` | 取新令牌原地发送 | 不管 | 同本实现 | 差异 13 |
| 房间号不对 | `connectionFailed`（`No usable room id`），不请求、不握手；前后空白去掉（平台层的 `normalizeRoomId`） | 不检查 | — | — |
| 帧解不开 | 丢掉这一帧（一条消息解不开只丢这一条），不影响连接 | 同 | 同 | — |
| 诊断文字 | 握手失败的错误里的令牌换成 `<token>` | 不报握手错误 | — | — |
| 代理 | 按平台 `17live` 取路由（构造参数 `proxy`）；令牌请求由 `LiveHttp` 按平台取路由 | 同 | — | — |

## 登记方式

应用（M12）建平台表时：

```dart
DanmakuRegistry({
  SiteIds.seventeenLive: () => SeventeenLiveDanmakuConnection(http: seventeenLiveHttp, proxy: proxyPolicy),
  // …
});
```

| 参数 | 必需 | 说明 |
|---|---|---|
| `http` | 是 | 请求令牌用的 `LiveHttp`，就用给 `SeventeenLiveSite` 的那个（按平台 id `17live` 取代理路由和限流） |
| `proxy` | 否（默认直连） | `live_net` 的 `ProxyPolicy`，每次握手按平台 id `17live` 取路由，和接口请求用同一份设置 |
| `connector` | 否 | 只给测试替换握手；默认 `dart:io` |
| `policy` | 否 | 只给测试缩短时序；默认 `SeventeenLiveDanmakuConnection.defaultPolicy` |

不需要 Cookie 或设置：v3 的 17LIVE 全程匿名（M4.33 没有它的登录和 Cookie），弹幕的令牌也是匿名的。参数来自 `getRoomDetail`（和录制详情），未开播的房间也带参数（频道属于主播，不随场次变），连上后没有消息，开播后自然收到。

## 与归档 v4 的差异

| # | 差异 | 原因 |
|---|---|---|
| 1 | 消息 id 不加 `17live:` 前缀 | 与 M5.1～M5.21 一致：去重闸门只在一个房间内比较 |
| 2 | 聊天带颜色（`comment.textColor`）和等级（`displayUser.level`） | 平台给了，网页也按它们显示；v4 不填 |
| 3 | 不报礼物（v4 报 `giftID` × 1） | v3 所有平台都不显示礼物（`LiveMessageType.gift` 注明“not shown yet”），M5.1～M5.21 也都不报 |
| 4 | `isDirty`、`isDirtyWord`、`isDirtyUser` 为真的评论不报 | 网页不显示它们（只给发言者本人看）；v4 照样显示 |
| 5 | 文本先取 `content`，没有时才取 `comment.text`；不是文字的不报 | 网页的聊天行显示的是 `content`（在画面上飞的付费弹幕才用 `comment.text`）；v4 先取 `comment.text`，还把数字、列表转成文字。录制里两者总是相同 |
| 6 | 消息没有 id 时用帧 id + 序号 | Ably 的规则（ably-js 同样补上）；v4 这时没有 id，同样的文字会被去重闸门按时间窗合并 |
| 7 | `sendTime` 超出 `DateTime` 范围时只是没有时间 | 统一原则“一行坏数据只跳过这一行”；v4 抛 `RangeError`，整帧（可能有好几条消息）丢失 |
| 8 | 只认 gzip + base64 的载荷 | 网页只认这种（`gzip_base64`，失败就不显示）；v4 还接受明文 JSON 文本和 JSON 对象 |
| 9 | 令牌在握手时取，请求失败按握手失败退避重试；`provider` 不是 1 时以 `connectionFailed` 结束 | 一次网络抖动不该让这个房间没有弹幕直到重新进房（同 M5.21 差异 5）；v4 开始时失败就终态 `credentials`，`provider` 不对也一样 |
| 10 | 令牌请求用平台层的目录请求头（多 `Accept-Language`，`Accept` 是平台层的） | 和平台层其他请求一致；服务端都接受 |
| 11 | 收到 `CONNECTED` 后才发 `ATTACH` | Ably 协议和 ably-js 都是连接好了再挂频道；v4 打开就发，服务端也接受（两次录制） |
| 12 | 主机失败时换网站配置的三个备用主机 | 网站就这样配置；实测三个都能用同一个令牌连上、加入、收到消息；v4 只有主机，它不可用时一直重连同一个 |
| 13 | 拒绝和异常照 ably-js 分开处理：只有令牌错误（40140～40149）换令牌，它和 `DETACHED` 连续第 4 次结束且加入成功后重新计数；其他连接 `ERROR` 和房间频道的 `ERROR` 结束；不带令牌错误的 `DISCONNECTED` 沿用令牌重连；`DETACHED` 原地重新 `ATTACH`；`AUTH` 取新令牌原地发送；别的频道的错误不管 | v4 把带 `error` 的 6、9、13 都当“拒绝”：换令牌重连并提示，第 4 次终态，一次开始里从不清零（每次令牌过期记一次，第 4 次过期后整场没有弹幕）；别的频道的错误也算；不理 `AUTH`，令牌过期前服务端要求换令牌时只能等断开 |
| 14 | 加入超时 10 s、无消息超时 25 s | ably-js 的 `realtimeRequestTimeout` 和空闲判定（`maxIdleInterval` + `realtimeRequestTimeout`）；v4 用运行时默认的 8 s、90 s |
| 15 | 结束原因用 M5.0 的类型 | v4 的 `credentials`、`rejected`、`maxRetries`；界面文字由 M13 给出 |

没有改的地方：令牌接口和读法、地址和查询参数、握手请求头、`ATTACH` 的内容、客户端不发心跳、`ATTACHED` 算加入、按频道过滤、gzip + base64 的解法、评论和在线人数的字段（用户名、用户 id、时间、`liveViewerCount`）、其他类型不报，都与 v4 相同。

## 与网页的差异

- 断线重连不带 `resume`：ably-js 重连时带上 `connectionKey`，服务端补发 2 分钟内漏掉的消息；框架的 `LiveSocket` 每次用同样的地址，做不到按次改查询参数以外的续接（握手包装可以改地址，但要同时处理续接失败、`connectionKey` 过期等，收益小），断线期间的弹幕会漏掉，和其他平台一样。列为候选。
- `DETACHED` 后重新挂也失败时，ably-js 把频道挂起、15 s 后在同一连接上再试；这里换连接。
- 退避按框架（最多 8 次）；ably-js 会一直重试（每 15 s，2 分钟后每 30 s）。
- 不处理下播（5）、禁言（`liveinfo.mute`）等房间状态。

## 审查发现的归档 v4 问题

| # | 问题 | 位置（归档 v4） | 根因 | 处理 |
|---|---|---|---|---|
| 1 | 一次开始里的“拒绝”从不清零：令牌过期（服务端断开并带 40142）记一次，第 4 次过期后以 `rejected` 终止，之后整场没有弹幕；别的频道的错误、`DETACHED`、服务端要换节点的 `DISCONNECTED` 都算“拒绝” | `runtime/socket_connector.dart` 的 `rejected` 分支；`SeventeenliveProtocol.decode` 的 `case 6 \|\| 9 \|\| 13 when root['error'] != null` | 没有区分令牌错误和其他错误，也没有看 `channel` | 差异 13 |
| 2 | 服务端 `AUTH`（要求换令牌）不处理 | `decode` 的 `default` | 规格没有记 `AUTH` | 差异 13 |
| 3 | `sendTime` 超出范围时整帧丢失 | `_time` | `DateTime.fromMillisecondsSinceEpoch` 抛错 | 差异 7 |
| 4 | 网页隐藏的评论照样显示 | `_event` 的 `case 3` | 没有对照网页的过滤 | 差异 4 |

## 实测

2026-09-28 22:57～23:02 UTC、2026-09-30 12:02～13:35 UTC，只读、匿名、直连，没有登录，没有发言。用只依赖 `dart:io` 的小程序：取推荐区块里在线最多的房间，`POST messenger/auth` 取令牌，连接，打开就发 `ATTACH`（同 v4），此外什么都不发；每分钟读一次房间接口的人数用来对照（2026-09-30 那次另外每 5 分钟请求一次 `messenger/auth` 看令牌是否变化）。录制和脱敏脚本没有放进仓库。

- **令牌**：回答总是 `{"provider":1,"token":"<应用 id>.<…>","permissions":["*"]}`；同一时间段里拿到的是同一个令牌（2026-09-28 22:57～22:59 的 4 次请求相同；2026-09-30 从 12:02 到 12:58 每 5 分钟一次的 12 次请求相同，13:03 那次换了新的）。两天拿到的令牌不同，应用 id 相同（网页脚本里 Ably API Key 的应用 id 也是它）。
- **令牌的有效期**：没有测到上限。2026-09-30 12:02 取到的令牌在接口换了新令牌之后的 13:34 仍能连上、加入、收到消息（至少 92 分钟）；两天前（09-28）的令牌连上后服务端回 `ERROR` 40142 `token expired`，随后以 1000 关闭——这是令牌错误，本实现取新令牌重连。90 分钟的连接里服务端没有发过 `AUTH`，也没有因为令牌断开过。
- **握手和加入**：打开后约 5 ms 收到 `CONNECTED`，`maxIdleInterval` 15000、`connectionStateTtl` 120000；`ATTACH` 后约 0.2 s 收到 `ATTACHED`（`flags` 786432）。`ATTACH` 在 `CONNECTED` 之前发也被接受；同一频道 `ATTACH` 两次，回两个 `ATTACHED`。
- **不存在的房间号**（`999999999999`）：照样 `ATTACHED`（`flags` 多了“有在线成员”），随后一个空的 `SYNC`（16），没有消息。频道是按名字随用随建的，所以本实现只检查房间号的格式。
- **备用主机**：`17-media-a/b/c-fallback.ably-realtime.com` 用同一个令牌都能连上、加入并收到这个房间的消息。
- **坏的令牌**：编造的应用 id → `ERROR` 40400 `No application found with id …`，随后以 1008 关闭；应用 id 对、其余编造 → `ERROR` 40101 `token invalid - could not decode legacy token: invalid token size`，1008 关闭；空令牌 → `ERROR` 40101 `no application id found in request`，1008 关闭。都不是令牌错误（40140～40149），ably-js 对它们直接失败，本实现以 `connectionFailed` 结束。
- **下行**：S06 的房间（约 1150 人）225 s 里 96 条消息：26 条评论（9 条是主播自己的）、18 个礼物、11 个直播信息、9 个在线人数、8 个福袋、8 个 74、6 个奖励、5 个反应、2 个入场、2 个任务提醒、1 个排行；14 个心跳，间隔 15 s。2026-09-30 另一个房间（`29577348`，约 300～680 人）连了约 62 分钟：566 条消息（147 条评论、39 个在线人数，其余是 74、6、13、79、56、54、18、80、28、32），245 个心跳；评论的颜色全是 `#FFFFFFFF`，`content` 和 `comment.text` 全都相同，没有隐藏的评论和付费弹幕；在线人数 307～677，同时段房间接口 303～680。第 3709 s（加入后约 62 分钟）socket 以 1006 断开，之前没有 `DISCONNECTED` 或 `ERROR`，而且前 20 s 有一批消息晚到了几秒，令牌那时仍有效（见上），所以是网络层的断开（09-28 那次录制在 225 s 也是这样断开）；框架对这种断开按普通断线重连，沿用令牌。
- **在线人数**：`LIVE` 的 `liveViewerCount` 和房间接口同时段的 `liveViewerCount` 在同一个范围（S06：1048～1235 对 1117～1200），网页的在线人数就是用它更新的（`updateLiveScoresEpic`）。
- **本实现**：没有接到真实服务器上跑（测试用本地服务器和假连接）；协议和上面逐项对照过，与实测一致。
