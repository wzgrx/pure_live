## 做法

照 T02a.1 哔哩哔哩：接口和输出沿用 v3，解析写成纯函数，用样本逐字段对照 v3 的输出，差异逐条说明。

- **解析采用归档 v4 的实现**，输出改回 v3 的模型：
  - 页面数据是 React Server Components 的流式载荷（`self.__pace_f.push`），按行解析并解开 `"$13"` 这类引用；
  - 错误有类型；综合搜索的分块正文能读。
- **会话**：每个 Cookie 一个会话，Cookie 一变就换；匿名 `ttwid` 每个会话只取一次，并发请求共用。
- **v3 的请求顺序全部保留**：
  - 详情先 enter，失败再抓直播间页面；
  - room_id 先走 reflow，本场已结束再用 web_rid 查 enter；
  - 搜索依次试直播搜索、综合搜索、分区匹配。

## 签名：纯 Dart

v3（3.2.11）已经不依赖 JS 引擎：上游在 7410eb9f 删掉了嵌入 QuickJS 的 `core/scripts/douyin_sign.dart`（65 万字符，含 a_bogus 的 JS 和 webmssdk），换成 Dart 的 `utils/douyin/abogus.dart`（SM3 用 dart_sm 包）和弹幕的 `danmaku/xbogus.dart`。这里以 v3 的 Dart 实现为准重写：

| 签名 | 用在 | 做法 |
|---|---|---|
| msToken | 所有 a_bogus 请求 | 184 个随机字符（`A–Z a–z 0–9 =`），与 v3 相同 |
| a_bogus | enter、分区房间 | 算法、常量表、字母表逐位照搬（移植自归档 v4）；SM3 自己实现，不再依赖 dart_sm |
| X-Bogus | 弹幕连接的 `signature` | 逐位照搬 v3 的 `generateXBogus` 和 `getSignature` 的参数串，放在 `DouyinSigner.danmakuSignature`，T06a 直接调用 |

- **验证**：把 v3 的 `abogus.dart`、`xbogus.dart` 和 dart_sm 的 SM3 原样拷出来，只把时钟和随机数改成可注入，跑出固定输入的结果作为测试向量：
  - a_bogus 4 组（与归档 v4 的向量一致）；
  - 完整签名地址 2 组（v3 `buildRequestUrl`）；
  - X-Bogus 5 组；
  - SM3 另用国标 GB/T 32905-2016 的两个示例。
- **v3 的一处怪异照旧保留**：a_bogus 第 24、25 字段（时间戳的高位字节）在 v3 恒为 0。原因是先截成 32 位再右移（`abogus.dart:665-666,695-696`），参考的 Python/JS 原版是 `时间戳/2^32`。录样时用的正是这个版本，带签名的分区和 enter 都拿到了数据；不带签名的会被滑块拦下（S08-partition-rooms-unsigned）。所以服务端接受这种写法。
- **没有移植的部分**：
  - 旧 JS 里的 webmssdk（`byted_acrawler.frontierSign`，约 1 万行混淆代码，依赖浏览器环境）；
  - 另一种 a_bogus 变体（pageId 6241、末尾 RC4 密钥 `y`）。

  v3 已经不用这两样，改用上面的 Dart 实现，所以不再需要，也无法逐位验证。

## 与 v3 的有意差异

| # | 差异 | 原因 |
|---|---|---|
| 1 | `display_type` 为 1 的房间：显示的数字不变，口径从“累计观看”改为“在线人数”，没有累计值 | 抖音网页对这种房间显示“713在线观众”，v3 却当成累计观看（REG-DOUYIN-008）。它的累计字段只有占位的 0 和分档文本（“10万+”），拿来显示会让几乎所有卡片的数字和排序都变掉 |

| 8 | 分区页的签名请求遇到滑块时，改请求 `webcast.amemv.com` 一次 | 归档 v4 的做法；该主机不签名也给同样的列表 |

## 保持 v3 行为、没有采用归档 v4 或上游做法的地方

- **推荐卡片没有分区时仍写“热门推荐”**：v4 返回空，电视版改成多语言文字；这里保持 v3 的输出。
- **匿名搜索仍用分区匹配兜底**：v4 直接报“需要登录”，匿名用户就搜不到任何房间。
- **媒体请求头仍带 Cookie**（用户的，或匿名的 ttwid）：v4 为了隐私去掉了，但没有样本证明 CDN 不需要。有媒体首部样本（规格 S10）后再定。
- **房间号是 web_rid，请求什么返回什么**；用本场 room_id 请求时身份换成主播的 web_rid。v3 也是这样，因为 room_id 下播就作废。本场 room_id 放在 `DouyinRoomData.roomId`，弹幕和外部打开用。
- **详情的请求顺序**：enter 失败（不存在除外）就抓页面，网络错误也兜底。v4 只在风控和格式错误时兜底。
- **签名指纹**：沿用 v3 的取值范围；每个适配器固定一个窗口尺寸（归档 v4 的做法），v3 每次请求随机一个，服务端两种都接受。
- **搜索卡片的封面**：先用主播大头像，再用房间封面。这是 v3 的顺序，改了会让卡片外观变样。
- **不新增链接格式**：`/root/live/`、`/follow/live/` 等网页链接，归档 v4 加了，但没有样本，规格也标着待确认。
- **只输出视频档**：不输出 v3 不读的 `lls`、`cmaf` 协议；默认画质仍由播放层决定。

## 取流

- 抖音的播放地址随详情一起下发，没有单独的取流请求。`DouyinRoomData` 保存：
  - web_rid；
  - 本场 room_id；
  - 在播时的 `stream_url` 原样（播放层的几何提示要读其中的 `sdk_params`）；
  - 取到详情的时刻。
- 画质的规则与 v3 相同：
  - 按 sdk_key 关联，不按位置（REG-DOUYIN-004）；
  - 排除纯音频档（REG-DOUYIN-001）；
  - 按语义等级排序（REG-DOUYIN-005）；
  - 地址相同的别名只留一个（REG-DOUYIN-006）；
  - `LivePlayQuality.data` 仍是地址列表。
- 线路：
  - 先 FLV 后 HLS，线路编号 `flv`、`hls`、`flv-2`……；
  - 编码取 `sdk_params.VCodec` 或 `v_codec`（`bytevc1` 即 HEVC），录到的推荐里 123 档中 81 档是 H.265；
  - 请求头就是 v3 播放层发的：UA、Origin、房间页 Referer、Cookie。
- 有效期：
  - 从 `expire`（十进制或十六进制）、`volcTime`、`wsTime + keeptime`、`k + t` 读出绝对时刻，录到的都是 7 天；
  - 提前 min(10 分钟, 寿命的 1/4) 续期；
  - 到期是否切断已建立的连接未知，标记为不切断，不套用斗鱼的规则。
- 恢复取流重新获取详情，不复用旧地址；原画质已不提供时换成最高档，并报告实际画质。
