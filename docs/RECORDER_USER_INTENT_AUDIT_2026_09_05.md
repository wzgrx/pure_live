## 实施前发现的首次失效状态

- `startTask` 只在申请存储权限后检查服务关闭，没有保存本次用户操作身份。
  等待期间停止/移除/同 ID 替换后，它仍清除停止标记、重置统计，再尝试排队。
- 同时点击开始各自发起权限请求；`_startingTasks` 仅覆盖随后同步排队的一小段。
- `stopTask` 等待调度器取消时，另一开始动作先清空旧统计并重新排队；旧停止最后
  又把卡片置为 stopped。旧任务的 `updateTask` 按 ID 替换列表，也会覆盖新的卡片对象。
- 启动恢复的文件检查/收尾没有登记在录制启动所等待的所有权中。用户开始可与旧文件
  恢复并行，后者覆盖新状态；只有逐个到达任务时才恢复，也漏掉首个慢任务之后的预约。
- `addTask` 的权限返回后缺少关闭检查，可向已经关闭的服务追加卡片。
- 调度器的 cancel 最多等待 runner 20 秒后返回，但保留仍运行的槽位；控制器将该
  返回误当成已经结束，提前清除统计监测与展示 stopped。取消请求和原生收尾是两个信号。

## 修复设计与不变量

1. 用户开始在第一个 await 前登记任务对象及请求实例；重复点击共享结果，停止、移除和
   服务关闭立即作废旧开始。权限结果仅说明资源访问条件，不代表旧操作意图仍有效。
2. 停止与中断文件恢复拥有可等待的完整 Future；新开始先等旧收尾释放，再重置计数和
   派发。不同任务保持独立，不用全局播放器锁或任意延迟来掩饰竞争。
3. 恢复任务在列表对用户可见之前全部预约；尚未开始扫描的旧文件同样保持恢复资格。
   同 ID 任务替换或服务关闭后，迟到回调不提交旧对象、不继续派发后续文件处理。
4. 未成功处理的旧分片继续保留。新录制开始不删除旧文件、历史待处理目录或错误证据。
5. 保留共享调度器的并发限制、正常原生停止/最终采样合同和有界持久化；不增加后台轮询。
6. 调度器提供仅等待已捕获运行实例的完成 Future，控制器在 cancel 之后等待该真正的
   收尾边界。原生仍运行时保留监测、统计及文件所有权；新开始继续等待，不冒充启动成功。
