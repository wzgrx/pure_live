## v3 的冻结输出

归档只给五个大站生成过 `expected.json`。这次按 E03.1 SOOP 的口径补上：

- 把 v3 的 `core/site/picarto/` 三个文件（`picarto_api.dart`、`picarto_hls.dart`、`picarto_site.dart`）和 `LiveRoom`、`LiveArea`、`LiveCategory`、`LivePlayQuality`、`LiveSite` 接口、`live_directory.dart`、`live_search.dart`、`request_scope.dart`、`HttpHeaderPolicy` **原样复制**到一个临时的纯 Dart 包里（依赖 3.x 用的 dio 5.11.1），只把运行环境换成桩：
  - 传输用 v3 自带的注入点 `PicartoApi(request: …)`，按请求地址回放样本；和 v3 的 `_defaultRequest` 一样，非 200 的响应正文为空；
  - `i18n` 返回 3.x `zh.json` 的文字，房间音量管理器、`HttpClient` 单例不会被调用。
- 逐个样本调用 v3 的入口（`PicartoApi.categories`，`PicartoSite` 的 `getCategores`、`getDirectoryPage`、`getRecommendRooms`、`getCategoryRooms`、`searchRooms`、`getRoomDetailForRefresh`、`getRoomDetail`、`getRoomDetailForRecording`、`getLiveStatus`、`getPlayQualites`、`getPlayUrls`，`parsePicartoHls`），抛出的异常记为 `throws`，同时记下 v3 发出的请求（地址、`playHeaders`）和进房、刷新各发了几个请求。搜索按 3.x 搜索页的每页 20 条调用。
- 房间的投影与其他平台相同：`toJson` 加上 `link`、弹幕参数，去掉 null 和空集合。

## 做法

- **接口和输出沿用 v3**：`LiveSite` 和 v3 实现过的全部可选能力（关注刷新、录制详情、恢复取流、目录分页、可取消的搜索），外加取流线路（`LivePlayUrlResolver`）和 `LiveSiteLinks`。3.x 的 JSON 不变。
- **请求照 v3**：
  - 接口在 `ptvintern.picarto.tv`：分类 `api/languages-categories`，目录 `api/explore`（按观众数、`filter_params[adult]=false`，分区另加空的语言过滤和 `<id>: true`），搜索 `api/search`（`searchProfiles`），详情 `api/channel/detail/<名字>`；参数与 v3 相同。
  - 所有请求带同一组请求头：v3 的 `playHeaders`（`Referer: https://picarto.tv/`、`Origin: https://picarto.tv`）加上 v3 播放层补的 Chrome 140 UA。v3 的接口和主列表请求没有设 UA（发出去的是 dart:io 的 `Dart/…`）。
  - 匿名，没有 Cookie（v3 没有 Picarto 登录，设置里也没有它的 Cookie），所以不注入 `CookieVault`。
  - 请求次数：分类 1 个（只有第 1 页有），目录、搜索各 1 个；关注刷新只请求详情（1 个）；进房和录制是详情加主列表（直播时 2 个，未开播 1 个），与 v3 相同。
- **目录**：一个分类“Picarto”，第一个分区是“公开直播（不含成人内容）”（`areaType: 'directory'`、`areaId: 'live'`，就是推荐），后面是平台的分类。目录分页每页 30 条，`page < last_page` 就还有下一页（离线、成人条目被滤掉，条数不能说明有没有下一页）。
- **严格校验照 v3**：v3 对每个响应都做了严格检查（页码、每页条数、`total` 对不上，某一行没有合法的名字、id、状态或 `adult` 标记，分区页里出现别的分区的频道），不给出残缺或空的列表。这些都保留，报 `ApiChanged`。
- **详情**：房间号是响应里频道名的平台写法（请求 `thebaker` 得到 `TheBaker`），与 v3 相同；请求时的写法留在 `PicartoChannel.requestedId` 和 `PicartoRoomData.requestedId` 备查。直播中时，按 `channelId` 在 `getMultiStreams` 里找自己那一路（REG-PICARTO-001），和负载均衡给的边缘节点拼出主列表地址；进房时再读主列表，画质放进 `PicartoRoomData`。人数：`viewers` 是同时在线（`onlineViewers`，也写进 `watching`），`total_views` 是累计观看（`totalViewers`），口径是 `onlineViewers`，与 v3 相同。
- **取流**：画质照 v3 的 `parsePicartoHls`：每个视频档位一个画质（分辨率、帧率、编码和分组组成 id，不含码率和主机，换边缘节点后 id 不变），名称 `720p 60fps`（没有分辨率时 `HLS 3.5 Mbps`），按码率从高到低；主列表带独立音轨或本身就是媒体列表时只有一个 `HLS Auto`，播放主列表本身。每个地址一条线路：v3 播放层的 Picarto 请求头、HLS、编码、边缘节点主机作线路编号。地址没有签名，没有租期；恢复时重新请求详情和主列表（REG-PICARTO-003）。
- **弹幕**：v3 没有 Picarto 弹幕（`EmptyDanmaku`）。进房时只输出 `PicartoDanmakuArgs`（平台写法的频道名、频道 id，归档 v4 连接弹幕用的就是这两项），不多发请求；是否启用由 D01 决定。

## 保持 v3 行为、没有采用归档 v4 或上游做法的地方

（E06 平台层升级 已按升级决定改掉其中的严格校验、画质排序和名称、未开播封面、搜索标题、私密频道和恢复时的档位，见文末“升级落地（E06 平台层升级）”。）

- **房间号用平台写法**（A:321）：v3 把房间号统一成响应里的频道名写法，3.x 存下的关注用的就是这个写法。用小写链接打开同一个房间时，改写后身份仍是已关注的 `picarto:TheBaker`，房间页显示已关注，也不会重复关注；关注刷新返回同一写法，合并不会失配。这在这里是保持身份一致的做法，不是 bug。
- **严格校验**（问题 12、14）：归档 v4 跳过坏行、不核对页码，缺取流字段时刷新照样成功。这会改变用户看到的列表和状态，列为候选。
- **画质**：名称 `720p 60fps`、`HLS Auto`（归档 v4 是“自动”），id 是 v3 的档位 JSON，按码率排序（归档 v4 先按高度），同一档位的多个地址都作为线路（归档 v4 只留第一个）。
- **独立音轨时播放主列表**（`HLS Auto`）：归档 v4 没有这条，上游和 v3 有。
- **多人同播时要求恰好一路是自己的**：归档 v4 取第一个。
- **进房和录制时就读主列表**（v3 的两个请求）：归档 v4 只在取流时读。
- **未开播的频道没有封面**：归档 v4 用 `getMultiStreams` 里的旧缩略图。
- **搜索卡片没有标题、分区**：归档 v4 用频道名作标题。
- **未开播时在线人数照样写 `viewers`（通常是 0）**：归档 v4 只在直播中写。
- **标题不解码 HTML 实体**：归档 v4 解码；样本的标题里没有实体。
- **私密频道在三种深度都报错**（`NeedsLogin`）：归档 v4 照常给详情（规格记为待确认，没有样本）。
- **恢复取流时档位变了就失败**（问题 13）：归档 v4 退回最好的一档。
- **分类只有第 1 页**，第 2 页起返回空，不请求。
- 显示名仍是“Picarto”。上游 pure_live_TV 与 v3 相同，没有要采用的修复。

## 回归条目的覆盖

三条都属于平台层，都有测试直接覆盖：

- 001 多人同播时按 `channelId` 选自己那一路：样本 S04 直播（一组四路，自己是最后一路）、合成响应（两路），以及两路都是自己时报 `ApiChanged`；
- 002 搜索的 `count` 不可靠：解析不读 `count`，以空页结束（样本 S03 的 `count` 是站内总数）；
- 003 边缘节点按请求分配：恢复时重新请求详情和主列表，每次拿到新的边缘节点（移植 v3 的用例），进房得到的房间本身不再发请求。

### 统一原则在 Picarto 上的落实

| 事项 | 做法 |
|---|---|
| 开播时间 | 内部接口（目录、搜索、详情）都没有开播时间。公开接口 v1 的 `api/v1/channel/name/<名字>` 有 `last_live`：<br>- 格式 `2026-09-28 16:12:10`，是 UTC；<br>- 在播时就是这一场的开播时间。依据：4 个在播频道与 HLS 分片名（从开播起的毫秒数）推出的开播时间都差 10 秒以内；<br>- 未开播时是上一场的开播时间，不填。<br>进房时对在播频道和主列表**同时**请求它（`PicartoApi.liveSince`），失败（网络、404、改版、取消）不影响进房。关注刷新、列表、搜索不填：每个频道要多一个请求，而刷新和列表不能加请求。进过一次直播间后，合并规则把开播时间保留到状态变化为止 |
| 受限类型 | 详情有 `private`（必须有，否则 `ApiChanged`，同 v3）：私密填 `private`，否则填 `none`。目录行和搜索资料没有这个字段，留空；目录行若带了 `private`，照样填。成人频道（`adult`）不算受限：匿名就能播放（E03.3 规格 §6.4），不标 `adult`（标了取流就要报 `NeedsLogin`） |
| 受限的直播改为直播中 | 私密频道直播中时状态是直播中（11-9）；v3 在三种深度都报“无权访问” |
| 占位信息 | 平台给没设标题的频道的默认标题 `My Channel Title`（`PicartoApi.placeholderTitle`）留空。2026-09-28 的 186 个在播频道里有 11 个是它，S02 第 1 页有 4 个，S04 未开播样本也是。这样刷新不会用它覆盖关注里存下的标题（X-2），界面按 M13 的规则显示。名字就是频道名，没有占位值；封面没有占位图 |
| 回放、轮播、“不可播放” | 这些接口没有回放和轮播状态（录像 `videos` 不在 v3 的范围里），不涉及 |
| 画质命名 | 11-4 是改名条目，但主列表不标哪一档是源画质（多数只有一档），名称仍按分辨率（`720p 60fps`）。只有整份主列表那一档从“HLS Auto”改为“自动”。画质 id 没有变 |
| 默认编码 | 样本和实测的主列表都是 H.264；线路本来就带编码（E03.3），“优先 H.264”对本平台没有影响 |
| 房间身份 | 见 11-8 |
| 按主播关注 | 本来就是按频道关注，没有单场 id |
| 容错 | 见 11-2、11-3 |
| 翻页 | 目录、搜索都是服务端分页，适配器不缓存 |
