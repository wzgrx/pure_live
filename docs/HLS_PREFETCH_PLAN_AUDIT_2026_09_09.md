## 实现

新增 `HlsPrefetchScheduler.selectAll`：把完整选择集合放入临时表，检查来源 URI、身份、名额、重复 ID、所有初始清单的保留窗口和渲染合同，再一次性写入 feed 表，最后才启动下载/轮询。第二路有未支持标签、空/重复 ID、非法来源或整个集合超限时，前一路不会先进入活动状态。旧单路 select 通过同一准入路径，原有单路调用继续工作。

这里的“原子”是**初始元数据与选择状态的原子准入**，不是承诺未来两路网络请求同时成功。网络失败、运行中清单变化、续签及来源切换仍由后续运行期规则负责。迭代输入按剩余最多两个 feed 的容量检查，超限即退出，不把外部 iterable 无界复制进内存。

新增 `HlsPrefetchPlan.fromMaster`，只识别无需替 native 做选择的 master：唯一视频/复用流，或唯一视频及其唯一明确 AUDIO 组。URI 使用 master 最终地址解析；来源及媒体协议/凭据/片段/长度有检查，HTTPS 引用降级不进入该计划。返回的 URI 集合不可变。

多清晰度、多个语言/音频候选、字幕/隐藏字幕组、session key、未知状态标签/属性、组关联不完整、重复字段、悬空 STREAM-INF、相同 URI 同时作为两路等，返回无预取计划。它不是通用 HLS 解析器，也不猜测 native 会选择哪档；生产调用者应整体保留现有路径，而不是选择第一档或只启用其中一路。媒体清单本身仍由已有严格 snapshot/window/renderer 合同验证。

原生实验适配层已经使用该计划：读取实际源站 master → 获取两份初始媒体 snapshot → selectAll 一次性准入 → 返回 master；随后 native 请求子清单时复用已选 feed，不重复选择/重复加载。此前由 native 顺序访问两路后逐个 select 的实验接线已替换。仍保留原始 master 和媒体字节，不改质量、音轨或时间戳。
