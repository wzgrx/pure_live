## 实现

1. `CCSite.getCategores` 改为读取官方游戏元数据 GET 与直播入口配置 POST（公开配置 ID）。请求走现有 HttpClient、应用代理与超时设置；无 Cookie、账号、设备 ID 或签名生成。移除旧 HTML/旧 game_list/四空页处理。
2. `CCCatalog` 按 appKey 连接两份响应，只保留配置指定的入口。当前夹具得到 **20 分类 + 3 官方入口**；106 个普通游戏元数据不扩展为直播分类。分组使用“直播分类”和“官方房间/专题”，不猜测配置未给出的 PC/手游标签。
3. 配置 ID、code、容器、条目数、名字、对应元数据、可见性和目标路径分别校验。隐藏项排除，明确空/隐藏配置正常返回空；缺组、错结构、重复身份、未知路由和外部主机报错，不部分提交目录。条目限额用于解析后的结构检查，不宣称网络传输有独立字节硬上限。
4. 游戏分类保留数字 areaId；官方入口使用 `official:<numeric-id>` 独立身份，复用原 LiveArea JSON 持久化结构。旧数字收藏仍指向既有分类 API，父类别改变不改变收藏身份。官方入口由数字 ID 重建固定 CC HTTPS 目标，不从持久化数据执行任意 URL。
5. `AppNavigator.toCategoryDetail` 区分官方入口；以外部浏览器打开已配置房间/专题链接，处理失败与重复点击。`AreaCard` 显示浏览器说明及外部打开图标；普通分类仍进入应用房间列表。这里是明确的官方网页入口，不表示新增赛事原生解析、媒体播放或录制能力。
6. 目录刷新按最新选中父 ID 恢复标签；父项消失则选第一项，避免四旧父项变两新父项后显示空白。刷新期间的用户标签选择保留。CC 列表错误显示持久重试状态，失败前已有分类保留；未修改播放器生命周期或通用房间分页。
