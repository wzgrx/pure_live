# 播放模块规格（playback）

- 状态：第 1 阶段草案，2026-09-27
- 范围：单直播间、多画面每一格、系统画中画、应用内小窗的播放行为；内核全平台只用 mpv（ADR 0006），不再有 fvp、IJK、Exo，也没有“换引擎”这一步
- 依据：旧代码行号已在 2026-09-27 对照 master 工作树核对；提交哈希和测试位置来自第 0 阶段诊断（[02-player](../../docs/rewrite/diagnosis/02-player.md)、[03-live-room](../../docs/rewrite/diagnosis/03-live-room-multiview-danmaku.md)）
- 本规格只规定行为和契约，不规定类名和代码拆分

**缩写**：PM = `lib/player/core/player_manager.dart`；MKA = `lib/player/adapters/media_kit_adapter.dart`；PST = `lib/player/core/playback_source_transport.dart`；FSR = `lib/player/core/flv_splice_relay.dart`；PLC = `lib/player/core/playback_lifecycle_coordinator.dart`；GPS = `lib/player/global_player_service.dart`；MVC = `lib/modules/multiview/multiview_controller.dart`；PERT = `test/player_error_recovery_test.dart`；MVT = `test/multiview_test.dart`。

**验收方式**：【单元】纯 Dart 单元测试，使用假时钟；【轨迹】回放真实 libmpv 录下的事件轨迹（见 §4）；【真机】K90（Android）或 Windows 实机记录；【探针】真实网络探针。

## 0 术语

| 术语 | 含义 |
|---|---|
| 会话 | 一次“打开房间/选择源”到关闭之间对播放器的占有。关闭、硬释放、每次换源都会让旧会话失效 |
| 源代次 | 同一会话内每次打开源（换画质、换线路、签名刷新、重建）都是新代次；同一 URL 重开也是新代次 |
| 播放意图 | 用户是否要播放。只由用户命令改变，内核上报的 playing/paused 不能改写它。每条用户命令让意图修订号加一 |
| 挂起 | 非用户原因的临时暂停（后台、音频打断），带令牌，不改变播放意图 |
| 推断类故障 | 由看门狗推断的故障：缓冲停滞、画面停滞、意外暂停、首帧超时。之后出现进展就作废 |
| 确认类故障 | 内核报错、直播中意外 completed、打开失败。残留帧不能推翻 |
| 租期 | 线路自带的 `refreshAt`（何时续期）和 `cutsConnection`（到期是否断开已建立的连接），由站点适配器产出 |
| 首帧栅栏 | 候选源真正呈现第一帧之前，不替换当前画面（没有帧进度的平台用“playing=true 且视频尺寸非零”代替，见 MON-5） |
| 源提交 | 打开成功后发布的快照：会话、意图修订号、房间、源、画质与线路选择。其他模块只信任当前的提交快照 |

## 1 会话生命周期

- **SES-1 懒创建**：浏览首页、设置时不创建原生播放器、解码器和纹理；第一次打开房间才创建。
  证据：GPS:70-73；PM:550-553。验收：【单元】未进房时内核创建次数为 0；【真机】首页空闲内存对比基线（Windows 私有 481 MB、Android PSS 195 MB，`docs/rewrite/BASELINE.md:39,52`）。
- **SES-2 串行执行，意图立即生效**：创建、打开、暂停、切换、释放等原生命令按到达顺序串行执行；意图变化（播放、暂停、关闭）在命令发出的同一时刻生效，不排队。排队中的旧任务执行前必须核对意图修订号，过期就放弃。
  证据：PM:1110-1118、1209-1243、3582-3609。验收：【单元】close 之后，已排队的打开不得出声或出画。
- **SES-3 打开**：依次为：意图修订号加一 → 取消未完成的输入 → 换房时清空恢复计数、线路失败名单、窗口历史和提交快照 → （串行）开始新源代次，几何回到 unknown → 先记下完整请求（URL 列表、请求头、画质选择），这样内核初始化失败也能进入恢复链 → 必要时创建内核 → 绑定本代次事件 → 打开源 → 成功后发布源提交快照。
  证据：PM:1209-1301、1358-1533、683-749。验收：【单元】参照 `test/video_source_commit_listener_test.dart`。
- **SES-4 同一 URL 重开是新代次**：软解重试、签名刷新返回同一 URL、手动重试，都必须真正重开并清空上一代次的尺寸与错误。
  证据：MKA:540-549；PM:4254-4260。验收：【单元】。
- **SES-5 暂停与继续**：暂停：撤销播放意图，清空挂起，取消未完成输入、看门狗、退避和预算清零计时，再暂停内核。继续：如果源还没打开完（暂停发生在打开途中），重新打开保存的源；否则播放，并重新布置看门狗、预算清零计时和续期。
  证据：PM:2723-2757。验收：【单元】。
- **SES-6 关闭**：同步撤销意图、使会话失效、清空提交快照、取消未完成输入和所有计时器；然后串行执行：Windows 画中画先还原主窗口 → 等界面卸载（最多 50 ms，没有 vsync 时不无限等）→ 停止后台音频服务 → 按设置软停或硬释放。
  证据：PM:3582-3649、793-810；提交 b231449e；PERT:2579-2720。验收：【单元】。
- **SES-7 软停与空闲释放**：软停卸载媒体、关闭输入和中继、状态回到 idle，但保留内核实例；45 秒内没有新的播放、也不在画中画或小窗，就硬释放。错误状态下软停直接硬释放；软停失败也改为硬释放。
  证据：PM:3656-3702；提交 c5072259。验收：【单元】假时钟 45 s；【真机】离开房间 60 s 后内存回落到首页水平。
- **SES-8 硬释放**：会话失效，取消全部计时与输入，释放内核和输入，清空纯音频状态和恢复计数；等原生释放真正完成才返回（Windows 顺序见 SURF-2）。
  证据：PM:3704-3741。验收：【单元】；【真机】见 SURF-2。
- **SES-9 从小窗回到同一房间复用会话**：不重开源，沿用当前会话和提交快照（画质、线路、纯音频）；房间不同则放弃复用。
  证据：PM:571-623、750-775。验收：【单元】；【真机】回房无黑屏、无重连。
- **SES-10 音量**：桌面每个房间恢复保存的音量；手机音量属于设备，只读不写（全局静音除外）；任何候选播放器在提交前静音，提交时再设为目标音量。
  证据：PM:1486-1499、2047、2083-2100；提交 789f03cc；PERT:846。验收：【单元】。
- **SES-11 只对连续直播做直播专属恢复**：回放、回看（`isRecord`、`isCatchUp`）不启用意外暂停、意外 completed、退避这几项。
  证据：PM:2423-2426。验收：【单元】。

## 2 播放意图与挂起

- **INT-1 意图优先**：内核 playing=false、paused 不改变意图。意图为播放时，界面显示“缓冲/重连”，不显示“已暂停”；显式用户暂停在调用内核之前先撤销意图，所以只有它会显示为“已暂停”。
  证据：PM:4447-4467、4520-4538。验收：【轨迹】。
- **INT-2 挂起令牌**：挂起原因有两种（后台、音频打断），可以同时存在。挂起时取消看门狗、退避和预算清零计时，返回令牌 =（会话，意图修订号）。恢复时要求：令牌与当前会话和意图修订号一致、意图仍为播放、该原因确实在挂起集合里；还有其他挂起时只移除这一项，不播放。
  证据：PM:483-548；PLC:9-13。验收：【单元】后台期间换房或用户暂停，回前台不得恢复旧会话。
- **INT-3 后台策略**：应用进入 hidden/paused/detached 时：纯音频先提交省电（AUD-3）；允许后台播放或正在画中画/小窗时继续播放；否则隐藏持续 1.5 秒后才挂起（合并旋转、进入画中画、替换 Surface 时的短暂 hidden）。回到 resumed：取消待执行的挂起；纯音频且没有睡眠定时时静默预热视频；用令牌恢复。
  证据：PLC:34、43-47、109-160；GPS:75-86。验收：【单元】假时钟；【真机】旋转、进出画中画不出现暂停。
- **INT-4 音频打断**：其他应用抢占音频焦点时按挂起令牌暂停，焦点归还时按令牌恢复；打断期间用户的任何操作都让令牌失效。
  证据：GPS:62-68；PM:494-500。验收：【单元】；【真机】来电后恢复。
- **INT-5 用户操作让进行中的异步工作作废**：暂停、继续、换源、换画质/线路、关闭、手动重试都递增意图修订号。进行中的恢复、续期交接、退避在每个异步点核对，过期就放弃，不计入恢复次数（见 REC-4）。
  证据：PM:3836-3858、3977-4006、4054-4063。验收：【单元】。

## 3 源管线与租期

- **SRC-1 输入事务**：每个播放器实例有一个输入所有者。打开 = 代次加一 → 取消未完成的输入创建 → 带取消令牌创建输入 → 内核打开 → 成功后才替换，旧输入随后关闭；过期的创建结果到达时直接关闭。
  证据：PST:188-303。验收：【单元】沿用 `test/playback_source_transport_test.dart` 的事务样本。
- **SRC-2 管线选择**（互斥，按顺序判断）：
  1. 租期会断开连接的 FLV（`cutsConnection=true`）→ FLV 拼接续流；
  2. ~~旧式 codec 12 HEVC 的 FLV → 标签转写~~：不做。所有平台的 libmpv 都是 FFmpeg ≥ 8（Android/Linux 为 9.0.2，Windows 为 FFmpeg master Lavc63.13，见 DIAGNOSIS），能直接识别 codec 12（2026-09-28 结清）；
  3. 带中继配方的 HLS（`StreamLine.hlsRelay`：按路径的 Cookie、分片还原）→ HLS 中继（ADR 0033）；
  4. 其它 → 直连。

  证据：PST:129-183；诊断 02 §1.4。验收：【单元】表驱动。
- **SRC-3 本地输入不走代理**：内核打开本地回环地址时绕过 HTTP 代理；上游请求由中继按当前代理策略发出。
  证据：MKA:572-579；PST:101-112。验收：【单元】；【真机】开启系统代理时斗鱼原画可播。
- **SRC-4 回环服务**：只绑定 127.0.0.1；每个会话一个随机、不可猜的路径，会话结束即失效；上游保留 TLS 证书和主机名校验（FFmpeg 的 HLS 子请求不继承 `ca_file`）；读取上游设空闲超时 [待确认：初始 15 s]。播放和录制共用同一套中继。
  证据：`lib/recorder/services/ffmpeg_hls_input_relay.dart:41-49、82、194、264`；诊断 02 ③6。验收：【单元】。
- **SRC-5 FLV 拼接续流**：
  - 到 `refreshAt` 时（斗鱼：签发后 300 s 断开，提前 45 s）解析同房间、同画质、同线路的新地址并连接，旧连接继续转发；
  - 在新连接里找旧连接还没送出的第一个关键帧；旧流转发到该时间戳后切过去。等旧流追上最多 10 s；在新连接里找关键帧最多 15 s；
  - 新连接第一个视频时间戳与已送出位置相差超过 60 s，视为另一条时间线，平移时间戳接上；
  - 切换后不再转发 script tag；视频或音频的编解码配置变了就补发；
  - 新连接开始找关键帧后，旧流转发到它的下一个关键帧前先扣住（最多 10 s），等新连接到达该关键帧再切换。两条连接都在直播边缘时，旧连接往往先送出这个共同的关键帧，不扣住就会一路推迟到断开（v4 真实套接字测试复现）；
  - 新地址就绪前旧流已结束，最多跳过一个 GOP；新连接失败则保留旧连接，每 10 s 重试，旧连接真正断开后交给恢复链；
  - 由续流负责续期的会话，播放层不再预取凭据或主动交接。

  证据：FSR:83-320、344-352；`lib/core/site/douyu/douyu_site.dart:30-34`；PM:4622；提交 31982153。验收：【单元】样本 FLV（`test/flv_splice_relay_test.dart`）；【探针】斗鱼真实流两次换源无缺口；【真机】斗鱼原画连续 30 分钟无卡顿。
- **SRC-6 按租期类型续期**（租期来自数据，不再从 URL 里的 `expire` 猜）：

  | `cutsConnection` | 行为 |
  |---|---|
  | true | 拼接续流（SRC-5），录制可以复用同一路输出 |
  | false | 到 `refreshAt` 只预取新凭据，不碰当前连接；连接真正断开（EOF 或错误）时，第一次签名刷新优先使用未过期的预取结果 |
  | 未知 | 首帧栅栏交接：到 `refreshAt`（或经验值，见 SRC-7）时在后台打开静音候选，候选出首帧后提交并释放旧的；候选失败则保留当前播放，10 s 后再试 |

  其它规则：`refreshAt` 已过时最少延迟 1 s；预取失败 10 s 后重试；预取是网络工作，不占用播放串行通道（慢网络不能阻塞换房和关闭）。
  证据：PM:4616-4673、4091-4291；提交 8a6fdce1、d6d4123c；PERT:2322、2364。验收：【单元】；【真机】虎牙 30 分钟无无谓重开。
- **SRC-7 短连接经验值**：Windows 上虎牙网页/HLS 回退源观察到约 100 s 断开，40 s 起开始交接，按“未知”类处理。[待确认：v4 首批 5 个平台是否还会产出这类源；没有就删除]
  证据：PM:218-226、4567-4576。验收：【真机】。
- **SRC-8 被动签名刷新总是开新连接**：即使签名服务返回同一 URL 也要重开，因为旧连接已经死了。
  证据：PM:4254-4260；PERT:2867。验收：【单元】。
- **SRC-9 自有源配方**（Bigo、FC2、Niconico 等）：播放层不接收占位 URL、原始 Cookie、签名 WebSocket；获取元数据和座位在同一个输入事务里完成。首批 5 个平台不用，但保留能力。
  证据：PST:183-186；`lib/player/core/playback_source.dart:31-41`。验收：【单元】。
- **SRC-10 HLS 查询策略**：不做。唯一的产出者 TTing 已在 1495f56b 下线，v4 没有平台需要；以后需要时给配方加字段（ADR 0033）。

## 4 mpv 内核事件契约

会话层只按下列真实顺序理解内核事件。测试替身不得自造顺序，只能回放录制的轨迹。

- **EVT-1 流结束**：先 `playing=false`，再 `completed=true`。在 completed 之前看到的 playing=false 不是用户暂停，走意外暂停宽限（MON 表），completed 到达后按意外 completed 处理。
  证据：提交 42cbded2；MVT:89-93；PERT:3362。
- **EVT-2 loading 之后会报 paused**：意图为播放时，这个 paused 是网络状态：正在缓冲就保持“缓冲”并布置缓冲看门狗，否则走意外暂停宽限。
  证据：PM:4520-4538；PERT:1212。
- **EVT-3 断供时可能一直报 playing=true**：以 buffering 为准，playing=true 不能取消缓冲看门狗。
  证据：PM:4418-4426；提交 3377ce30、6a8c007d；PERT:1434。
- **EVT-4 buffering=true 常先于 playing=false**：playing=false 到达后如果仍在缓冲，要重新布置缓冲看门狗。
  证据：PM:4458-4467。
- **EVT-5 open 返回前就可能报错**：打开期间的诊断先暂存，打开结束后按同一代次处理；对应组件（音频或视频）已经出帧的就丢弃。
  证据：MKA:829-833、876-890；PERT:2045。
- **EVT-6 去重只在同一代次内**：同一代次内相同错误文本 2 s 内只报一次；换线路后同样的文本必须再报。
  证据：MKA:757-765、911-923；PERT:3232。
- **EVT-7 可恢复诊断与致命错误混在同一日志流**：非立即终态的诊断先观察 1.2 s，期间出帧或恢复播放就撤销。只有前缀为 file、vd、ad、ffmpeg/video、ffmpeg/audio、cplayer、stream 的 error 级日志，或前缀为 ffmpeg 且以 `tcp:` 开头的日志，才进入分类。
  证据：MKA:792-866。
- **EVT-8 open 成功不代表有画面**：0×0 输出不算首帧。
  证据：PM:4336-4362；PERT:1514。
- **EVT-9 Android 打开后不重发 `vid=auto`**：这个异步命令可能在出画后仍不返回。
  证据：MKA:587-596。
- **EVT-10 换源前复位**：新代次开始时清空宽高、状态和暂存错误，否则上一 URL 的尺寸和迟到错误会回放到新代次。
  证据：PM:1460-1466。
- **EVT-11 帧进度**：Windows 每 500 ms 最多通知一次；看门狗用单调时钟的截止时间，收到通知只推后截止时间，不重建计时器。
  证据：`third_party/media_kit_video/windows/video_output.cc:216`；PM:2507-2512。
- **EVT-12 错误分类**：生命周期、视频输出、解码器初始化、传输、打开失败属于立即终态类；运行期解码、运行期源、其它原生诊断属于可恢复类（先观察，见 EVT-7）。
  证据：`lib/player/core/player_error_classifier.dart:30-170`。

- **EVT-13 打开时先发一组复位事件**：`open` 之后依次到达 playing=false、completed=false、buffering=false，随后在任何数据到达之前就报 playing=true、buffering=true。所以 open 之后的 playing=true 只表示“正在尝试播放”（与 EVT-8 一致）。
  证据：`fixtures/player/*/trace.jsonl` 开头几行。
- **EVT-14 流结束的完整顺序**：buffering=true → playing=false → completed=true → buffering=false，同一毫秒内还会把轨道列表复位（EVT-1、EVT-4 的实测版本）。
  证据：`fixtures/player/eof`。
- **EVT-15 断供超过 `network-timeout` 表现为流结束**：连接保持打开但不再发数据时，buffering=true 之后约 `network-timeout` 秒报 playing=false、completed=true，**没有 error**（录制时 media_kit 默认 5 s，旧应用设为 15 s）。会话层不能靠 error 区分断供和正常结束，要结合结束前的缓冲时长判断。
  证据：`fixtures/player/stall`（最后一个数据包在 3.0 s，completed 在 8.1 s）。
- **EVT-16 中途断开与正常结束无法区分**：服务端在传输中途断开连接（不发 chunked 结束块），内核同样只报 completed=true，没有 error。
  证据：`fixtures/player/reset`。
- **EVT-17 打开失败只报 error，不复位状态**：403 或非媒体数据时，内核只发一条 error（`Failed to open …`、`Failed to recognize file format.`），playing 和 buffering 保持在 open 时的 true。会话层收到这类 error 后必须自己把状态置为失败，不能等 playing=false。同一个播放器随后再 open 能正常起播。
  证据：`fixtures/player/http403`、`garbage`、`reopen_after_403`。
- **EVT-18 暂停和停止**：pause() 与 play() 只切换 playing，不产生缓冲事件；stop() 报 playing=false、duration=0、buffering=false，不报 completed。
  证据：`fixtures/player/pause_resume`、`stop_while_buffering`。
- **EVT-19 无时长元数据的直播流**：duration 报告的是持续增长的已缓冲长度，不是 0，不能用 duration 判断是不是直播。
  证据：`fixtures/player/eof`（媒体用 `-flvflags no_duration_filesize` 生成）。
**验收**：【轨迹】在 Windows 和 K90 上用真实 libmpv 录下这些场景的事件轨迹：正常起播、流结束（斗鱼 300 s）、CDN 断开、断供缓冲、打开 403/404、硬解失败回退软解、纯音频切换、换线路、关闭。轨迹存入样本目录，契约测试逐条断言 EVT-1～EVT-19；每次升级 libmpv 或 media_kit 分支都重录并比对差异。

进度：Linux 无视频输出（`vo=null`）的 8 个场景已录入 `fixtures/player/`（`tool/probes/player_event_trace_probe_test.dart`）。无视频输出时宽高一直为 null，首帧和画面相关的轨迹要在 Windows 和 K90 上用真实视频输出录制。

## 6 恢复策略（单直播间和多画面共用）

- **REC-1 恢复链顺序**（每一步开始前都重新确认仍需恢复；失败就进入下一步）：
  1. **签名刷新**（网络类或源类故障，且站点提供刷新能力）：每轮最多 2 次，第 1 次同线路，第 2 次换下一条线路；第 1 次优先使用未过期的预取结果；有首帧栅栏的平台用候选交接替换。
  2. **换线路**（网络类或源类，同一画质下有多条线路）：把当前线路记为失败，换到下一条可用线路。画面停滞时，有备用线路就先换线路（比在同一签名 URL 上重建更快更安全）。
  3. **同引擎重建**（停滞类：缓冲停滞、意外 completed、两种意外暂停、画面停滞）：每轮最多 1 次；有首帧栅栏的平台以候选方式重建，候选一直 0×0 就丢弃候选、保留旧画面。
  4. **软解重试**（视频解码类，音频类除外）：同一 URL 只一次；只标记“下次打开用软解”，不在出错的解码器仍占用时修改硬解设置。
  5. **退避**（网络类或源类，且是连续直播）：750 ms、2 s 两轮；每轮开始时重置签名刷新、重建次数和线路失败名单，先签名刷新，再重开当前源。
  6. **终态错误**：撤销播放意图，停止全部监测，显示错误和“重试”。

  意外 completed 和缓冲停滞既算网络类，也算停滞类（EVT-15、EVT-16：断供和断连只表现为这两种），所以先签名刷新、换线路，再重建，最后退避。解析时站点报的非暂时性错误（下播、需要登录、地区限制）直接进入终态。

  Android 上的硬解兜底由 mpv 自身完成（`hwdec-software-fallback=1`）；mediacodec 兼容模式是用户设置，不是自动步骤 [待确认：是否加成自动步骤]。
  证据：PM:3826-4008、4010-4088、4091-4291、4311-4387；MKA:105、505-529。验收：【单元】把 PERT 约 100 个场景转为行为样本；【轨迹】。
- **REC-2 次数按时间窗口计算**：
  - 一轮恢复从第一次故障开始，到“连续健康播放 30 s”结束（playing、不在缓冲、无错误、无挂起；有帧进度的平台还要求帧在前进）。一轮结束时清空各步计数和线路失败名单。
  - 每个会话（多画面每一格）在任意 3 分钟内最多开始 2 轮；超出后，单直播间报终态错误，多画面该格停止自动恢复并显示错误。这样每 5 分钟断一次的租期源可以一直恢复，立即失败的源不会被反复重试。[待确认：单直播间是否放宽到 3 轮，用真机轨迹校准]
  - 不设“一辈子最多 N 次”。

  证据：PM:304、2553-2574；MVC:338-345、1234-1240；提交 bf570796；MVT:1540、1560。验收：【单元】假时钟模拟每 300 s 断开 1 小时，持续恢复；立即失败的源在第 3 轮前停止。
- **REC-3 保留手动选择**：恢复全程保持当前画质（按画质标识匹配，不按下标）；签名刷新和重建保持当前线路；只有“换线路”这一步可以离开当前线路，而且只在同一画质内换；恢复不会自动降画质。多画面重新解析后先还原画质，再还原线路。
  证据：MVC:1241-1284；提交 4fe4f7b7；MVT:1472、1507；PM:4102-4104、4130-4137。验收：【单元】。
- **REC-4 用户操作让进行中的恢复作废**：任何用户命令都会让进行中的恢复在下一个检查点放弃；被放弃的这一次不计入次数（退还），并按内核当前状态重新布置监测。
  证据：PM:3977-4006；MVT:1507。验收：【单元】。
- **REC-5 恢复期间的界面**：显示“缓冲/重连中”，不显示“已暂停”，也不显示错误；只有终态才显示错误。
  证据：PM:3859-3860、4027-4031。验收：【单元】。
- **REC-6 手动重试**：清空各步计数和 3 分钟窗口（用户明确要求重试），按当前画质和线路重新解析，再打开当前源（旧签名可能已过期）。
  证据：PM:3743-3767。验收：【单元】。
- **REC-7 换房**：清空全部计数、线路失败名单和窗口历史。
  证据：PM:1386-1393。验收：【单元】。
