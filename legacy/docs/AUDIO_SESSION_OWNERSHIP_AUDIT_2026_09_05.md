# 音频中断、通知控制与播放器绑定所有权

## 范围与实施前证据

本地冻结 `9549000f3040fcb9a2092bd025007fbeccfb8415`；上游只读参考仍为
`c6c9bd70aedc503c003110dae10a83ad0bb891d8`，不合并、不操作手机。

从历史 PiP 观察继续追踪实际暂停调用，发现独立音频处理器边界：

- 本分支 `b6f243e16` 引入串行音频事件队列，但排队回调只在执行时使用 `_currentPlayer`，
  没有保存接收事件时的播放器/源所有权。旧耳机事件或中断回调可能作用到新房间。
- 同提交保存的中断 token 在 await 返回后直接写入全局字段；新播放器已经绑定时，旧 token
  仍覆盖它，使后续真实中断被错误地当成已处理。分类 `fork-regression`。
- 上游原有 `setPlayer` 在取消旧订阅后才更新播放器；并发绑定会安装多条状态订阅。
  `releasePlayer` 保留 `_currentPlayer` 和订阅，旧停止收尾仍取消焦点/发布 idle。
  当前上游同样保留相关模式，分类 `upstream-existing`。
- 无管理器回调的回退路径收到中断结束后直接 play，即使未收到对应开始事件。
- 上游原始 duck 处理固定写入 0.2/1.0，不考虑房间音量或静音；已修改为对当前保存音量
  做衰减，并在结束时恢复最新的用户选择，旧房间结束事件不操作新房间音量。

这些是新的源码疑点。历史日志仍缺少 Dart 触发原因和 source/session 代次，尚未证明
本批缺陷就是那次 PiP 黑屏；不以“都涉及暂停”替代同一根因的证明。

## 方案与不变量

1. 播放器绑定在异步取消前声明新所有者；旧订阅回调和迟到绑定完成只处理自己的实例。
2. 音频事件在到达时绑定当前播放器与源有效性；排队执行前、等待暂停完成后分别复核。
3. 关闭立即解绑通知控制/状态，旧 stop 完成后不撤销新房间焦点或覆盖通知状态。
4. 焦点激活/放弃串行且带有效性检查；通知 play 等待焦点期间换房后失效。
5. 管理器继续拥有用户播放意图和生命周期暂停 token，不新增第二套播放器重连。
6. 同一 native adapter 换房也更换源所有权，不能仅比较 player 对象是否相同。
7. 音频事件队列跟随绑定换代；旧 pause 的未完成 Future 不阻塞新绑定事件。全局系统
   焦点队列继续串行，避免旧 abandon 在新 activate 之后落地；两种队列职责分开。

## 参考

- [audio_session 官方说明](https://pub.dev/packages/audio_session)：分别处理焦点中断、duck、
  becoming-noisy；共享焦点与每个播放插件的行为需要协调，事件处理不是无条件恢复。
- [Flutter Android Surface 合同](https://docs.flutter.dev/release/breaking-changes/android-surface-plugins)：
  Surface 清理/恢复是独立渲染层；本次不通过改动 Surface 或重新打开网络流处理音频事件所有权。
