## 做法

> T02.U（2026-09-29）按用户批准的升级改了推荐、搜索、人数、标题和封面、画质（新增“原画”）、翻页和列表的容错，见文末“升级落地（T02.U）”。本节以下是 T02b.5 时的做法。

- **接口和输出沿用 v3**：`LiveSite`、`LiveRoom` 等模型和 3.x 的 JSON 不变。v3 实现过的可选能力全部保留：原生目录（`LiveSiteDirectoryPager`）、目录范围说明（`LiveDirectoryNotice`，文字键 `inke_directory_scope`）、刷新（`LiveSiteRoomRefresher`）、录制详情（`LiveSiteRecordRoomResolver`）、恢复时重新取流（`LivePlayRecoveryResolver`）、可取消的搜索（`LiveCancellableSearch`）、按关键词决定是否翻页（`LiveSearchPaginationPolicy`）。另加 `LivePlayUrlResolver`（线路带请求头和租期）和 `LiveSiteLinks`。
- **列表和搜索照 v3**，请求数也相同：
  - 分类和频道：`web/Live_channel_pc`，一个“映客”分类下 6 个频道（`areaType` 为 `showcase`，`typeName` 为“映客官网精选”）；
  - 推荐：`web/Live_top_pc` 的 8 个推荐位；
  - 都只有一页，第 2 页起为空且不发请求；调用方按页取时照 v3 切片，每个切片请求一次整页；
  - 昵称搜索：`Live_top_pc` 加全部频道，按昵称（不区分大小写）过滤，按 uid 去重再分页，两个请求；
  - 输入是 uid 或映客房间链接时直接查这个房间，只有第 1 页。
- **请求头照 v3**：`Referer: https://www.inke.cn/`、`Origin`、UA `Mozilla/5.0`，不跟随跳转。App 接口用同样的请求头也能正常回答（2026-09-28 实测）。
- **房间照 v3**：`web/live_share_pc?uid=` 一个请求，进房、关注刷新、录制都是它。
  - 在播：标题 `live_name`（缺时用昵称），头像和封面都是主播头像，没有人数；
  - 错误码 1099999920（“当前用户无直播”，不存在的 uid 也是它）是未开播，只有 uid 和不带直播编号的链接；
  - 回答的主播、状态、直播编号对不上就报 `ApiChanged`，不当成未开播。
- **房间身份与 v3 一致**：v3 的详情返回请求时的 uid（`roomId(input)` 只做了去空白和校验，并要求 `live_uid`、`media_info.inke_id` 都等于它），卡片的房间号是行里的 `uid`。新代码相同，样本对照里所有 `roomId` 都与 `expected.json` 一致。每场直播的编号 `liveid` 不是身份，放进 `InkeRoomData`，只用于取流兜底和链接。
- **画质照 v3**：一个画质 `FLV`（id `flv`），一条网宿线路（`live-pull-ws.ikstatic.cn/live/<直播编号>_t.flv`，H.264 转码流）。地址校验照 v3（主机、端口、路径必须是这场直播的 `_t.flv`，签名原样保留），即构的 HEVC 线路不提供。
- **取流改用 App 接口，v3 的做法作兜底**（下一节）。线路带 v3 `PlaybackHeaderResolver` 里映客的请求头，租期取网宿签名的 `wsABStime`。
- **没有 Cookie、登录和弹幕**：v3 的映客全部匿名，弹幕是 `EmptyDanmaku`，所以没有弹幕参数类，也不注入 `CookieVault`。

## 取流：修 bug，用户看到的不变

v3 在进房时就要拿到拉流地址：网页房间接口匿名不给地址，它只好到三个展示位（`Live_top_pc`、`Live_hot_pc`、`Live_channel_pc`）里找同一场直播的行，找不到就让整个进房失败，提示“当前官网精选未提供已验证的公开播放地址”。展示位一共只有四五十个直播，关注的主播多半打不开（REG-INKE-001）。

本模块用 2026-09-28 同一时刻录下的一组样本核实过：

- `S05-unlisted-share` 的主播在播，但不在任何展示位里。v3 发了 4 个请求后报错，房间都进不去（冻结输出 `S05-unlisted-share/expected.json`）。
- App 接口 `service.inke.cn/api/live/now_publish?id=<uid>` 对任何在播主播都给出签名的网宿地址（`S05-unlisted-publish`）；用 v3 的请求头直接拉流，是 FLV，视频编码 7（H.264），签名约 2 小时后到期。
- 对同一个主播，展示位里的地址和 App 给的地址是**同一路流**：主机、路径、`stream_id` 都相同，只有签名和到期时间不同（`S01-top` 与 `S04-publish-live`，都是 `771067357` 的 `1790521153165881_t.flv`）。

所以修好后用户看到的画质名称（FLV）、线路和播放方式都和 v3 一样，只是原来打不开的直播间能打开了。按“修 bug、用户所见不变”处理：

1. 进房、录制只读房间接口（1 个请求），不再因为拿不到地址而失败；
2. 取流时先问 `now_publish`（1 个请求，每次重新签名）：
   - App 说没有在播（`live` 为空或 `status` 不是 1），就报 `StreamUnavailable`，不再去翻展示位；
   - 给出网宿地址就用它；
3. App 失败（网络、5xx、限流、格式变化）或只给了即构地址时，走 v3 的查找：按 v3 的顺序翻三个展示位，找 App 说的这场直播（App 没回答时用进房时记下的直播编号），找到的地址与 v3 逐字节相同；都找不到时报 App 的错误（临时错误仍可重试），没有直播编号可找时直接报 App 的错误。

列表内容不变：推荐仍是官网 8 个推荐位，搜索仍只在官网展示位里找。归档 v4 把推荐换成 App 热门、搜索加上 App 热门，会改变列表内容，列为升级候选。

## 样本与 v3 的冻结输出

归档没有映客的 `expected.json`：归档的旧版对照工具只做了前五个平台，v3 应用现在也构建不了。本模块用 `fixtures/inke/legacy_expected.dart` 生成：

- 把 v3 的 `InkeApi`、`InkeSite` 原样搬进一个纯 Dart 脚本。v3 本来就把传输做成可注入的函数（`InkeRequest`），所以只换了它：按主机、路径和查询读样本；状态码不是 200 时正文为空（同 v3）；没有样本的请求抛 StateError。
- `i18n` 换成用到的两个键的中文（`site_inke`、`inke_media_unavailable`），弹幕的 getter 和只在网络路径上用到的 `readBody` 没有搬。
- v3 的 `LiveRoom`、`LiveArea`、`LivePlayQuality` 等只搬用到的部分。
- 输出格式同旧版工具（`roomProjection`、`errorProjection`、`{generator, value}`）；每个调用还记下了它发出的请求。
- 重新生成：在仓库根目录运行 `dart run fixtures/inke/legacy_expected.dart`。

8 个样本有 `expected.json`：

- `S01-top`：推荐页（第 1、2 页）、5 种切片；6 个关键词的昵称搜索和 3 页分页（同时读 `S01-channels`）。
- `S01-channels`、`S05-unlisted-channels`：分类、每个频道的页、第一个频道的 5 种切片。
- `S05-unlisted-top`：推荐页。
- `S05-unlisted-hot`：v3 的展示位查找（`_showcaseMedia`）对 S05 三个展示位里每一行（44 场直播）找到的地址和所用请求数。
- `S03-share-live`（同时读 `S01-top`）、`S03-share-offline`、`S05-unlisted-share`（同时读 S05 的三个展示位）：进房、刷新、录制、按 uid 和链接搜索、开播状态、打开官网、画质、地址、恢复。

v3 不请求的样本没有 `expected.json`：`S02-simpleall`（App 热门，留作升级候选的依据）、`S04-*` 和 `S05-unlisted-publish`（App 当前直播，新代码的取流）。

## 与 v3 的有意差异

| # | 差异 | 原因 |
|---|---|---|
| 1 | 取流先问 App 的 `now_publish`，展示位查找作兜底；进房、录制不再因为没有地址而失败 | 问题 1、2（REG-INKE-001）。同一路流，画质名称和播放方式不变 |
| 2 | 进房、录制 1 个请求（v3 是 2～4 个），取流另发 1 个（兜底时再加 1～3 个）；恢复 1 个（v3 重读详情，2～4 个） | 随 1 一起改；关注刷新、列表、搜索的请求数与 v3 相同 |
| 3 | 未开播取流报 `StreamUnavailable`；App 说没有在播时也是 | 问题 3 |
| 4 | `scheme://` 形式才算链接，带冒号的关键词正常搜索 | 问题 4 |
| 5 | 错误类型化：401/403 `RiskControl`，404 `NotFound`，429 `RateLimited`，5xx 和其他状态码 `NetworkFailure`，未知错误码和格式不对 `ApiChanged`；调用方的参数错误（页号、每页条数、超长关键词、别的平台的分区）是 `ArgumentError`，同 v3 不发请求 | 问题 5、6、9 |
| 6 | 线路带媒体请求头（值与 v3 的 `PlaybackHeaderResolver` 相同）、格式 FLV、编码 H.264、线路编号 `ws` 和租期 | 问题 7、9 |
| 7 | 另认 App 分享链接 `mlive<n>.inke.cn/app/…?uid=` | 问题 8。只加了识别，不发请求，不影响已有链接 |
| 8 | 图片地址用通用的 `normalizeImageUrl` | 所有平台共用；协议相对地址也能处理。样本里的地址结果与 v3 相同 |
| 9 | 超过 1 MiB 的回答在下载完后判定，v3 是边读边判；非法 UTF-8 不再单独报错 | 传输统一由 `live_net` 负责（同猫耳）；超限结果相同（`ApiChanged`），总时长仍是 20 秒 |

## 保持 v3 行为、没有采用归档 v4 或上游做法的地方

> T02.U 已改：推荐（App 热门）、昵称搜索（加 App 热门）、人数、标题和封面（App 的）、即构 HEVC 线路（“原画”）、列表的行校验（坏行只跳过），见文末。其余各条不变。

- **推荐仍是官网 8 个推荐位**。归档 v4 改成 App 热门 `simpleall`（约 20 个，每次请求内容都会变），列表内容会变。
- **昵称搜索仍只找官网展示位**。归档 v4 另加 App 热门。
- **没有人数**。归档 v4 把 `numbers.real` 作在线、`online_users` 作热度（REG-INKE-003），但 3.x 的人数设置页写明映客“缺失值保持未知”，列表和详情都不显示人数；显示出来会改变界面。
- **标题、封面照 v3 取自房间接口**：封面仍是主播头像。归档 v4 用 App 的直播封面和标题，这会改变卡片和详情的外观，关注刷新还要多一个请求。
- **不填简介**。归档 v4 用 `media_info.description`，但两个样本里它都是映客的默认占位“难道在火星？”，显示出来没有意义。
- **画质名称仍是 FLV**（id `flv`）。归档 v4 叫“原画”（id `origin`）。
- **请求头照 v3**：UA 仍是 `Mozilla/5.0`。归档 v4 用完整的 Chrome UA；App 接口用 v3 的请求头也能正常回答。
- **分类仍是一个“映客”组**，`typeName` 仍是“映客官网精选”。归档 v4 是 id `channel` 的“频道”，上游把 `typeName` 改成了英文。
- **打开官网**：房间链接没有直播编号时仍去官网首页。归档 v4 改为不带编号的房间页，这个页面是否可用没有核实。
- **未开播主播的 uid 搜索卡片仍叫“UID <uid>”**：回答里没有资料。
- **列表的行照 v3 严格校验**：一行缺 uid、直播编号或昵称，整页报错。归档 v4 跳过坏行。
- **展示位查找没有丢掉**：归档 v4 只用 App 接口；这里保留 v3 的查找作兜底，App 出问题时 v3 能播的房间仍能播。
- **没有即构（HEVC）线路**（REG-INKE-002）。归档 v4 同样没有。

### 按统一原则补的

| 原则 | 做了什么 |
|---|---|
| 开播时间 | App 热门卡片和带 App 回答的房间（进房、关注刷新、录制、uid 搜索）填 `start_time`（Unix 秒，按 UTC 换算）。0、2000 年以前、2100 年以后、不是整数的不填（`InkeApi.startTime`）。官网推荐位、频道的卡片和网页房间接口都没有开播时间，不填；未开播不填 |
| 受限类型 | App 的回答给了网宿或即构地址就是 `none`（平台把流给任何人）；在播但一个地址都没有时留空（看不出来）；官网展示位的卡片、网页房间接口、App 没回答时留空；未开播不填。映客的公开回答里没有付费、私密、密码房的字段：S02 的 15 个和 2026-09-29 两次探测的 39 个直播，`live_type`、`sub_live_type` 都是空串，都带两个地址。所以没有填其他受限类型，取流的报错不用改 |

### 与 v3 冻结输出的新差异

样本对照测试里写明，原因写条目编号；`expected.json` 没有改：

- 分类（S01-channels、S05-unlisted-channels）：第一格是“官网推荐”（14-1），其余 6 个频道逐项一致；每个频道的房间一致。
- 推荐（S01-top、S05-unlisted-top）：v3 的推荐页现在是“官网推荐”分区，逐项一致；推荐改为 App 热门（14-1）。v3 的推荐切片与“官网推荐”分区的切片一致。
- 昵称搜索（S01 + S02）：v3 的结果仍在前面、顺序不变；同时在 App 热门里的房间是 App 的卡片（14-2、14-3、14-4）；多一个 `simpleall` 请求（14-2）。只用官网两份列表时与 v3 逐项一致。
- 进房、刷新、录制（S03 + S04、S05 + S05-publish）：`cover` 和 4 个人数键换成 App 的（14-3、14-4），新键只有 `startedAt`、`restriction`；标题（样本里 App 与网页相同）和链接不变。只读网页接口时与 v3 逐项一致。
- uid 搜索的未开播卡片（S03-share-offline）：`title`、`nick` 从“UID 1”变为空（占位信息）。
- 展示位卡片的 `supportsRealOnlineCount` 从假变真（14-3，能力表），卡片本身仍没有人数。
- 坏行、坏频道跳过（容错），只有合成用例。

### 受阻

没有受阻的条目。

没有样本、只靠实测的部分：

- 付费、私密、密码房：没有找到（见“受限类型”）。
- 即构线路的租期规则（以开播时间为准，约 24 小时，与何时签发无关）来自 2026-09-29 对 54 个直播的统计；超过 24 小时的直播到期后能否续上没有核实，由 T04 在续期失败时按恢复处理。

### 测试

本平台 99 个用例（T02b.5 是 67 个；新增 32 个，另改写了分类、推荐位、搜索、进房、取流的用例），`live_core` 共 3070 个，全部通过：

- `inke_api_test.dart`（60 个）：
  - 分类：第一格“官网推荐”，其余与 v3 逐项一致；坏频道只跳过这一个，整个回答不对仍失败；
  - 官网推荐位：与 v3 逐项一致，没有人数但平台支持在线人数，坏行跳过；
  - App 热门（S02）：15 张卡片的标题、占位标题、封面、开播时间、在线和热度、`none`、链接，“优先显示在线人数”开关两种显示，JSON 往返；坏行、非直播、重复跳过；没有地址、人数、开播时间时的取值；开播时间的范围；
  - 昵称搜索：只用官网列表时与 v3 一致；加上 App 热门后 v3 的结果在前、App 的卡片替换、只在 App 热门里的房间；
  - 详情：S03、S05 与 v3 一致；S06 的占位标题；App 的回答并进房间（S03 + S04、S05、S06）：与 v3 的差异只有封面和人数，新键只有两个；App 标题优先、新的直播编号改链接、占位标题、没有地址时不标受限；下播后的合并清掉开播时间；
  - 取流：`now_publish` 的新字段；即构线路的校验、编码、线路和租期（开播后 24 小时）；原有的网宿线路、兜底查找、租期、链接用例。
- `inke_site_test.dart`（39 个）：
  - 请求头（进房时的 App 请求、播放复用它）；
