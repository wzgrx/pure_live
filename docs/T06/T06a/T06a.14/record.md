## 做法

- **建在 T06a.1 的 WebSocket 运行时上**（`DanmakuSocketConnection`），平台只写 `target`、`onOpen`、`onData`、`heartbeatFrame`，另覆盖 `onJoinTimeout`。换地址、退避、最多 8 次、无消息超时、停止后不再有事件，都由框架和 `LiveSocket` 负责。框架没有改。
- **Socket.IO 只实现用到的那一小部分**：没有引入 Socket.IO 客户端库（也不加依赖）。握手地址带 Engine.IO 的查询参数，打开后发一个命名空间加入包（文本帧），之后每 25 s 发一个 Engine.IO ping `2`；收到的文本帧按 Engine.IO、Socket.IO 两层的前缀分类（见“协议”）。
- **加入要等服务端确认**：发出加入包后，收到 `connect_error`（`code` 为 0，这是服务端说“join success”的方式）或命名空间的 `40` 任一个就算加入，每个 socket 只报一次 `DanmakuReady`；8 s 内没有确认就换一个 socket（同归档 v4）。
- **上报聊天和在线人数**：
  - 聊天是 `content.t` 为 200 的消息；
  - 在线人数来自房间状态（`content.t` 为 637）里的 `watchNumber`：它是官网直播页显示的“收听”人数，直播中约每 5 s 推一次（归档 v4 的规格说“没有在线人数消息”，是因为它的录制把这类消息的内容丢了，见差异 3）；
  - 礼物（220）、礼物条（10004）、进场、离开、点赞不上报，和 T06a.2～T06a.12 的范围一致。
  - 付费留言：平台有“付费提问”（637 里的 `payNumber`、`unansweredNumber`；页面收到 240 等带 `uc.question` 的消息时更新直播间的提问卡片，不进弹幕列表），两次录制里都是 0，也没有出现过提问消息，没有样本，不上报（见“受阻”和候选 3）。
- **服务端的拒绝和踢出都能认出来**：
  - 加入被拒（`connect_error` 的 `code` 不是 0，或命名空间的 Socket.IO 错误包 `44`）：带 `protocolError` 提示重连；连续被拒 3 次后，第 4 次以 `connectionFailed` 结束；成功加入一次就清零；
  - 服务端离开命名空间（`41`）或关闭传输（Engine.IO `1`，比如 85 s 没收到 ping）：马上重连，不单独提示（`LiveSocket` 自己会报一次“断开，正在重连”）；
  - 放弃了的 socket（被拒、被踢、加入超时）在重连前还可能送来帧，这些帧不再算数。

## 协议

**连接**：`wss://wim.hongrenshuo.com.cn/socket.io/?roomId=<roomIdStr>&appId=111&clientType=1&EIO=3&transport=websocket`。

- 官网脚本里写的是 `wss://wim.hongrenshuo.com.cn/live_chat_room_guest?roomId=…&appId=111&clientType=1`（`ROOM_CONFIG.ROOM_URI`），这是 socket.io-client 的“地址 + 命名空间”写法：路径是默认的 `/socket.io/`，命名空间在加入包里。`appId=666` 是同一脚本里日文版（pika）的配置。
- 握手请求头：`origin: https://live.kilakila.cn`、`user-agent: Mozilla/5.0`（`KilakilaApi.userAgent`，适配器所有请求都用它）。不需要 Cookie，不需要保留大小写，用默认的 `dart:io` 握手，不用 `connectExactWebSocket`。
- **订阅的直播由握手地址里的 `roomId` 决定**：加入包里的查询写成别的直播号、写成 `abc`、留空或者不写，收到的都是握手地址那一场的消息（实测）。

**帧**：全是文本帧，一帧一个包。

| 帧 | 含义 | 本实现 | 归档 v4 |
|---|---|---|---|
| `0{"sid":…,"pingInterval":25000,"pingTimeout":60000}` | Engine.IO 打开 | 不报 | 不报 |
| `40`、`41` | 默认命名空间的连接和断开（服务端每次都先发这两个） | 不报 | 不报 |
| 客户端发 `40/live_chat_room_guest?roomId=<id>&appId=111&clientType=1,` | 加入游客命名空间（socket.io-client 2 的写法：命名空间、查询、逗号） | 打开后立即发 | 同 |
| `42/live_chat_room_guest,["connect_error","{\"result_type\":0,\"code\":0,\"message\":\"join success\"}"]` | 加入的应答（事件名是 `connect_error`，`code` 0 是成功） | `code` 为 0：加入；否则：被拒，说明取 `message`，没有时写 `code <值>` | 加入 / 被拒 |
| `40/live_chat_room_guest`（或后面带逗号） | 命名空间连接成功 | 加入 | 加入 |
| `44/live_chat_room_guest,<错误>` | 命名空间的 Socket.IO 错误包 | 被拒，说明取错误的文字或 `message` | 不识别（差异 6） |
| `41/live_chat_room_guest`、`1` | 服务端离开命名空间、关闭传输 | 掉线，马上重连 | 不识别（差异 7） |
| 客户端发 `2`，服务端回 `3` | Engine.IO ping、pong | 每 25 s 发一次；`3` 不报（任何帧都会让框架的无消息计时清零） | 同 |
| `42/live_chat_room_guest,["text_message","<JSON>"]` | 消息，见下 | 见下 | 见下 |
| 其他命名空间、其他事件、二进制帧、带确认号的事件、坏 JSON | — | 不报 | 不报 |

### 在线人数

- 637 的 `watchNumber` 和列表、`getRoomInfo` 里同名的 `watchNumber`（累计收听，REG-KILAKILA-003）不是一回事：它会上下波动，量级也不同，是“现在的收听人数”。
- 它和主页卡片的 `onlineNumber`（T02.U 15-2 用作在线人数）变化一致，但数值不同，实测见下表；官网直播页开播时用直播信息的 `onlineNumber` 初始化“收听”，之后用 637 的 `watchNumber` 更新，所以直播间里显示的就是它。

| 直播 | 637 的 `watchNumber` | 主页 `onlineNumber` | `getRoomInfo` 的 `watchNumber`（累计） |
|---|---|---|---|
| S08 那一场（热门第 1 页累计最多，150 s） | 315、316、312、314、317 | 308（几分钟后） | 1233 |
| 热门第 1 页的另一场（200 s，每 10 s 对照一次） | 40 → 47 | 58 → 63 | 199 → 208 |

- 所以进房后本实现按 T02g.2 的约定报 `LiveAudienceUpdate(onlineViewers, watchNumber)`，与官网直播间一致。`audience.dart` 里克拉克拉仍是 `roomRealtime`（“只在房间里有：详情或实时消息”），能力没有变，只在注释里补上了这个来源。
- 进房时详情给的是主页卡片的数，几秒后弹幕给的是直播间的数，两者差几个到十几个人；显示哪个由 M13 决定（其他平台也是后到的实时值覆盖详情值）。

| 项目 | 本实现 | 归档 v4 | 官网直播页 | 依据 |

## 登记方式

应用（T07a.1）建平台表时：

```dart
DanmakuRegistry({
  SiteIds.kilakila: () => KilakilaDanmakuConnection(proxy: proxyPolicy),
  // …
});
```

| 参数 | 必需 | 说明 |
|---|---|---|
| `proxy` | 否（默认直连） | `live_net` 的 `ProxyPolicy`，每次握手按平台 id `kilakila` 取路由，和接口请求用同一份设置 |
| `connector` | 否 | 只给测试替换握手；默认 `dart:io` |
| `policy` | 否 | 只给测试改时序；默认 `KilakilaDanmakuConnection.defaultPolicy` |

不需要 `LiveHttp`、Cookie 或设置：游客聊天室全程匿名，v3 也没有克拉克拉的 Cookie。参数来自 `getRoomDetail`；没有当前直播的主播没有参数，按 T06a.1 不连接。

- 它对 S07、S08 写下每个收到的帧的结果（是否加入、是否被拒、事件），对 S09 写下每组每帧的结果。运行：在仓库根目录 `dart run fixtures/kilakila/danmaku/v4_expected.dart`，`generator` 字段写明来源。

## 与归档 v4 的差异

| # | 差异 | 原因 |
|---|---|---|
| 1 | 消息 id 不加 `kilakila:` 前缀 | 与 T06a.2～T06a.12 一致：去重闸门按房间内的 id 比较 |
| 2 | 不报礼物（220） | v3 所有平台都不显示礼物（`LiveMessageType.gift` 注明“not shown yet”），T06a.2～T06a.12 也都不报。以后要显示时再加（字段见上） |
| 3 | 房间状态 637 的 `watchNumber` 报为在线人数 | v4 的录制把这类消息的内容丢了（`meta.json`：`$.content[other t]` dropped），规格因此写“没有在线人数消息”。补录的 S08 保留了内容；它就是官网直播间显示的“收听”（见“在线人数”） |
| 4 | 聊天文字必须是文字；时间超出范围只让这一行没有时间 | v4 会把数字、`true` 当成聊天；时间超出范围时 `DateTime` 抛错，整帧丢失（统一原则“一行坏数据只跳过这一行”） |
| 5 | 用户 id 只收数字和文字，其他为空 | v4 会显示 `{x: 1}` 这样的文字（同 T06a.11 差异 6） |
| 6 | 命名空间的 Socket.IO 错误包 `44` 当作被拒 | Socket.IO 用它拒绝命名空间连接；v4 不识别，只能等 8 s 加入超时 |
| 7 | 服务端离开命名空间（`41/live_chat_room_guest`）或发 Engine.IO `1` 时马上重连 | v4 不识别：`41` 之后连接还开着，却再也收不到消息，要等 90 s 无消息（`3` 还会一直来，所以可能永远等不到）；`1` 之后服务端会断开 TCP，只差一点时间 |
| 8 | 被拒的计数按“连续”算，成功加入就清零；提示用 `protocolError`，结束用 `connectionFailed` | v4 按每次开始计，长时间的连接里偶尔的拒绝会累积到上限；结束原因用 T06a.1 的类型。v4 被拒后“重新规划”得到的还是同一个地址，所以和直接重连一样 |
| 9 | 握手的 UA 用适配器的 `Mozilla/5.0` | 与 T02b.6 的所有请求一致（v3 的 `playHeaders`）；实测 Python 客户端和 `dart:io` 都能连上、收到消息。v4 用 Chrome 140 的 UA，版本号会过时 |
| 10 | 心跳从 socket 打开起算，加入前也发 | socket.io-client 从 Engine.IO 打开包起算，服务端的 85 s 时限也从打开起算；这是框架的做法，不用单独处理 |
| 11 | 参数不对时以 `connectionFailed`（`No broadcast`）结束，并且要求是直播号（正整数） | v4 只检查是否为空，终态叫 `credentials`；这里没有凭据，按 T06a.1 的类型 |

没有改的地方：

- 地址、加入包、心跳帧、`origin`、打开即发加入包、两种加入确认、`room_id` 的检查、8 s 加入超时、90 s 无消息超时、退避和次数，与 v4 相同。
- 聊天的解读（文本去首尾空白、用户名原样、等级、`created_at` 为正才有时间、`content` 可以是字符串或对象）与 v4 相同；时间用本地时区的 `DateTime`（同一时刻），和其他平台一样。
- 载荷必须是 JSON 字符串（官网页面 `JSON.parse` 它），带确认号的事件、`t` 写成文字的消息不读，与 v4 相同。

## 与官网直播页的差异

- 页面的 socket.io-client 不限重连次数（1～5 s 随机退避）；这里按框架最多 8 次。
- 页面 60 s 没收到 `text_message` 就手动重连（`msgTimer`，而且写法有问题：第二条消息之后计时器不会再设）。这里按任何帧（包括 `3`）判断连接是否活着：直播结束后只剩 ping、pong，照页面的做法会每分钟重连一次并提示。
- 页面忽略 `connect_error` 的内容；这里按 v4 读它的 `code`。
- 页面显示进场、第一次点亮、礼物条和礼物动画；这里只报聊天和在线人数（候选见后）。
- 页面在 `msg_type` 11 时转到结束页；这里不报，由直播间刷新详情（M13）。
- 登录用户走 `/live_chat_room?access_token=…`（要先向 `uim.hongdoufm.com/wesync` 取令牌），这里只做游客。

### 礼物：每次送礼报一次

录到的规律（按送礼人、礼物、`c.lun` 这次送出的时间配对；有的礼物没有订单号 `c.no`）：

- 连击：每点一下来一条 220，`isDoubleHit` 为 true，`doubleCount` 是到这一下为止的累计（1、2、3……），`price` 是累计数乘单价；连击结束来一条 10004，数量是总数，`price` 是单价。1,933 条礼物条里 1,932 条跟在同一次连击的 220 之后（另一条是录制开始前的连击），其中 10 条的数量比看到的最后一下还多（点得快时有的 220 没发）。
- 一次送出的（`isDoubleHit` 为 false，699 条；另有 2 条推广账号的礼物没有这个字段）：只有 220，`price` 是这次的总价，之后没有礼物条。

所以（`KilakilaDanmakuProtocol.gift`）：

- 10004 报一次，数量取它的，价格是单价乘数量；
- 220 不是连击（`isDoubleHit` 不是 true）时报一次，价格照写；
- 连击的 220 不报，由结束时的 10004 报总数。用本实现解全部录制：礼物 2,634 条，正好是 1,933 + 699 + 2。

`LiveMessage`：类型 `gift`，文字照网页的礼物条写（`我送了<收礼人><数量>个<礼物>`，没有收礼人时“豆咖”），用户是 `n`、`u`，等级 `l`，消息 id、时间是回答的 `mid`、`created_at`；`data` 是 `KilakilaGift`（照 `BaiduLiveGift` 的写法）：`id`、`name`（去首尾空白，空的不报）、`count`（至少 1）、`price`（这次送出的全部，红豆，不小于 0；免费礼物是 0，`free` 为真）、`receiverName`（主播或连麦的嘉宾）、`icon`（`c.pic`，只收 https）。`c` 不是对象、`t` 写成文字、别的直播间的都不报。

### 顺手修的问题

`_decodeUriComponent`（637 的房间状态也用它）原来用 `Uri.decodeComponent`：它遇到 U+007F 以上的字符就抛 `ArgumentError`，而这里只接住了 `FormatException`，所以带明文中文的 URL 编码文字会让 `decode` 抛出。问题的文字正是明文中文和表情（录到的都没有百分号编码），所以改成照 JavaScript 的 `decodeURIComponent` 自己解：只解 `%XX`（连续的按 UTF-8），其他字符原样保留，坏的转义和坏的 UTF-8 仍返回 null。录到的 637 都是纯 ASCII，以前没出过事。
