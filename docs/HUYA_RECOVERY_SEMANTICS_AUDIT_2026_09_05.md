# 虎牙连续播放：恢复语义复查

## 修改前冻结与根因假设

- 本地 `e76702201d92bb0408eb51d2d77216d7ec117a09`，上游只读核对
  `c6c9bd70aedc503c003110dae10a83ad0bb891d8`；未合并上游、未操作手机。
- 上游虎牙取流最后的实质改动仍为 `c5944dd5` 的 WUP 原生凭据；随后是留言标识与格式化，
  不是新增的连续播放修复。Issue 808 关闭后仍有 Windows 两分钟卡住的反馈，关闭状态不等于全端验收。
- 已有原生 WUP、取消健康 FLV 定时重开及缓冲预算修复保留，不重新引入周期换源。

本次发现本分支 `74d5e184` 延迟重试的语义与即时恢复不一致：即时恢复区分“推断停帧”与
“明确 EOF/原生错误”，但退避/已派发阶段在收到任意一帧时取消所有错误的重试，并强制发布播放中。
最后几帧缓存、迟到的纹理通知只证明有一帧抵达，不证明已结束的连接恢复。随后可能停在最后一帧，
等下一轮看门狗才重连。来源分类为 `fork-regression`，不是凭据更新本身或必须登录。

## 直接修复与边界

1. 先使用生产 PlayerManager 的受控测试重现“明确结束后，已派发重试被尾帧取消”。
2. 只允许已定义的推断停帧/缓冲/暂停诊断被相应进度撤销；明确 EOF/原生错误保持有限重试。
3. 用户暂停、换房、关闭仍以意图/来源代次撤销整个事务；持续故障仍沿用既有次数和退避。
4. 对高帧率播放的 watchdog 热路径单独测量 Timer 创建量，避免用帧率倍数的定时器分配增加负担。
5. 不修改比例、录制、弹幕协议、持久化设置或缓冲容量；不把离线回归当作双端实机零卡顿证据。

资料：[上游改动](https://github.com/liuchuancong/pure_live/commit/c5944dd5a529cd93eb29486500abd5d496618f80)、
[Issue 808](https://github.com/liuchuancong/pure_live/issues/808)、
[mpv 缓存/EOF 合同](https://mpv.io/manual/stable/)。

## 验证结果

### 先复现再修复

- 红测 `20260905T092421185Z-quality-focused.json`：71 通过、3 失败。两个明确结束场景
  （完成事件、原生 transport error）在解析重试期间收到尾帧后都没有继续创建恢复候选；第三个
  场景记录到 600 帧新增 600 个 Timer。第一次命令在格式检查阶段中止，修正格式后才取得这份红测。
- 修复后 `20260905T092758854Z-quality-focused.json`：五组 **149/149** 通过，覆盖来源/意图隔离、
  音频切换、WUP/HLS 合同、连续帧与真正停帧。新增 7 个用例，另将旧的三项“网络错误被一帧取消”
  用例明确为推断停帧，保留它们的撤销断言，并新增相反的真实 EOF 用例，避免用例固化错误合同。
- 退避和已派发阶段现在只接受同类恢复证据：停帧看新帧、缓冲看 buffering=false、暂停看 playing=true。
  明确结束/原生错误仍恢复；并不解析中文或英文错误文案。缓冲/暂停的修正也覆盖没有纹理帧通道的内核。
- watchdog 改为一个挂起 Timer 加单调时钟截止点。健康帧只推迟截止点；定时器醒来后核对余量，
  从最后一帧算完整超时，不因系统校时产生误判。隐藏画面、音频模式、暂停、换源与释放仍取消监督。
  600 个连续帧的热路径不再新增 Timer；这只是分配量证据，不换算成整机 CPU 降幅或屏幕帧率。
