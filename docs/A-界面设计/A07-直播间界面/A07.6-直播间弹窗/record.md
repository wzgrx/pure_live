- 日期：2026-10-01
- 设计：[docs/A-界面设计/A07-直播间界面/A07.6-直播间弹窗/README.md](README.md)（第五版，用户已确认；待选 F1～F3 按建议做）；计划书 [specs/UI.md](../../../specs/UI.md) 第 4 节（尤其第 7 条各客户端一致）

状态卡：

| 状态 | 内容 | 按钮 |
|---|---|---|
| 没在录 | 开始后一直录到主播下播，或你点“停止录制”。 | ● 开始录制 |
| 等待开播 | 主播开播时自动开始录。现在想录也可以直接开始。 | ● 现在就录 |
| 准备中 | 正在获取直播流（清晰度）… | 取消 |
| 排队中 | 同时最多录 N 个，现在正在录 M 个；有空位就自动开始。 | 取消、改上限（打开录制设置） |
| 录制中 | 时:分:秒、已录大小、码率、清晰度、弹幕条数（录弹幕时）、第几段 · 每几分钟一段 | ■ 停止录制 |
| 重连中 | 第几次，共几次；多少秒后重试，已录时长和大小不会丢 | ■ 停止录制 |
| 整理文件 | 把 N 段合成一个 MP4，可以关掉这里 | — |
| 已保存 | 今天 hh:mm；时长、大小、清晰度、弹幕条数 | 播放、在录制中心查看、● 再录一次 |
| 失败 | 最近失败（哪一步）：原因（第 N 次，已不再重试） | 查看原因（对话框）、重试 |

偏差和原因：

1. **排队中只在名额真的满了才显示**：录制器两次开始之间有 5 秒间隔，这期间任务也是“排队”状态；名额没满时显示成“准备中”，免得出现“最多 3 个、正在录 1 个”却在排队的说法。
2. **第几段按已录时长和分段长度算**（录制器没有公开当前分段号）；重连后新的一次尝试从新的文件开始，这时只是近似。
3. **保存位置只显示最后两级目录**，完整路径在提示里。
4. **顶栏的“自动录”跟着“开播自动录”**：A07.1 时只要有任务就显示“自动录”，但停止、失败、完成的任务不会自己开始录（R4、R5），现在这些情况显示普通的灰圈红点，和面板里的开关一致。

## `live_record` 的改动（只做添加）

| 内容 | 说明 |
|---|---|
| `RecordTask.qualityOverride` | 这个任务录的清晰度（平台的清晰度名或五档之一），没有就用录制设置的默认清晰度。调度时生效：每次尝试、续期和预取都用 `task.preferredQuality(settings.defaultQuality)` |
| `RecordTask.recordDanmakuOverride` | 这个任务录不录弹幕，没有就用录制设置；`RecordChatRecorder.sync` 按任务判断 |
| `RecordTask.autoRecord` | 开播自动录：`false` 时录到的会话在主播下播后结束（合成 MP4、状态“已完成”），重试用完时结束为“失败”，不再回到等待开播；`true` 或没有字段（3.x 的任务）照旧 |
| `RecordTask.lastOutputPath` | 最近一次合成的 MP4，面板的“播放”用 |
| `RecordTask.lastLiveCheckAt`、`nextRetryAt` | 运行时（不存）：上次开播检查、下次重试的时间 |
| 存储 | 四个字段只在有值时写进 JSON，`schemaVersion` 仍是 9；3.x 读到多出的字段会忽略，没有字段就用全局设置 |
| `Recorder.addTask(..., quality, recordDanmaku, autoRecord)` | 新任务带上这次的选择 |
| `Recorder.setTaskOptions` | 改任务的选择（正在录的这一次不变） |
| `Recorder.monitorTask` | 停止、失败、完成的任务重新等待开播 |
| `RecordChatRecorder.countOf(task)` | 这次会话保存的弹幕条数（跨多次尝试，结束后保留给“已保存”） |
