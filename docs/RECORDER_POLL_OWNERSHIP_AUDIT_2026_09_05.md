## 首个错误状态与复现

1. `_pollInFlight.add(id)` 在停止/任务有效性判断之前执行，跳过的任务永久占有 busy。
2. 请求只在发出前检查任务；期间停止、移除、同 ID 替换或关闭，迟到结果仍修改对象、
   `updateTask(id)` 覆盖新卡片，甚至重新排队录制。迟到错误也污染已停止任务。
3. `_stopPolling` 原来只取消 Timer，已经派发的 HTTP 继续执行；旧请求 finally 还可能
   移除新请求的 busy。Timer 不等同于完整异步请求所有权。
4. 重复刷新发现 busy 后立即返回，调用方误认为本次状态检测已完成。
5. 启动恢复清除 `wasStoppedByUser`，把已完成、失败和手动停止的历史任务全都当成待录任务。
   所有房间依次等待，一个慢平台阻塞其后全部任务。
6. 自动检测关闭后仍留有已派发请求；设置中的启动恢复开关又被隐藏在自动检测开关内部，
   已保存的启动行为存在但用户看不到。原“开机自动检测”文案混淆应用启动与系统开机。

先通过生产控制器、受控平台 Future 和调度 spy 加入九个测试；旧逻辑 **0 通过 / 9 失败**，
`20260905T075129237Z-quality-focused.json`。这些是行为断言失败，不是原生依赖或夹具编译错误。

## 实施

- 用每次请求的独立实例标识所有权，保存任务对象、来源和共享完成 Future；先核对有效性再登记。
  同任务并发刷新等待同一请求，避免重复接口读取和过早结束等待。
- 在成功、异常与 finally 分别核对服务存活、任务对象、用户停止意图、调度/收尾占用和请求实例。
  停止/移除/关闭立即使旧请求失效，旧完成事件不释放新请求。运行、排队和收尾任务不重复轮询。
- 保留平台轻量状态刷新合同。20 秒上限限制控制器等待，超时结果继续接受所有权过滤；
  这不是底层 HTTP socket 取消。适配器继续负责实际 I/O 超时，不把三条启动 worker 宣称为
  极端超时场景中严格只有三个底层连接。
- 自动检测关闭时取消未来 Timer 与自动请求的提交资格，显式单次检测独立保留；重新打开时
  检查等待开播任务。重复系统通知不额外叠加常驻轮询。
- 启动恢复先按 ID 去重，再从已保存状态选出原先录制、准备、排队、重连或等待开播的任务；
  保留手动停止与终态历史。启动请求合并，最多三个 worker，关闭后停止派发后续房间。
- 启动开关独立可见，改为“应用启动时恢复待录任务”，中英文明确恢复范围与关闭自动检测时
  只检查一次的规则，说明允许换行。沿用原键和默认值，不引入配置迁移或新依赖。

此改动不调整视频比例、PiP/横竖屏、媒体缓存、Huya WUP、播放恢复或弹幕帧率。
录制控制器由 Android/Windows 共用；调度 spy 验证是否派发，不冒充实际 FFmpeg 写文件。

## 参考合同与剩余边界

- [Dart Future.timeout](https://api.dart.dev/dart-async/Future/timeout.html)：限制等待结果，原 Future
  仍可能随后完成；因此必须独立校验迟到结果。
- [Dart Timer.cancel](https://api.dart.dev/dart-async/Timer/cancel.html)：取消尚未执行的 Timer 回调，
  不替代已派发异步操作的所有权管理。
