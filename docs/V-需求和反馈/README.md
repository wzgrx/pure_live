# V 需求和反馈

所有“从外面进来的要求”的入口：3.x 没有的新功能先在这里提议、评估、等用户确认；用户的问题和 GitHub issue 在这里登记、复现、归类、回复；维护者主动做的审查和调研报告放在这里；决定不做的也记在这里。这一组自己不写代码，采纳后在目标组开任务。排在 S 质量和验证之后、W 上游借鉴之前：它决定以后做什么，但不阻塞正在做的。

## 范围

- 管什么：
  - **新功能提议**（V01）：3.x 没有的功能（D-026）：登记、评估（用户要解决什么、3.x 和上游怎么做、影响、规模）、界面类出图和评审页、用户确认后在目标组开任务。
  - **用户反馈和 issue**（V02）：GitHub `wzgrx/pure_live` 的 issue（`gh --repo wzgrx/pure_live issue list`）和用户在对话里提的问题：原话、复现、根因线索、去向、发布后回复和关闭。
  - **审查和调研**（V03）：只读的全面审查、专题调研、清点和登记表的核对；报告和“每条去了哪”。
  - **不做的**（V04）：是什么、为什么不做（引用 DECISIONS）、替代、重新考虑的条件。
- 不管什么（归哪里）：
  - 修 bug、补 3.x 已有的行为、已批准升级（[specs/UPGRADES.md](../specs/UPGRADES.md)）的余项：直接在目标组登记（PROCESS 第 6 节第一段）。
  - 实现：都在目标组（界面 A 组，功能对应组）；V 组的任务只写 `to`。
  - 上游项目的定期对照 → [W 上游借鉴](../W-上游借鉴/README.md)（看到可借鉴的新功能再进 V01）。
  - 真机验证 → [S 质量和验证](../S-质量和验证/README.md)。
  - 发布说明、issue 模板、隐私 → [Y 发布和运营](../Y-发布和运营/README.md)。

## 风险和注意

- **新功能要用户拍板**（D-026）：D-003（“需要你选的”按建议 A）只管设计细节，不管做不做；不要因为评估写好了就直接在目标组开实现任务。
- **回复 issue 要等修复发布**，最好等真机验证；回复写清版本、怎么用、要不要重新下载（已装构建号 5000 的收不到应用内提示，D-008）。V02.1 回复时只写了“已经修复”。
- **只读访问 GitHub**：查 issue 用 `gh --repo wzgrx/pure_live issue view/list`；评论、关闭只由维护者在发布后做。
- **报告不改正文**：V03 的报告是当时的结论，行号会过时；后来的变化写在报告末尾的“结果”，不改正文。
- 新功能的设置只加不改、默认值让老用户感觉不到变化（D-018）。
