# 发给云端的提示词

在 Claude 桌面应用的 Code 标签页新建会话并选 **Cloud**（或打开 claude.ai/code），仓库选 `wzgrx/pure_live`，然后发下面的提示词。**一个任务开一个会话**，互不影响，可以同时开几个；先开哪些、哪些不能同时开，看 [TASKS.md](TASKS.md) 的“建议顺序”和“哪些能同时开”。

## 总提示词（一个会话按顺序做完全部任务）

不想一个个开会话时用这一段。所有任务在同一个分支 `cloud/4.0.x` 上按依赖顺序做，所以不用等维护者合并。会话中途结束（时间或上下文用完）时，新开一个 Cloud 会话**再发一遍同样的话**，它会从总表的状态接着做。

```text
你在 GitHub 仓库 wzgrx/pure_live 上工作，目标是按顺序做完 docs/cloud/TASKS.md 里的全部任务（只做 Android）。

一、先读
完整读 docs/cloud/RULES.md（共同规则）和 docs/cloud/TASKS.md（总表、依赖、维护者已经定下的决定）。下面和 RULES.md 不同的地方以这里为准：所有任务都在同一个分支 cloud/4.0.x 上做，整个过程只开一个草稿 PR。

二、分支
远端已有 cloud/4.0.x 就检出它接着做；没有就从最新的 master 新建。只推送这个分支，不要推送到 master，不要合并 PR，不要 rebase，不要强推。

三、顺序
按这个顺序做：B01、B02、B03、B04、P01、P02、B05、B06、U02、F02、P03、P05、B07、B08、F01、U01、B09、P06、P04。
跳过分支上的 TASKS.md 里状态已经是“待合并”或“完成”的；状态是“进行中”的从记录里写的进度接着做。

四、每个任务
1. 开始前 git fetch origin，把 origin/master 合并进 cloud/4.0.x（有冲突就解决）。
2. 读 docs/cloud/tasks/<编号>.md，严格照做：先找根因，修 bug 先写会失败的测试；要出设计的任务先出效果图再实现。
3. 提交信息以 [<编号>] 开头（英文）。写记录 docs/cloud/records/<编号>.md（中文，内容按 RULES.md“交付”第 2 条）。
4. 跑 bash tools/gate/gate.sh --all，不通过就修到通过；跑不了完整门禁时按 RULES.md 的最低要求跑，并在记录里写明。
5. 在 TASKS.md 把这个任务的状态改成“待合并（cloud/4.0.x，<该任务最后一个代码提交的短哈希>）”，单独提交，然后推送。
6. 第一个任务推送后开草稿 PR 到 master，标题“4.0.x 云端任务”；之后每完成一个任务，在 PR 里加一条中文评论：编号、每条做到没有、测试结果、要在真机上看的、需要维护者确认的。
7. 不用等我确认，接着做下一个。

五、拿不准的时候
按 TASKS.md“维护者已经定下的”和 RULES.md 选最稳妥、最接近 v3 习惯的做法继续，写进该任务记录的“需要维护者确认”一节，不要停下来等我。只有会删除用户数据、要改签名或版本号、需要真实账号或真机才能做的，跳过那一条并在记录里写明原因。

六、快结束时
会话的时间或上下文快用完时，在一个任务中间也要先停：把做完的部分提交并推送，在 TASKS.md 把状态写成“进行中（cloud/4.0.x，做到 c<几>）”，推送后再停。

七、最后
全部做完或停下时，用中文汇总：完成了哪些任务（编号和提交）、PR 链接、每个任务要在真机上看的、需要我决定的、还没做的。
```

## 单个任务（最常用）

把 `<编号>` 换成任务编号（例如 `B01`）：

```text
你在 GitHub 仓库 wzgrx/pure_live 上工作。先完整读 docs/cloud/RULES.md（共同规则），再读 docs/cloud/tasks/<编号>.md（你的任务单），严格照做。
从最新的 master 新建分支 cloud/<编号>，只提交到这个分支，不要推送到 master，也不要合并 PR。
完成后：写 docs/cloud/records/<编号>.md，推送分支，开一个草稿 PR 到 master，最后用中文告诉我分支名、PR 链接、每条做到没有、测试结果和需要我决定的事。
```

## 一个会话连做几个小任务

只用于互不依赖、不在同一组的小任务（例如 B01 和 F02）；同一组有先后的任务（例如 B02 → B05）要等前一个合并进 master 再开：

```text
你在 GitHub 仓库 wzgrx/pure_live 上工作。先完整读 docs/cloud/RULES.md，再依次读 docs/cloud/tasks/<编号1>.md、<编号2>.md、<编号3>.md。
按顺序做，每个任务一个分支（cloud/<编号>，都从最新的 master 新建）、一份记录、一个草稿 PR；一个做完、推送、开好 PR 后再做下一个。不要推送到 master，也不要合并 PR。
全部做完后用中文汇总：每个任务的分支、PR 链接、做到没有、测试结果、需要我决定的事。
```

## 修改上一次的结果

维护者看过 PR 后有意见时，在同一个会话里接着发：

```text
按下面的意见修改分支 cloud/<编号>（不要新开分支），改完更新记录、推送，并回复改了什么：
<意见>
```

## 合并（维护者在本地做）

云端推送分支后，维护者在本地：

```bash
git fetch origin cloud/<编号> && git merge --no-ff origin/cloud/<编号>
```

然后跑 `bash tools/gate/gate.sh --all`，在 K90 上按记录里的步骤看，通过后推送 master，在 `docs/cloud/TASKS.md` 里把状态改成“完成”。

用总提示词时只有一个分支 `cloud/4.0.x`，可以只合并到某个任务为止：`git fetch origin cloud/4.0.x`，再 `git merge --no-ff <那个任务状态提交的哈希>`（每个任务的状态提交以 `[<编号>]` 开头，`git log --oneline origin/cloud/4.0.x` 能看到）。
