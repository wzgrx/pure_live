## 做法

- **接口和输出沿用 v3**：`LiveSite` 和 v3 实现过的全部可选能力——目录分页（`LiveSiteDirectoryPager`）、目录说明（`LiveDirectoryNotice`，键 `jdlive_directory_scope`）、可取消的搜索（`LiveCancellableSearch`）、关注刷新（`LiveSiteRoomRefresher`）、录制详情（`LiveSiteRecordRoomResolver`）、取流（`LivePlayUrlResolver`）、恢复（`LivePlayRecoveryResolver`），外加 `LiveSiteLinks`。3.x 的 JSON 不变。
- **请求照 v3**：
  - 所有请求都以 `jdlive` 的名义发出（代理路由由应用按平台注入），**不跟随跳转**，不带 Cookie（v3 的京东直播没有账号）；
  - 接口请求头是 v3 的 `apiHeaders`：UA（iOS Safari）、`Accept: application/json, text/plain, */*`、`Origin: https://lives.jd.com`、`Referer: https://lives.jd.com/`；
  - 精选列表 `GET https://api.m.jd.com/api?appid=h5-live&functionId=liveListWithTabToM&v=<毫秒>&body={"tabId":1,"currentCount":"<条数>","page":<页>,"timestamp":<首页时刻>}`；
  - 播放接口 `GET …&functionId=getImmediatePlayToM&t=<毫秒>&body={"liveId":"<场次号>"}`，不需要 h5st 签名；
  - 进房和录制时，直播中的房间还要用 v3 的媒体请求头（UA、`Origin`、`Referer: https://lives.jd.com/#/<场次号>`）下载 HLS 媒体列表并校验（下面“房间”）；
  - 一页列表、一次“播放接口加媒体列表”共用一个 20 秒的总时限（v3 的 `_scope`），超时是 `NetworkFailure`，调用方取消原样抛出取消。时钟可注入，`v`、`t` 和首页时刻都来自它。
- **目录照 v3**：
  - 一个分类 `JD Live`（id `jdlive`），一个分区“精选直播购物”（`areaType: official`，`areaId: featured`），只在第 1 页、每页条数至少 1 时给出，不发请求；
  - 原生分页：第 1 页以当时的时刻开始一个“序列”，之后每页带上一页回答的 `currentCount` 和同一个首页时刻；上一页没有要求下一页（或没有取过）时，这一页为空、不发请求；页码小于 1 为空；
  - 本页有 30 场以上直播才有下一页（v3，见问题 1）；
  - 目录、推荐（分区房间同推荐）、每个搜索词各有自己的序列；推荐截取前 `pageSize` 条（最多 30），页码或条数小于 1 时为空、不发请求；
  - 列表项只取 `templateType` 为 1 的直播，运营位（`-100`）跳过；没有合法场次号、`liveId` 与 `id` 不一致或重复的项跳过；项不是对象、直播没有 `data` 对象、名字或图片不是文本时整页 `ApiChanged`（v3 的检查）。
- **卡片照 v3**：房间号是场次号；`userId` 是店铺账号 `authorId`，没有时用场次号；标题 `title`、主播 `userName`（店铺名），空时写 `JD Live`；头像 `userPic`，没有时用封面；封面 `indexImage`；图片只收 `https` 的 `*.360buyimg.com`；分区写 `JD Live`；`pv` 作为累计观看（`totalViewers`，口径 `totalViewers`）；状态 1 直播，0 预告、2 结束、3 回放都显示为未开播，10/11 暂停和未知显示为未知；公告是 3.x 的聊天说明；`link` 是 `https://lives.jd.com/#/<场次号>`；房间带 v3 的媒体请求头 `httpHeaders`（3.x 的 JSON 里有）。
- **搜索照 v3**：场次号（5～18 位数字）或房间链接直接查播放接口（只有第 1 页，平台说没有的是没有结果，其他错误照样报出）；其他关键词请求这个词的序列的第 `page` 页，按场次号、店铺账号、店铺名、标题筛选（不区分大小写），取前 `pageSize` 条。空白、页码或条数小于 1、条数超过 100 给空、不发请求。别的网站的链接现在直接给空（问题 14）。
- **房间照 v3**：
  - 播放接口只有状态、封面（`blurredImg`）和地址，**没有标题、店铺名、头像和观看数**（带这些的详情接口 `liveDetailToM` 要 h5st 签名，S03）。v3 用本次运行中见过的列表卡片补上（`_known`）：店铺账号、名字（仍是占位 `JD Live` 时）、头像、观看数；封面保留播放接口的 `blurredImg`。没见过的房间，标题和主播名是 `JD Live`，`userId` 是场次号，头像用封面。播放接口的结果随后替换这场的卡片；
  - 房间号就是请求的场次号（v3：播放接口回答的 `liveId` 必须等于它，否则 `ApiChanged`）；传入房间链接也按链接里的场次号（v3），不是场次号的输入 `NotFound`，不发请求；
  - 直播中必须同时有 `h5VideoUrl`（`.m3u8`）和 `videoUrl`（`.flv`），都是 `https` 的 `*.jdcloud.com`、端口 443、在 `/live/` 下，而且流名相同，否则整个回答 `ApiChanged`（v3 的严格检查）；`secret` 为 1 时不论状态都是“仅限京东 App”，状态未知，公告写 3.x 的“仅限京东应用访问”；
  - 深度照 v3：刷新、开播状态、按号搜索只请求播放接口（1 个请求，房间不带数据）；进房、录制在直播中时再下载媒体列表并校验（2 个请求），房间带 `JdLiveRoom`（含地址，不存进 JSON）；
  - 媒体列表的校验照 v3：不超过 1 MiB 字符，以 `#EXTM3U` 开头，每个媒体引用（URI 行和标签里的 `URI="…"`）都解析到同一主机的 `https`、`/live/` 下、以流名开头，至少 1 个、最多 1000 个；不合格 `ApiChanged`，列表 404 是 `StreamUnavailable`（问题 6）。
- **开播状态**：一个请求。直播为真；预告、结束、回放为假；仅限 App 报 `NeedsLogin`，暂停报 `StreamUnavailable`，未知状态报 `ApiChanged`，都不当作未开播（问题 7）。
- **画质和线路照 v3**：两档，`HLS（推荐）`（id `hls`，排序 2）在前，`FLV 原始线路`（id `flv`，排序 1）在后，不发请求。取流直接读进房时的播放接口，不发请求，确认的画质就是请求的；恢复重新请求播放接口和媒体列表（2 个请求，v3）。每档一条线路：格式 HLS 或 FLV，线路编号是主机名（`zt-pull-ai.jdcloud.com`）；**不带请求头**（v3 的播放器没有京东分支，发的是自己的默认值；归档规格 §6 实测不带也能拉）；地址没有签名和过期参数，没有 `PlayLease`；编码不写（接口不说；归档 v4 按一次实测写了 AVC）。
- **不能播时在取流时报错**：列表卡片、刷新或搜索得到的房间（没有进房数据）、明确未开播的房间报 `StreamUnavailable`，仅限 App 报 `NeedsLogin`，都不发请求；别的平台的房间、别的画质是调用方错误（`ArgumentError`）。
- **没有 Cookie、登录和弹幕**：v3 的京东直播全部匿名，弹幕是 `EmptyDanmaku`，所以不注入 `CookieVault`，也不输出弹幕参数。
- **缓存有上限**：见过的卡片最多记 2000 个、搜索词的序列最多 32 个，超出时丢最早的（问题 3）；目录和推荐的序列不丢。

## 样本与 v3 的冻结输出

归档没有京东直播的 `expected.json`（归档的旧版对照工具只做了前五个平台，规格 §11 也写明没有旧版期望值）。本模块用 `fixtures/jdlive/legacy_expected.dart` 生成，做法同 BIGO、微博：

- 把 v3 的 `JdLiveApi`、`JdLiveLink`、`JdLiveSite` 原样搬进一个 Dart 脚本（由一个只做下列改动的脚本拼接，每处改动都校验恰好生效一次），以及 `request_scope.dart` 的 `withRequestCancellation`。v3 本来就把传输做成可注入的函数（`JdLiveRequest`），所以只换了它：按主机、路径和查询读样本；时钟不参与比较（`v`、`t` 和列表 `body` 里的 `timestamp`，v3 读的是 `DateTime.now()`），请求记录里也去掉它们；翻页的流程另记各请求的 `timestamp` 是否相同（`timestamps`，每个不同的值一个记号）。没有样本的请求抛 StateError，v3 的 `_scope` 把它记为 `transport`，脚本另记在 `unmatched` 里。`apiHeaders` 以外的请求头写在地址后面。
- 其他改动：去掉导入；只在网络路径上的 `_defaultRequest`、`_readBody` 不搬，传输因此必填；去掉 `extends LiveSite implements …`、`@override` 和弹幕 getter；站点的默认 api 必填。`i18n` 返回 3.x `zh.json` 的文字；Dio 的 CancelToken 是桩；v3 的 `LiveRoom` 等模型只搬用到的部分（`toJson` 里有 v3 的 `HttpHeaderPolicy.normalize`）。
- 归档的直播样本 `S02-play-live` 没有媒体列表，v3 的进房在它上面会失败（没有样本）；为了也能对照归档房间的进房，另记一份用 `S04-playlist` 的正文、换成这场的流名作答的输出（`withS04Playlist`）。
- 对录下的回答做合成修改，记下 v3 的结果（`variants`）：列表 38 种（名字、标题、图片、观看数、状态、场次号、重复、`templateType`、结构、`currentCount`、`code`、`subCode`），播放接口 31 种（`secret`、各状态、地址缺失/协议/主机/端口/路径/流名/带查询、封面、`code`、`subCode`、`data`），媒体列表 23 种。
- 重新生成：在仓库根目录运行 `dart run fixtures/jdlive/legacy_expected.dart`。

**脱敏**：归档规则没有处理响应头 `x-rp-sdtoken`（京东网关下发给客户端的风控令牌，`set;1800;<令牌>`），8 个样本里的 7 个带它，已换成同形的合成值（同样的前缀、长度和字符集，同一个原值换成同一个值），记在各自 `meta.json` 的 `scrubbed`。`S04-playlist` 分片地址的 `volcDst`（CDN 内部 IPv4 地址的 Base64）和响应头里 CDN 节点的地址（`tracestate` 的 `server_ip`、`x-server-ip`、`via`）换成文档地址 `198.51.100.1`～`3`（RFC 5737，`volcDst` 保持 16 个字符、没有填充）。另外查过访客编号、设备编号、Cookie、出口 IP：请求没有 Cookie，回答没有 Set-Cookie，列表和播放接口只有店铺的公开信息；`x-api-request-id`、`x-mlaas-at`、`tranceId` 是单次请求的追踪号，保留。`raw.sha256` 仍是原始正文的摘要。

## 保持 v3 行为、没有采用归档 v4 或上游做法的地方

- **详情用列表卡片补名字**（v3、上游 TV）。归档 v4 的详情标题和主播名是空串，直接粘贴链接进房时什么都没有。
- **没见过的房间写占位 `JD Live`，刷新会覆盖关注里存下的名字**（v3 用户实际看到的）。改成留空、让 `mergeFrom` 保留存下的名字，列为升级候选 2。
- **“本页至少 30 场才有下一页”**。归档 v4 改成“本页有直播就继续”，修好了只翻一页的问题（问题 1），但会改变列表内容，列为升级候选 1。
- **两档画质 `HLS（推荐）`、`FLV 原始线路`，HLS 在前**。归档 v4 是一档 `fhd`“超清”、两条线路 FLV 在前，会改变画质菜单和已存的画质 id。
- **进房和录制时下载并校验媒体列表**（2 个请求）。归档 v4 不预先下载，交给播放器；那样请求更少，但媒体列表坏了时进房不再报错，行为不同。
- **状态照 v3**：暂停和未知状态显示为未知，回放（状态 3）显示为未开播。归档 v4 把暂停当未开播、未知状态报 `ApiChanged`（整个房间失败）。
- **直播中缺一个地址整个房间失败**，不用 `pcVideoUrl` 兜底。归档 v4 用 `pcVideoUrl` 补 FLV；列为升级候选 4。
- **线路不带请求头**（v3 的播放器没有京东分支）。归档 v4 带 UA、`Origin`、`Referer`（站点根）；列为升级候选 5。
- **有分类、分区和搜索**（v3、上游 TV）。归档 v4 没有分类，没有搜索。
- **图片只收 `https` 的 `*.360buyimg.com`**（v3）。归档 v4 收任何 http(s) 地址。样本里的图片都是 https，结果相同。
- **编码不写**。归档 v4 按一次实测写了 AVC；接口本身不说（同 LiveMe）。
- 上游 pure_live_TV 与 v3 相同，没有要采用的修复。

## 回归条目的覆盖

归档规格没有 REG-JDLIVE 条目。§10“踩过的坑”两条和 `spec/regressions.md` 里涉及本平台的通用条目，属于平台层的部分都有测试：

- **精选只翻一页**（§10）：本模块查明根因是“本页至少 30 场”的判断（问题 1）。按 v3 保留，测试固定了 v3 的行为：S01 第 1 页 30 场会要第 2 页（`currentCount` 37、同一个首页时刻），S04 第 1 页 29 场不再要；修法列为升级候选 1。
- **探测脚本以为播放接口要签名**（§10）：播放请求只有 `appid`、`functionId`、`t`、`body`，没有 h5st；请求经 `live_net`（`dart:io`）发出。
- REG-COMMON-001（详情失败不等于下播）：所有失败都是类型化错误；开播状态在仅限 App、暂停、未知状态时报错，不返回假。
- REG-COMMON-004（观众数分开）：`pv` 是累计观看，没有在线人数。
- REG-COMMON-008（请求头随取流结果走）：线路自带请求头（本平台为空，与 v3 的播放器一致），播放和录制共用。
- REG-COMMON-011（链接识别）：只认 `lives.jd.com` 的片段路由 `#/<场次号>`（可带 `/live`、`/notice`、`/closed`、`/replay` 和查询），仿冒域名、别的端口、带用户信息的、路径里的号码都不认；分享文本经 `LinkParser` 识别，不发请求。
- REG-LEASE-005（恢复重新获取）：恢复重新请求播放接口和媒体列表，不复用旧地址。
