## 目标

用户想知道关注的主播什么时候开播，现在只能打开应用看关注页（或开着“关注自动刷新”放着）。提议：给关注的直播间加“开播提醒”，主播从没开播变成开播时发一条系统通知，点通知直接进直播间。

下面“方案”一节是 2026-10-07 的**评估初稿**；D-036 同意做以后，2026-10-09 补完评估、定了设计，见“评估结论和设计（定稿）”，实现在 [O01.1](../../../O-Android系统集成/O01-通知和前台服务/O01.1-开播提醒/README.md)。

## 方案（评估初稿）

### 三种做法

| 做法 | 怎么做 | 能提醒到的时候 | 代价 |
|---|---|---|---|
| A 应用活着时提醒（建议先做） | 关注刷新（启动、下拉、定时、回前台）每轮结束后，比较这一轮和上一轮的 `effectiveLiveStatus`：从 offline/unknown 变成 live 的、开了提醒的房间发通知；定时刷新的间隔照用户设的 | 应用在前台、或在后台但进程没被系统冻结（开着后台播放、录制时一定活着） | 小：不加后台服务；只在用户已经开着“关注自动刷新”时才真的“及时” |
| B 系统定时唤醒检查 | Android 用 WorkManager 周期任务（最短 15 分钟，系统决定实际时间），只查开了提醒的房间 | 应用不在后台时也能查，但 HyperOS、ColorOS 等会延后或不执行，最多晚几十分钟 | 中：新插件和原生代码；要处理电池优化、自启动；耗流量和电 |
| C 常驻前台服务 | 像录制一样开前台服务，常驻通知栏，按间隔查 | 最及时 | 大：常驻通知、耗电；用户多半不接受；不建议 |

建议：**先做 A**（改动小、和 3.x 的关注刷新同一套），把“需要应用活着”在设置说明里写清；B 等 A 用一段时间、用户还想要更及时时再提议。

### A 的改动清单（确认后在目标组开任务）

| 编号 | 改什么 | 目标组 |
|---|---|---|

| c2 | 关注刷新每轮结束后找出“刚开播”的房间：上一轮是 offline/unknown、这一轮 live，且开了提醒；同一场直播只提醒一次（按开播时间或场次去重）；应用在前台、正在看这个直播间时不提醒 | I04 |
| c3 | 新通知类别“开播提醒”（`IMPORTANCE_DEFAULT`），标题“主播名 开播了”，正文直播标题；点通知进直播间；几个同时开播合并成一条 | O01（原生）、A14（样子） |
| c4 | 设置：总开关“开播提醒”（默认关）；说明写“需要打开关注自动刷新，应用在后台被系统清理后收不到”；打开时要通知权限、建议打开关注自动刷新 | A11（设置界面）、I04 |

## 评估结论和设计（定稿，2026-10-09）

做不做由 D-036 定了（同意做，默认关）；下面要选的都由维护者按 D-003 选了建议的做法，用户随时可以推翻。

### 核对过的现状（2026-10-09 的代码）

1. **关注刷新**（`apps/pure_live/lib/features/favorite/favorite_controller.dart`）：启动核验 `_verifyAll`、下拉和再点“关注” `refreshVisible`、回到前台 `_resumed`（`refreshFavoriteOnResume` 默认开，15 秒内不重复）、直播间“看其他”的刷新按钮 `refreshAll(visible: false)`（`app/app.dart:98`）、定时 `_scheduleAutoRefresh`（`Timer.periodic`，`autoRefreshFavorite` 默认关，间隔默认 30 分钟、5～360）。每轮的结果 `FollowRefreshResult.rooms` 是新拿到的详情，失败的房间是 `pendingAfterError()`（状态 `unknown`）。刷新结果合并进存储，**不保留上一轮的状态**，所以“刚开播”要在内存里记。
2. **状态**：`LiveRoom.effectiveLiveStatus`（`packages/live_core/lib/src/live_room.dart`）：`live`、`offline`、`replay`、`unknown`、`banned`、`carousel`；受限的直播（付费、要登录）仍是 `live`。`startedAt`（开播时间）只有部分平台给，没给是 null。
3. **录制的等开播检测**（`packages/live_record/lib/src/recorder.dart` 的 `_schedulePoll` `:1145`、`_doPoll` `:1191`）：开了“自动轮询”（`enable_polling`，默认关）的等待任务每 `live_check_interval` 秒（默认 30，10～300）查一次；成功时 `task.updateFromRoom(room)..lastLiveCheckAt = now`（`:1205`），失败时 `lastLiveCheckAt` 和 `markFailure` 的 `lastFailTime` 同一时刻（`:1223`）。任务列表的每次变化从 `Recorder.changes`（广播流）发出。等开播时**没有**前台服务，只有真正在录时才有（`RecorderForegroundService`）。
4. **通知**：只有原生的两个类别“录制”“录制提醒”（`RecorderForegroundService.kt:159-172`），提醒的点按意图请求码是 `0x1000 + 28 位哈希`（`:194`）。点通知打开直播间不用新路：桌面长按快捷方式已经用 `ShareIntakePlugin.ACTION_OPEN` 带 `platform`、`roomId`、`title`、`nick` 打开直播间（`ShareIntakePlugin.kt:238`，Dart 侧 `app/intake/share_intake.dart` 的 `openRoom`）。
5. **权限**：`shared/permission_prompts.dart` 的 `BackgroundPermissions.confirm` 先问通知、再问电池优化，文字是讲后台播放的；设置里的 `GatedToggleTile`（`features/settings/playback_tiles.dart`）开开关前走它。
6. **后台能做到什么**：Android 12 起，退到后台、没有前台服务的应用进程很快会被系统冻结（cached apps freezer），Dart 的定时器不再跑；HyperOS 还会更早清理后台。进程不被冻结的时候只有：应用在前台、开着后台播放（`mediaPlayback` 前台服务）、正在录制（`dataSync` 前台服务）。所以“应用开着时提醒”的实际意思是：在前台，或在后台播放、录制时。

### 设计选择（D-003）

| 编号 | 问题 | 选了什么 | 为什么 |
|---|---|---|---|
| L1 | 三种做法选哪种（A 应用开着时 / B 系统定时唤醒 / C 常驻前台服务） | **A**，先做；B 登记成 O01.2 以后再看；C 不做 | A 不加常驻服务、不加插件，和关注刷新同一套；C 要常驻通知、耗电，用户多半不接受；B 在 HyperOS 上不可靠，要等 A 用一段时间再定 |
| L2 | 检测从哪来 | 不加新的检查：每轮关注刷新的结果、录制等开播任务每次成功的检查（`lastLiveCheckAt` 往前走了、这次没失败），都交给同一个“看到过什么”的记录（`LiveAlertTracker`）比较前后状态。开了“关注自动刷新”时就用它的定时器（用户的间隔，查全部关注）；没开时，开播提醒自己的定时器每 15 分钟只查要提醒的关注 | 复用现成的刷新和录制轮询，同一个房间被两边查到也只算一次（L6）；15 分钟和 Android 周期任务的最短间隔一样，流量和耗电都低；想更及时的人打开“关注自动刷新”选 5 分钟 |
| L3 | 按主播选还是按分组选 | 一个总开关“开播提醒”（默认关）+ 下面“只提醒这些标签的关注”：每个标签一个开关，都不开 = 全部关注；已删除的标签不算，选的标签都删了就回到全部。只想提醒几位主播的，给他们加同一个标签 | 标签（I07）已经有存储、备份、同步和管理界面，不用新字段、不改 3.x 的关注格式；用标签同时做到了“按分组”和“按主播”。每张卡片、直播间关注菜单里单独的开关和小铃铛要出图评审、要新存储，登记成 A09.13，用户嫌建标签麻烦再做 |
| L4 | 什么算“开播了” | 这次看到是 `live`，上次看到的是不在播（`offline`、`replay`、`banned`、`carousel`）；`unknown`（请求失败、状态待确认）不算证据，前后都跳过；轮播、录播不算开播；受限的直播（付费、要登录）算开播 | 失败后恢复（待确认 → 直播）不误报（任务书的风险）；受限的直播也是主播开播了，进房后由播放说明为什么看不了 |
| L5 | 第一次看到的状态 | 只记下，不提醒：应用启动、新关注的房间、刚打开开关、刚把房间加进提醒的标签时，已经在播的不发 | 启动时一下子弹出一堆“开播了”是噪音；刚打开开关时用户正看着设置；这样应用重启后也不会把同一场再发一遍 |
| L6 | 同一场不重复 | 同一个房间：在播 → 失败 → 在播是同一场；下播后 15 分钟内又开播算断流重连，不发；两次开播时间相差 2 分钟以内算同一场（平台说下播是误报），不发；一直在播但开播时间往后挪了 15 分钟以上，算两次检查之间下播又开播，发。录制的检查和关注刷新共用同一份记录，谁先看到谁发，另一个不再发 | 断流重连很常见，不能每次都响；`startedAt` 只有部分平台给，所以两条规则都要 |
| L7 | 通知长什么样、点了去哪 | 新通知类别“开播提醒”（默认重要性：有声音、不弹横幅）；一个房间一条：标题“主播名 开播了”（没有主播名用平台名），正文是直播标题（没有标题写“点按进入直播间”），时间显示开播时间（平台给了的话），小图标用媒体通知的单色电视；同一个房间的下一场替换上一条；几个房间同时开播就是几条，四条起系统自动叠起来；点通知直接进直播间（和桌面长按快捷方式同一条路），点了通知自动消失 | 一条一个房间，点哪条进哪个房间，不用新的“合并后去哪”的页面；不加新图标资源 |
| L8 | 通知权限 | 打开开关时只问通知权限（文字讲开播提醒），拒绝或取消时开关不开、说明变红（和后台播放一样）；不问电池优化 | 没有通知权限这个功能就没用；电池优化豁免挡不住系统冻结后台进程，问了也不能让它在后台更可靠，反而多一个弹窗；开后台播放时已经会问 |
| L9 | 哪些客户端有 | 只有 Android（设置里只在 Android 显示；别的平台不记、不发） | 当前只做 Android（D-004）；Windows、Linux 的系统通知等 X 组 |
| L10 | 应用在前台时发不发 | 发，但用户自己发起、看得到结果的几轮只记不发：启动核验、下拉、再点“关注”、直播间“看其他”的刷新按钮；回到前台、定时、录制检查发 | 看着别的直播间时，关注的主播开播了正是要提醒的；用户自己刷新时结果就在眼前 |
| L11 | 正在看的就是这个直播间时 | 这次不判断（照发） | 4.x 没有“现在在看哪个房间”的全局状态；要从没开播的直播间页面等到它开播才会碰到，很少见；有反馈再补 |
| L12 | 和自动录制的同一个房间 | 照发一次开播提醒（同一场只一次，L6）；录制的常驻通知照旧 | 录制通知是静音的常驻状态，点了去录制中心；开播提醒有声音、点了进直播间，用途不同，不算重复 |
| L13 | 默认值、存储、备份 | 新设置 `liveAlertEnabled`（默认关）、`liveAlertTagIds`（默认空 = 全部），都在 `refresh` 一节，跟备份和设备同步；3.x 的 `refresh` 只读自己的键，看不到它们 | D-036：老用户感觉不到变化；D-018：只加不改。同步到另一台设备时如果那台没给通知权限，通知发不出来，关掉再开一次会问 |
| L14 | 精确还是不精确的定时 | 都不用系统闹钟：应用活着时用 Dart 的定时器；O01.2 如果做，用 WorkManager 的周期任务（不精确，最短 15 分钟） | 精确闹钟要 `SCHEDULE_EXACT_ALARM`，Android 14 起只给闹钟和日历类应用，耗电；开播提醒晚几分钟没关系 |
| L15 | 说明怎么写 | 开关的说明直接写清限制：“关注的主播开播时发通知，点了进直播间；只在应用开着时（前台、后台播放或录制）提醒”（设置说明最多 40 个字，A01.4 c2；15 分钟一查和被清理后收不到写在 O01.1 的说明里） | 不承诺做不到的（任务书的风险） |
| L16 | 效果图和评审页 | 不出 | D-036 授权维护者定；只是设置里的一个开关和一组标签开关（和现有设置行同一种样子），加一种系统通知；布局由 widget 测试固定，真机截图在 O01.1 的验证里补 |
