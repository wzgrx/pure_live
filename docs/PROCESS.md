# 做法

- 更新：2026-10-03（第 2 版，docs v1：字母编号和文件夹、新功能、上游借鉴、维护、文档版本）
- 适用于所有任务和所有执行者：维护者、Claude，以及其他 AI。

## 0. 一页看懂

```text
登记（tasks.toml）→ 准备 → 设计（界面类要评审）→ 任务书 → 开发（按阶段，独立分支）
      ↑                                                        │
      └──── 额度不够：停在阶段边界，写接手说明（第 5 节）◀────────┤
                                                               ▼
              收尾（登记表、生成、推送）◀── 真机验证 ◀── 合并审查（第 8 节）
```

## 1. 编号和文件夹

| 层 | 编号 | 例子 | 文件夹 |
|---|---|---|---|
| 组 | 一个大写字母 | `A` 界面设计 | `docs/A-界面设计/`（README 生成） |
| 子分类 | 组 + 两位数字 | `A07` 直播间界面 | `docs/A-界面设计/A07-直播间界面/`（README 生成） |
| 任务 | 子分类 + `.` + 序号 | `A07.13` 切换直播间面板 | `docs/A-界面设计/A07-直播间界面/A07.13-切换直播间面板/` |
| 逐项界面 | 任务 + `-` + 两位序号 | `A07.13-08` | 写在任务 README 的界面清点表里 |

- **组的字母按优先级排**：A 界面设计排第一，往后是各功能组，最后是支撑和流程。B、F、M、P、T、U 不用（旧编号用过，见 [MAPPING.md](MAPPING.md)）。加新组时用还没用过的字母，并在 [CHANGELOG.md](CHANGELOG.md) 记一个小版本。
- **文件夹 = 编号 + `-` + 简短的中文名**，不含空格和括号（括号会弄坏 Markdown 链接）。组和子分类的名字取登记表里的 `title`（去掉空格和括号），门禁检查两者一致；改名时文件夹和登记表一起改，再运行 docs.py 查链接。任务文件夹的中文名取标题开头的几个字（14 个字以内），建好后不再改。
- 任务序号在子分类里按登记顺序递增，不复用、不改。**返工和后续开新任务**（新序号），标题写“接 A07.13”。
- 子分类是长期的范围，不会做完；任务才有完成。
- 任务文件夹在开工时建，没开工的任务只在登记表里。文件夹里固定的文件名：

| 文件 | 内容 | 模板 |
|---|---|---|
| `README.md` | 界面任务的设计说明，或功能任务的说明和 3.x 对照 | [templates/design.md](templates/design.md)、[templates/feature.md](templates/feature.md) |
| `brief.md` | 任务书：交给执行者（任何 AI 或人）的全部要求 | [templates/brief.md](templates/brief.md) |
| `record.md` | 记录：做了什么、根因、偏差、测试、提交；分几次做的写 `record-2.md` | [templates/record.md](templates/record.md) |
| `verify.md` | 真机验证：步骤、结果、截图 | [templates/verify.md](templates/verify.md) |
| `review.md` | 合并审查：逐条检查的结果 | [templates/review.md](templates/review.md) |
| `page.json`、`src/`、`*.jpg`、`page/` | 界面任务的评审页源、效果图源文件、效果图、评审页导出 | [templates/page.json](templates/page.json) |

- 子分类文件夹里可以放这个子分类共用的资料（例如 S02 的真机清单 `CHECKLIST.md`、Y03 的 `releases/` 和 `readme/`）；生成的 README 会自动列出它们。
- **组和子分类的 README 分两部分**：上面是手写的说明（组用 [templates/group.md](templates/group.md)，子分类用 [templates/sub.md](templates/sub.md)：范围、现状、代码地图、3.x 基线、已知问题、路线），下面 `docs:生成开始` 到 `docs:生成结束` 之间是脚本生成的进度和任务表。只改上面，生成区由 docs.py 维护。
- **每个任务都有 `README.md`**（任务说明）：界面任务用 design.md，其他用 feature.md；**每个没完成的任务都有 `brief.md`**（任务书，模板 v2）；**待真机的任务都有 `verify.md`**（真机步骤）。

## 2. 任务类型和证据

| 类型 | 什么任务 | 设计阶段的产出 | 完成的证据 |
|---|---|---|---|
| 界面 | 用户看得到的界面 | 效果图、评审页、用户确认 | 布局测试、真机截图对照效果图 |
| 功能 | 行为和逻辑 | 和 3.x 的行为对照 | 测试（修 bug 时改之前会失败）、真机步骤 |
| 平台 | 直播平台、弹幕协议 | 真实接口样本 | 样本对照测试、真实接口跑一遍 |
| 性能 | 速度、流畅度、内存、耗电 | 测量现状和目标 | 改前改后的数字（基准 JSON、帧时间、毫秒） |
| 原生 | Android、Windows 原生代码 | 方案 | 构建通过、真机日志 |
| 验证 | 真机验证、覆盖安装验证 | 清单 | 逐项结果和截图 |
| 发布 | 版本、签名、发布页、更新通道 | 检查清单 | 安装包检查结果、发布页地址 |
| 工程 | 工具、门禁、脚本 | — | 门禁通过、脚本输出 |
| 文档 | 文档本身 | — | 文档检查通过 |

## 3. 登记表、状态、阶段、进度

### 3.1 登记表

[tasks.toml](tasks.toml) 是唯一的进度来源，每个任务一段：

```toml
[[task]]
id = "A03.3"                 # 编号
title = "直播间拖动手感：…"    # 标题
type = "性能"                  # 第 2 节的类型
status = "暂停"                # 第 3.2 节的状态
size = "中"                    # 小（约 1 小时内）、中（1～3 小时）、大（3 小时以上）
tier = 2                       # 档位：1 马上做、2 应该做、3 以后；没完成的必须写
date = "2026-10-02"            # 完成或合并的日期（完成、待真机必须写）
commit = "abc1234"             # 合并提交
old = ["P04"]                  # 旧编号（有的话）
stages = ["换台和面板的弹簧", "到头的橡皮筋", "拖面板不重建播放器", "把手和手势细节"]
done = 0                       # 做完了几个阶段
next = "按任务书从头做"         # 接着做的人从哪开始（暂停时必须写）
branch = "…"                   # 半成品所在的分支或工作区
note = "…"                     # 其他说明（受阻的原因等）
from = "GitHub issue #37"      # 来源：用户、issue、审查、上游提交（需求和反馈、借鉴来的任务写）
to = ["A07.13"]                # 去向：实现这个提议或反馈的任务（V 组写）
```

改完运行 `python3 tools/docs/docs.py`，[STATUS.md](STATUS.md)、[TASKS.md](TASKS.md)、[MAPPING.md](MAPPING.md) 和各组、各子分类的 README 会重新生成；门禁检查它们是不是最新。

### 3.2 状态

| 状态 | 意思 | 进度（没有阶段时） |
|---|---|---:|
| 未开始 | 登记了，还没动 | 0% |
| 设计中 | 在出方案或效果图 | 15% |
| 待确认 | 方案等用户确认 | 25% |
| 已确认 | 方案确认了，还没开发 | 35% |
| 开发中 | 在写代码 | 60% |
| 暂停 | 做到一半停下（额度、时间、等别的任务） | 30% |
| 受阻 | 外部原因做不了（例如平台要签名） | 50% |
| 待真机 | 代码已合并、门禁通过，还没在真机上逐项看 | 90% |
| 完成 | 真机验证过（`verify.md` 或记录里写了结果） | 100% |
| 不做 | 决定不做（写进 DECISIONS），不计进度 | — |

**“完成”必须有真机结果。** 只合并了代码的是“待真机”。

### 3.3 阶段

- 中、大规模的任务都要分阶段（2～6 个）。每个阶段：
  - 能单独合并进 master（门禁通过，不留半截功能，用户看不到坏掉的界面）；
  - 能单独验证（有测试或真机步骤）；
  - 约 1～3 小时的工作量。
- 阶段的顺序：先做用户最先感觉得到的，最后做细节。
- `done` 只在一个阶段合并后加一。

### 3.4 进度怎么算

- 有阶段的：`90% × 做完的阶段 / 阶段数`（完成和待真机按状态算）。
- 没有阶段的：按第 3.2 节的状态。
- 组、档位、全项目的进度：按规模加权平均（小 1、中 2、大 4，没写按中），“不做”不算。
- 新任务加进来，百分比会下降，这是正常的：进度条反映的是“已知的工作做了多少”。

## 4. 一个任务的步骤

| 步 | 做什么 | 产出 | 谁 |
|---|---|---|---|
| 1 | 登记：在 tasks.toml 加任务，写类型、规模、档位、阶段 | tasks.toml | 维护者 |
| 2 | 准备：读 3.x 和 4.x 的代码、相关任务的设计和记录、[DECISIONS.md](DECISIONS.md)、清点 | — | 执行者 |
| 3 | 设计：界面类出图和评审页（第 4.1 节），功能类写和 3.x 的对照，平台类录样本，性能类先测量 | README.md | 执行者；界面类由用户确认 |
| 4 | 任务书：照模板写清范围、要做的、不能做的、验收、测试、真机步骤、报告格式 | brief.md | 维护者 |
| 5 | 开发：在独立分支或工作区里按阶段做，每个阶段提交一次 | 代码、测试、record.md | 执行者 |
| 6 | 合并审查（第 8 节） | review.md | 维护者（可加另一个 AI 交叉审查） |
| 7 | 真机验证（第 10 节） | verify.md | 维护者 |
| 8 | 收尾：登记表改状态和阶段，运行 docs.py，门禁通过后推送 | — | 维护者 |

小任务可以省掉第 3、4 步，直接在登记表里写清要做什么。

### 4.1 界面任务的设计（从界面重构流程沿用）

1. **清点**：在 [inventory/UI.md](inventory/UI.md) 找到这个任务的逐项界面，在 [inventory/UI_FILES.md](inventory/UI_FILES.md) 找到文件，全部读完；在 README 写界面清点表（每个用户看得到的界面一行：从哪打开、形态、状态）。文字从代码取：`python3 tools/ui/strings.py <3.x 文件>`。
2. **还原 3.x**：`src/v3-<内容>.html`，用 `tools/ui/mock/kit/kit.css` 的组件，头里写尺寸 `<meta name="mock-size" content="393x852@3">`；生成 `python3 tools/ui/mock/render.py docs/<组>/<子分类>/<任务>/src/`。准备工作（每台机器一次）见 [tools/ui/mock/README.md](../tools/ui/mock/README.md)。
3. **新设计**：先对照 [specs/UI.md](specs/UI.md) 第 3 节的原则；出图顺序：Android 手机（竖屏、横屏 852×393、窄横屏 740×360）→ 宽屏 1280×800 → 电视 1920×1080 → 苹果平台差异；可点的控件加 `data-n` 出编号示意图（`render.py --annotate`），确认后补深色图（`--dark`）。
4. **评审页**：写 `page.json`（章节：说明、对比、3.x 的问题、改了什么、每个按钮怎么用、各客户端、需要你选的、性能要点），`python3 tools/ui/mock/page.py docs/<…>/page.json` 生成，发布成 claude.ai 私有页面给用户评审；每一版更新同一个地址。
5. **修改**：读评审结果，满意的不动，不满意的找原因，版本号加一重新发布；通用的教训写进 specs/UI.md 第 3 节。
6. **定稿**：`python3 tools/ui/export_compare.py ~/ref/design/compare/<任务>.html docs/<…>/page` 按章节导出；写好 README；登记表改成“已确认”。
- 用户授权“需要你选的按建议 A”时（DECISIONS D-003），定稿时在 README 注明。

## 5. 分阶段完成（额度或时间不够时）

**原则：随时可以停，停下的地方别人能接着做。** master 上只合并做完的阶段。

### 5.1 开工前

- 看 [STATUS.md](STATUS.md)，挑第一档的任务；同一组同时只开一个开发（避免冲突）。
- 估一下这次额度能做几个阶段，在登记表里写清阶段。

### 5.2 停下前必须做（哪怕只剩几分钟）

1. 把手上的改动提交到任务分支（不提交到 master），提交信息开头写任务编号，例如 `[A03.3] WIP: spring for the room swipe`。
2. 在 `record.md` 末尾写“停在哪”：做完了哪些阶段、正在做的阶段做到哪、已知问题、下一步。
3. 改登记表：状态（做到一半是“暂停”，阶段边界上停的保持“开发中”）、`done`、`next`、`branch`；运行 `python3 tools/docs/docs.py`。
4. 半成品要交给别的 AI 或换机器时，把分支推到 GitHub：`git push origin <分支>:wip/<任务编号>`（不推 master）。
5. 已完成的阶段照常走合并审查（第 8 节）进 master。

### 5.3 接着做

1. 在 [STATUS.md](STATUS.md) 的“暂停”表找到任务，读它的“停在哪、怎么接着做”。
2. 读 `brief.md` 和 `record.md` 的“停在哪”。
3. 检出分支（`wip/<任务编号>` 或登记的工作区），先合并最新的 master，再从下一个阶段开始。

## 6. 新功能和需求

新功能指 3.x 没有的功能（例如开播提醒、多账号）。小的改进（修 bug、补 3.x 的行为）直接在目标组登记任务，不走这一节。

1. **提议**：在 [V01 新功能提议](V-需求和反馈/V01-新功能提议/README.md) 登记一个任务（状态“未开始”，档位一般是第三档），写 `from`（谁提的：用户、issue、上游提交、审查）。
2. **评估**：在任务文件夹写 `README.md`（模板 [templates/feature.md](templates/feature.md)）：用户要解决什么、3.x 和上游怎么做、对其他功能的影响、要改哪些组、规模；有界面的出效果图和评审页（第 4.1 节）。状态改成“设计中”或“待确认”。
3. **决定**：用户确认后，状态改“已确认”，在 [DECISIONS.md](DECISIONS.md) 记一条；在目标组登记实现任务（界面在 A 组、功能在对应组），把它们的编号写进提议的 `to`。决定不做的，状态改“不做”，原因写进 DECISIONS，移到 V04 的说明里。
4. **实现**：照第 4 节做目标组的任务；提议任务在实现任务都完成后改“完成”。

**用户反馈和 issue**：在 [V02](V-需求和反馈/V02-用户反馈和issue/README.md) 登记（`from` 写来源和链接），复现后写根因线索，修复任务开在目标组并写进 `to`；修好、发布后回复 issue 并关闭。**审查和调研**的报告放在 V03 的任务文件夹里，发现的问题同样开到目标组。

## 7. 交给其他 AI

任何能读写代码的 AI（Claude、Codex、Gemini 等）都可以做任务，条件是：

- **任务书自包含**：不依赖聊天记录。brief.md 写清背景、要读的文件、可以改的目录、不能做的事、逐条要做的、验收标准、测试、真机步骤、报告格式（模板 [templates/brief.md](templates/brief.md)）。
- **给 AI 的提示词**（复制后把编号换掉）：

```text
你在 GitHub 仓库 wzgrx/pure_live 上工作。先完整读 AGENTS.md、docs/PROCESS.md，
再读任务书 docs/<组>/<子分类>/<任务>/brief.md 和它列出的文件，严格照做。
从最新的 master 新建分支 ai/<任务编号>，只提交到这个分支，提交信息以 [<任务编号>] 开头（英文）。
不要推送到 master，不要改版本号、assets/version.json、assets/releases.json，不要写入任何密钥、Cookie、账号。
按任务书的阶段做；每做完一个阶段提交一次。做不完时按 docs/PROCESS.md 第 5.2 节停下。
完成后写 record.md，推送分支，用中文报告：每条做到没有、根因、测试结果、要在真机上看的、需要维护者决定的。
```

- **分工**：设计、实现、审查可以交给不同的 AI；同一组的任务同时只交给一个执行者。
- **不给的东西**：签名文件、密钥、Cookie、用户的 3.x 数据、手机的控制权（真机验证由维护者做）。
- 其他 AI 的产出和自己做的一样，走第 8 节的合并审查。

## 8. 合并审查

**谁审**：维护者。重要的任务可以再请一个没参与开发的 AI 交叉审查：把 brief.md、record.md 和 `git diff master...<分支>` 给它，让它按下面的清单逐条回答。

**清单**（写进 review.md，模板 [templates/review.md](templates/review.md)）：

1. **对照任务书**：每一条做到没有；偏差有没有理由。
2. **根因**：修 bug 的有改之前会失败的测试；记录写了根因（文件:行）。
3. **改动范围**：只改了任务书允许的目录；没有多余改动、调试代码、注释掉的代码；没有密钥和真实数据。
4. **规则**：用户看得到的文字走翻译（zh、en 都有，按键名排序）；颜色和图标来自 `live_ui`；3.x 的设置键名和含义不变；测试里的定时器至少 1 秒；测试不访问真实平台。
5. **门禁**：`bash tools/gate/gate.sh --all` 通过，日志里有 `gate: passed`。**不要在门禁运行时在同一份代码里构建正式包**（会互相改生成的文件）。
6. **真机**：按 verify.md 在 K90 上看（第 10 节）；看不了的写明原因，状态停在“待真机”。
7. **文档**：record.md 写完；登记表的状态、阶段、日期、提交改好；运行了 docs.py。
8. **合并**：`git merge --no-ff <分支>`；冲突时两边的改动都保留，再跑相关测试；推送；删掉工作区和分支。

**不通过**：在 review.md 写清意见，退回同一个分支修改，修改后重新审查。

## 9. 上游借鉴

上游是 3.x 的作者 liuchuancong 的五个仓库：手机版 [pure_live](https://github.com/liuchuancong/pure_live)（在 v3.2.11 上接着开发）、电视版 pure_live_TV、播放核心 media_core、弹幕引擎 flame_barrage、flv_lzc（清单和许可证见 [specs/ENGINEERING.md](specs/ENGINEERING.md) 第 5 节）。

1. **每周一次**（[W01](W-上游借鉴/W01-定期对照/README.md)）：拉取（手机版用主仓库的远程 `upstream`：`git fetch --no-tags upstream master`，看 `git log <上次看到的提交>..upstream/master`；其余在 `~/ref/` 下 `git pull`）。
2. **逐条对照**：只看修复和新功能；每一条先在 4.x 的代码里找对应位置（文件:行），判断是“4.x 也有这个问题”“可以借鉴”“已经有”“不适用”。
3. **记录**：在 W01 登记这次对照的任务，`README.md` 写对照表和看到的提交范围（下次从这里接着看）。
4. **登记任务**：4.x 也有的问题开到目标组（`from` 写上游仓库和提交）；可借鉴的新功能先进 V01 提议（第 6 节）。
5. **借鉴代码**：AGPL-3.0 的注明来源仓库和提交，MIT 的保留版权声明；不照搬架构（例如上游把播放换成 media_core，4.x 有自己的播放层），只借鉴修复的思路和行为。

## 10. 真机验证

## 11. 发布

1. **版本号**：换安装包就必须改版本号（3.x 和 4.x 的应用内更新只比较版本号）；构建号同时加一。Android 的 versionCode = ABI 编号 × 1000 + 构建号（v7a 6、arm64 7、x86_64 9）。
2. 改 `apps/pure_live/pubspec.yaml` 和 `features/version/app_version.dart`，写发布说明（[Y03](Y-发布和运营/Y03-发布说明和README/README.md) 的 `releases/`）。
3. 构建：`flutter build apk --release --split-per-abi`（门禁不在跑的时候）；签名用维护者调试密钥（和 3.x 同一证书，见 D-006）。
4. 检查：包名、versionCode、签名证书、通知图标资源、16 KB 对齐（命令见 [Y01](Y-发布和运营/Y01-版本签名和发布/README.md) 的记录）。
5. 用同一提交的测试包在 K90 上冒烟。
6. 打标签、建发布页、上传安装包和 SHA256SUMS。
7. **最后**改 `assets/version.json` 和 `assets/releases.json`（3.x 从 master 读它们检查更新），门禁通过后推送。

## 13. 文档规范和版本

- **只手改**：tasks.toml、本文件、README、PLAN、DECISIONS、GLOSSARY、specs/、inventory/ 的说明、templates/、任务文件夹里的文件。**生成的文件不手改**（文件开头有说明）。
- **图片**：只提交定稿的图；宽不超过 1080，单张不超过 300 KB；被否掉的版本不进仓库；本机中间文件不进仓库。
- **链接**用相对路径；代码注释里提到文档时写 `docs/` 开头的完整路径。门禁会检查两者都能找到。
- **旧编号**只出现在 [MAPPING.md](MAPPING.md) 和登记表的 `old` 里；新写的文档一律用新编号。
- **决定**写进 [DECISIONS.md](DECISIONS.md)（新编号 D-xxx），任务里引用编号；改主意时加一条新的，写明取代哪条。
- **文档版本**：分组、编号或目录结构变了升大版本（v1 → v2），加组或子分类、改做法里的规则升小版本（v1 → v1.1）；写进 [CHANGELOG.md](CHANGELOG.md)，推送后打标签 `docs-v1` 这样的。日常改任务状态不算版本变化。

## 14. 规则汇总

- 用户看得到的文字一律中文；代码、注释、提交信息用英文。
- 3.x 是功能基线；先找根因再改；各处一致。
- 推送前门禁必须通过（文档改动也一样）；不强推（例外见 D-007）。
- 只在本机构建；签名文件和密钥不进 git；不把真实 Cookie、账号、IP 写进仓库（样本要脱敏）。
- 版本号只在发布时改；`assets/version.json`、`assets/releases.json` 必须留在 master。
- 不碰用户的 3.x 安装和数据。
- 测试里的定时器至少 1 秒；测试不访问真实平台。
- 3.x 的设置键名和含义不变，新设置只加不改，写清默认值。
