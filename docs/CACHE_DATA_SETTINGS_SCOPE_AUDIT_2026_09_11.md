## 修改前复现与代码审查

修改前页面在固定矩阵稳定触发 `ListTile` 断言：缓存数值与刷新图标作为自然宽尾部，占满 256 像素卡片正文宽度，
标题区失去布局空间。继续审查操作语义和目录调用后确认更严重的范围错误：

1. 页面把“清空本地所有缓存”映射到 `RECORDS`、`DOWNLOADS`、`IPTV_CACHE` 和图片目录，并对这些根目录执行递归删除。
2. `RECORDS` 是默认录制成品目录；`DOWNLOADS` 持有已下载字体和升级包；`IPTV_CACHE` 持有播放列表数据库、用户导入、
   EPG 与同步状态。三者都是可感知的持久用户数据，不属于临时缓存。
3. 页面误用录制中心的 `clear_all_cache` / `confirm_clear_cache` 文案，所以标题显示“清空录制文件目录”，说明却又声称
   “清空本地所有缓存”，与实际混合删除范围互相矛盾。
4. 任一目录删除失败后控制器仍把大小强制写成 0，页面仍显示成功；重复缩略图刷新还会让后一次调用提前返回，产生过早成功提示。

## 修订

- 新增单一 `CacheStoragePolicy`：本页只管理 `IMAGE_CACHE`、`EMOJI_CACHE` 与编码图片缓存；录制、下载、字体和 IPTV
  数据不参与大小统计，也不进入删除列表。
- 缓存大小扫描继续在后台 isolate 执行，根路径先去重；清空后重新实测剩余大小，不再把失败结果伪装成 0。
- 清空、缩略图刷新和大小扫描共享进行中任务；重复清空/刷新等待同一 Future，清空会观察先前扫描失败后继续本次独立操作，
  定时刷新异常也被完整观察。
- 清空返回 `CacheClearResult`。路径解析、后端清理或单目录清理失败会显示剩余缓存和失败状态；初始扫描异常被观察，
  手动扫描及缩略图刷新另有可见错误反馈。
- 页面使用独立双语缓存文案，明确列出保留的数据类型；忙碌期间禁用并发入口并显示进度。
- 缓存大小尾部在窄屏堆叠且内部可换行，确认弹窗整体可滚动，320×480 / 3.0 倍英文下所有入口和操作均可点击。
- 录制中心仍使用独立 `CacheService` 与 Pure Live 专用录制目录，原录制文案和保护规则保持不变。
