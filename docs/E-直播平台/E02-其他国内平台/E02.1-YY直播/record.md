## 3.x 的冻结输出从哪来

其他平台的 `expected.json` 是用 3.x 自己的测试工具（`legacy/test/fixtures_expected`）回放样本得到的。YY 的样本录制时 3.x 已经不能构建（归档 ADR 0016），所以没有 `expected.json`。

这次补上：`fixtures/yy/legacy_expected.dart` 是 `legacy/lib/core/site/yy/yy_site.dart` 解析部分的逐行转写，只把 `HttpClient` 换成录下的响应，并按 3.x 的 Dio 那样解码（JSON 类型变成对象，其余是文本，再交给 `YYSite.decode`）。房间和分区用 3.x 的 `toJson`，按 3.x 的 `roomProjection` 投影；画质名称用 3.x 的 `LiveQualityLabel`。每个 `expected.json` 的 `generator` 都写明了来源。重新生成：

```bash
dart run fixtures/yy/legacy_expected.dart
```

3.x 从不请求房间页，`S05-page-*` 没有 3.x 输出。

## 做法

- **接口和输出沿用 v3**：`LiveSite` 和 `LiveRoom` 等模型，3.x 的 JSON 不变。分区的 `shortName` 仍是 3.x 的格式 `{"moduleId":313,"biz":"dance","subBiz":"idx"}`，3.x 存下的关注分区能直接用。
- **请求按 v3**：API 请求头就是 3.x 的 `getHeaders`（Chrome 128、`Origin`、`Sec-Fetch-*`），用户配置了 Cookie 就带上；没有游客会话。stream-manager 的正文字段、SDK 版本、`text/plain` 类型都照 3.x。
- **取流保持 3.x 用户实际得到的样子**：先走匿名移动 HLS（1200、4000 两档，按实际视频流去重，画质叫“流畅 · 360p”“高清 · 720p”）。3.x 的代码本想先问 stream-manager，但因为问题 1 从没成功过，用户拿到的一直是移动 HLS。修好的 stream-manager（FLV）只在移动 HLS 没有流或失败时顶上。
- **房间号保持请求时的号码**。频道号 `sid`、`ssid` 放在 `YyRoomData`；短号（`asid`）在进房时经房间页换成规范频道号，只用于详情、取流和弹幕。
- **房间页只在进房时读**（`getRoomDetail`）。关注刷新、录制检查和开播状态查询只请求 `liveInfoDetail`，与 3.x 的请求量相同。（T02.U 的 6-8 改为未开播时每个房间号读一次房间页，见文末“升级落地（T02.U）”。）
- 解析写成纯函数（`YyApi`），错误有类型；站点类只管请求。

## 与 v3 的有意差异

| # | 差异 | 原因 |
|---|---|---|
| 1 | 移动 HLS 没有流或失败时，由修好的 stream-manager 顶上：画质是 stream-manager 的（“高清”“流畅”），线路是 FLV，带有效期；替移动画质取流时按同档请求（4000 → gear 2，1200 → gear 1），不确认画质 | 见问题 1。3.x 在这种情况下什么也拿不到（stream-manager 的请求是坏的）。默认结果仍是 3.x 的移动 HLS 画质和线路 |
| 2 | stream-manager 的画质不列没有网页流的档位；实际档位按应答报告 | 见问题 2。选不了的档位列出来只会误导 |
| 3 | 进房时不存在的房间抛 `NotFound` | 见问题 3 |
| 4 | 进房时短号房间按规范频道号查询和取流，房间号不变；之后的刷新直接用记住的频道号 | 见问题 4 |
| 5 | 进房时未开播的房间带主播名、头像、频道标题、分区和链接（多一个房间页请求） | 3.x 只给房间号和状态。房间页同时用来区分不存在和短号。关注刷新不读房间页：v4 的关注合并（`LiveRoom.mergeFrom`，E05.1）遇到空的名字、头像会保留已存的值，刷新结果不带这些字段也不会清空卡片 |
| 6 | 搜索卡片的分区是 `category` | 见问题 9 |
| 7 | 图片统一 https，并经通用的 `normalizeImageUrl` 规范化；`thumb2` 缺失时用 `thumb` | 见问题 10 |
| 8 | 出错抛类型化错误 | 见问题 5、12。`resultCode` 不为 0、搜索 `status` 不为 0 是 `ApiChanged`；HTTP 429 是 `RateLimited`；5xx 和传输错误是 `NetworkFailure` |
| 9 | 线路自带请求头、格式、线路编号和有效期 | 请求头与 3.x 的 `PlaybackHeaderResolver` 一致：`Origin`、`Referer: https://www.yy.com/`、Chrome 140，有用户 Cookie 才带。移动 HLS 的 `t` 是签发时间，不算租期（与 3.x 一样没有续期信息）；FLV（只在兜底时出现）的 `t` 是签名到期时间（签发后 600 秒），提前 1 分钟续期，到期不断开已建立的连接 |
| 10 | 分类：分区页并发请求，失败只影响这个分区；没有参数的分区打开时读分区页；`moduleId: 0` 的分区不请求直接为空 | 见问题 6、7、8。服务端对这类分区答 `data: null`，3.x 显示的也是空列表 |
| 11 | 空关键词不请求；没有频道号的卡片跳过 | 见问题 13 |
| 12 | 链接也认手机页 `wap.yy.com/mobileweb/{sid}/{ssid}`；`0` 和前导零不是房间 | 手机页的格式来自 3.x 自己的移动 HLS Referer |

## 保持 v3 行为、没有采用归档 v4 或上游做法的地方

- **移动 HLS 优先**，画质名称和线路与 3.x 用户实际看到的一致（“高清 · 720p”“流畅 · 360p”，HLS）。v4 以 stream-manager（FLV）为主，移动 HLS 兜底。（T02.U 的 6-1 加了 `flvFirst` 开关，默认仍是移动 HLS 优先，G 之后打开。）
- **关注刷新、录制检查和开播状态查询只请求 `liveInfoDetail`**，与 3.x 的请求量相同；未开播就是 3.x 的“只有房间号和状态”。v4 每次都读房间页。（T02.U 的 6-8 改为每个房间号第一次未开播时读一次房间页。）
- **推荐卡片和详情的分区仍是“分区页学到的名字，否则原始 `biz`”**（推荐都是 `other`）。v4 在学不到时留空。（T02.U 的 6-3 已改为留空。）
- **搜索卡片的标题仍是 `channelName`（“XX 正在直播”）**。v4 去掉了“ 正在直播”后缀。（T02.U 的 6-2 已去掉，列表和详情的同一默认标题也去掉。）
- **一次 stream-manager 请求只给一条线路**（3.x 的 `parsePlayUrls`）。v4 会按 `stream_line_list` 再请求其他 `line_seq`，凑出两条 CDN 线路。（T02.U 的 6-4 已补上第二条线路。）
- **取分类时照旧读每个分区页**，分区带着 `shortName` 返回，关注分区和 3.x 通用。v4 改为打开分区时才读（取分类 4 个请求而不是 22 个）。（T02.U 的 6-5 已改为打开时读。）
- **移动 HLS 照旧请求 1200 和 4000 两档**。v4 只请求 1200。
- **媒体请求照旧带用户 Cookie**（3.x 的 `PlaybackHeaderResolver`）。v4 不带。
- **主播搜索照旧用 `t=1`**，直播状态照旧取 `liveOn`（规格实测它不可靠）。v4 不做主播搜索。（T02.U 的 6-6 核实后保留 `liveOn`：它是主播本人的状态，见文末。）
- **未开播的房间没有弹幕参数**，和 3.x 一样。（T02.U 的 6-7 已加上。）
- **stream-manager 正文里的浏览器照旧是 Chrome 128、1366×768**。录制样本用的是 v4 的 Chrome 140、1920×1080，回放时这三个字段不参与匹配。
- **显示名仍是“YY 直播”**。

## 后续升级候选

以下会改变用户看到的内容，按规则不在本模块做，列出由用户决定：

1. **FLV 优先**：先问 stream-manager，移动 HLS 兜底（3.x 代码本来的设计，发布说明写的是“YY 保留真实 gear 并在匿名 StreamManager 失败时回退实际可用移动 HLS”）。
   - 3.x 没做到的根因：见问题 1。正文以 Map 交给 Dio 又声明 `text/plain`，被表单编码，服务器一律答 HTTP 500，所以 3.x 用户一直在用移动 HLS。请求本身已在本模块修好。
   - 名称：画质会从“高清 · 720p”“流畅 · 360p”变成“高清”“流畅”（两者是同一组流：gear 2 = 4000 档，gear 1 = 1200 档）。
   - 延迟：FLV 比 HLS 低。
   - 续签：FLV 地址签名 10 分钟有效。线路已带 `PlayLease`，但播放器按它续签要到 G 才有，应在 G 之后再切换。
2. 搜索卡片标题去掉“ 正在直播”后缀（v4 做法）。
3. 推荐卡片和详情的分区：学不到名字时留空，或把 `other` 隐藏，而不是显示原始 `biz`。
4. FLV 每个画质补齐第二条 CDN 线路（按 `line_seq` 再请求一次；实测线路 10 是 `tx-flv-web`，线路 14 是 `ks-flv-web`）。
5. 取分类时不再读 18 个分区页，打开分区时再读（`shortName` 仍能兼容 3.x 存下的关注分区）。
6. 主播搜索的直播状态不可靠：改用房间搜索的结果，或不显示状态。
7. 未开播的房间也给弹幕参数（房间页有 `sid`、`ssid`）。
8. 关注刷新也区分不存在的房间和短号（要多读一次房间页）。

## 测试

#### 6-6 的核实

- 候选的依据是规格里的一条实测：22490906 当时在播，`t=1` 却给 `liveOn: "0"`。
- 这是公会的共用频道：录制时在 22490906 表演的是“燃舞蹈-福星”（uid 107923068，S05-detail-live），而主播搜索列在 22490906 下的是“燃舞蹈-Chisato”（uid 411865223，S04-search-anchors）。`liveOn` 说的是这位主播本人没在播，并没有错。
- 2026-09-29 用“燃舞蹈”“舞蹈”各两页主播搜索（60 个频道）逐个对照 `liveInfoDetail`：59 个一致；唯一不一致的仍是 22490906，当时在表演的是另一位主播（uid 2211874788）。另用推荐页里 7 个在播主播的名字搜索：6 个（青宝宝、乔三、猫酱、Kasy、柠小檬、刀疤哥）在结果里，`liveOn` 都是 1，同名的其他人都是 0；第 7 个“至尊宝”同名的人太多，第一页没有他。
- 候选的两个办法都更差：
  - 改用房间搜索（`t=120`）多一个请求，而且会漏：“燃舞蹈/小兮”在播（`liveOn` 1、详情在播），但“舞蹈”的房间搜索前两页里没有她；
  - `LiveAnchorItem.liveStatus` 是布尔值，“不显示状态”只能全标未开播，把 59 个对的也弄错。
- 所以保留 `liveOn`，只改了代码注释和测试（测试断言了共用频道的这个情况）。

### 画质 id 对照、设置项、身份迁移（给 J02.1、M13）

- **画质 id**：默认（`flvFirst: false`）不变，仍是 `mobile-hls:4000`（高清 · 720p）、`mobile-hls:1200`（流畅 · 360p）。打开 `flvFirst` 后画质来自 stream-manager，id 是档位号：

  | 旧 id | 旧名称 | 新 id | 新名称 |
  |---|---|---|---|
  | `mobile-hls:4000` | 高清 · 720p（或 1080p） | 该频道的最高档：`4`（有蓝光时）或 `2` | 蓝光或高清 |
  | `mobile-hls:1200` | 流畅 · 360p | 该频道的最低档，实测都是 `1` | 流畅 |

  最高档随频道变，所以对照是方法而不是常量：`YyApi.flvQualityId(旧 id, 该房间的画质列表)`，4000 取第一档（最好的），1200 取最后一档；别的 id 原样返回。依据：移动 HLS 4000 给的流就是 stream-manager 最高档的 `…_0_0_0`，1200 给的是最低档（2026-09-29 探测 3 个频道）。
- 3.x 只存全局的画质偏好名（原画、蓝光8M、蓝光4M、超清、流畅），没有存 YY 的画质 id，所以迁移 3.x 数据用不到这张表；它用于 v4 自己记住的画质（如果 G、M13 做了按房间记住画质）在打开 `flvFirst` 时的换算。
- **设置项**：没有用户设置。`YySite.flvFirst`（布尔，默认 `false`）是给 G 的开关，不进设置页：含义是“画质先取 stream-manager（FLV），移动 HLS 兜底”。G 在播放器能按 `PlayLease` 续签 FLV 地址、真机验证后，把默认值改成 `true`（或由组装适配器的地方传入）。
- **身份**：不变，房间号仍是请求时的频道号或短号。YY 没有按主播关注的条目。3.x 用短号存的关注不用迁移：6-8 以后刷新时自动换成规范频道去查，身份仍是短号。
