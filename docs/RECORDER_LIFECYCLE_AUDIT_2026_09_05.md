# 录制调度与 MP4 收尾生命周期审查

## 冻结与归属

- 本批基线：`58a528a7`，不合并上游。修改只涉及共享录制调度和 MP4 收尾，不改变播放器、
  竖屏比例、直播质量选择、平台签名或录制分段格式。
- 调度先调用 runner、后登记 running task 的结构来自上游 `7a2d18abf`；本分支
  `cf35dcf95` 增加异常收尾后仍保留该顺序。同步异常路径会先执行 remove，再登记一个
  已结束的任务，导致容量被永久占用。归属为共有结构缺陷，不归因于平台服务器。
- MP4 的 `await _ffmpeg.start` 后才启动 terminal timeout，及准备中取消缺少启动前检查，
  来自本分支 `233d858de` / `cf35dcf95` 的实现，当前只读上游 `c6c9bd70` 也存在相同逻辑。
  原始来源为本分支；上游当前包含该代码不代表此缺陷已解决。
- 本机锁定插件 `ffmpeg_kit_extended_flutter 0.6.2` 的 `FFmpegSession.executeAsync`
  明确等待原生执行结束；其 `sessionCompleter` 在最终回调清理后完成。`FFmpegService.start`
  继续等待该 Future，所以它是执行生命周期，不是启动确认。

## 首个错误状态与红测

1. 同步抛错：runner 的 finally 早于 `_runningTasks[id]` 写入，录制中心会留下空转的运行名额。
2. 超时边界：若原生处理始终不结束，程序一直停在 `await start`，后面的 timeout 从未开始计时。
3. 准备中取消：取消时还没有 native task ID；标志虽然设置了，目录/清单准备完成后仍启动原生处理。
4. 对超时后的补充约束：发出 stop 不等于原生已退出，清理临时文件和释放任务/目录所有权须等待实际结束。

`20260905T062858736Z-quality-focused.json`：四个新增断言均在旧业务顺序上失败，
不是编译失败或真实平台故障。测试只添加依赖注入与等价的可配置时限，未先修复被测逻辑。
此前 `062653525Z` / `062736620Z` 两次 gate 停在新文件格式检查，未运行产品断言，单独保留。

## 修复方案

- 调度器先登记带 completion fence 的任务，再异步进入 runner。立即取消可以阻止打开原生资源；
  同步/异步异常都从同一 finally 释放本任务所有权，旧完成也不删除新任务。
- 原生执行 Future 与终止事件由一个总体时限包住；仍使用原有按文件大小/时长计算的 30～3600 秒
  时限，没有通过调大默认值掩盖错误顺序。
- 一次合并有独立 operation，准备阶段在异步边界检查取消。文件检查后、原子 rename 前再检查一次；
  rename 开始是提交点，已开始的完整文件提交继续收尾，避免半提交。
- 超时先请求原生停止。若停止尚未完成，调用方获得失败，但保留该任务的排他所有权、事件监听、
  临时清单/文件；实际 native Future 结束后才清理。迟到的 startAck 也会观察取消标志并停止。
- 合并自身持有独立的引用计数目录保护；录制外层生命周期结束或用户清缓存不会删除仍在写入的文件。
  成功先提交 MP4，再删除这一次的 TS；失败/取消保留全部源分片。
- 不同任务、用户停止、重复启动、前置取消、迟到启动、自然成功、原生失败、延迟停止与清缓存分别验收。

## 资料核对

- [Dart Future.timeout](https://api.dart.dev/dart-async/Future/timeout.html)：只限制等待，源 Future 可以在之后完成，
  所以 stop 请求、真实完成和文件释放必须分别建模。
- [FFmpegKit Extended](https://pub.dev/documentation/ffmpeg_kit_extended_flutter/latest/)：公开 API 文档作为入口，
  本次具体 Future 合同以本机锁定的 0.6.2 源码为准，不用网页 latest 替代已安装依赖。
