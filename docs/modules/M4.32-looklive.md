## 做法

- **接口和输出沿用 v3**：`LiveSite` 和 v3 实现过的全部可选能力——目录分页（`LiveSiteDirectoryPager`）、目录说明（`LiveDirectoryNotice`，键 `looklive_directory_scope`）、可取消的搜索（`LiveCancellableSearch`）、关注刷新（`LiveSiteRoomRefresher`）、录制详情（`LiveSiteRecordRoomResolver`）、取流（`LivePlayUrlResolver`）、恢复（`LivePlayRecoveryResolver`），外加 `LiveSiteLinks`。3.x 的 JSON 不变。
- **请求照 v3**：
  - 每个请求都是 `POST https://api.look.163.com/weapi/…`，表单是网易网页版的 `weapi` 信封（下面“weapi 信封”），以 `looklive` 的名义发出（代理路由由应用按平台注入），**不跟随跳转**，不带 Cookie（v3 的 LOOK 没有账号）；
  - 请求头是 v3 的 `requestHeaders`：`Accept: application/json, text/plain, */*`、`Origin: https://look.163.com`、`Referer: https://look.163.com/`、`User-Agent: Mozilla/5.0`，加上 dio 的 `Content-Type: application/x-www-form-urlencoded`；表单按 v3 的 `Uri(queryParameters: …).query` 编码，与录下的请求逐字节相同；
  - 视频推荐 `/weapi/livestream/homepage/recommend`、声音推荐 `/weapi/livestream/listen/homepage/recommend/list`，载荷 `{"offset":<(页-1)×20>,"limit":20}`；房间 `/weapi/livestream/room/get/v3`，载荷 `{"liveRoomNo":"<房间号>"}`；
  - 每个请求 20 秒时限（v3 的 `deadline`），超时是 `NetworkFailure`，调用方取消原样抛出取消。
- **weapi 信封**：`params` 是紧凑 JSON 先用网页 nonce、再用固定密钥做两次 AES-128-CBC（PKCS#7，IV `0102030405060708`）再 Base64；`encSecKey` 是倒序密钥按十六进制读成整数后 `^65537 mod` 网页公钥模数，补足 256 位——密钥固定，所以是常量。v3 用 PointyCastle 加密，这里用 `live_core` 已有的 `AesCbc`（`aes.dart`），测试核对了 v3 冻结的 7 个载荷的 `params` 和录下的请求体。
- **目录照 v3**：
  - 一个分类 `LOOK 直播`（id `looklive`），两个分区“视频直播”（`official`/`video`）、“语音直播”（`official`/`audio`），只在第 1 页给出，按每页条数截取（条数 1 只有视频直播），不发请求；
  - 分区翻页用平台原生的 `hasMore`；推荐和不带分区的目录同时请求两个列表的同一页，视频在前、按房间号去重，任一列表还有下一页就继续；页码小于 1 为空、不发请求；超过 10000 是调用方错误（v3 的 `schema`），也不发请求；
  - 列表项只取 `type` 为 "1"、有 `liveData` 的；另一类的卡片跳过（声音列表里插着视频卡片）；同一房间只留一张，位置是第一次出现处、内容是最后一张（v3）；项不是对象、`liveType` 不是 1 或 2、卡片不合 v3 的检查（房间号、主播账号、场次号必需，热度和在线数为负或不是整数，拉流地址不在白名单）、超过 100 项、`hasMore` 不是布尔值，整页 `ApiChanged`（v3 的检查）；
  - **列表到头时平台回答 `itemList: null`、`hasMore: false`（S04-video-p2），现在当作空的最后一页**（问题 1）。
- **卡片照 v3**：房间号 `userInfo.liveRoomNo`；`userId` 是主播账号；标题 `liveTitle`、主播名 `nickname`（只去首尾空白）；头像 `avatarUrl`，没有时用封面；封面 `liveCoverUrl`；图片只收 http(s)、有主机、没有用户信息、端口和片段的地址，并改成 https；分区按 `liveType` 写“视频直播”或“语音直播”；`onlineNumber` 是在线人数、`popularity` 是热度，两者分开存，`watching` 和口径优先在线人数；状态直播；公告是 3.x 的聊天说明；`link` 是 `https://look.163.com/live?id=<房间号>`；房间带 v3 的媒体请求头 `httpHeaders`（3.x 的 JSON 里有）。
- **搜索照 v3**：只有第 1 页；房间号（2～18 位数字）或房间链接直接查房间接口（平台说不存在是没有结果，其他错误照样报出）；其他关键词请求两个列表的第 1 页，按房间号、主播名、标题筛选（不区分大小写），取前 `pageSize` 条。空白、页码不是 1、条数小于 1 或超过 100 给空、不发请求。别的网站的链接现在直接给空（问题 15）。
- **房间照 v3**：
  - 房间号就是请求的号码（v3：回答里的 `anchor.liveRoomNo` 必须等于它，否则 `ApiChanged`）；传入房间链接也按链接里的号码（v3），不是房间号的输入 `NotFound`，不发请求；
  - 状态按 `liveStatus`：1 直播，0 和 -1 未开播，-10 受限（显示为未知，公告加一行“受私密房或账号访问条件限制”），其他值未知；分区按 `roomInfo.liveType`（1 或 2，否则 `ApiChanged`）；主播账号和场次号必需；
  - 深度照 v3：刷新、开播状态、按号搜索只读房间信息，不看拉流地址；进房和录制在直播中时读拉流地址，房间带 `LookLiveRoom`（含地址，不存进 JSON）；三种深度都是 1 个请求；
  - 房间接口没有观众数。v3 用本次运行中见过的**同一场次**（`liveId` 与 `roomInfo.id` 相同）的列表卡片补上热度和在线数，也补空的名字和图片；直播中而回答没有地址（`liveStreamType` 不是 50）时沿用那张卡片的地址（`enrich`）。
- **开播状态**：一个请求。直播为真，未开播为假；受限报 `NeedsLogin`，未知状态报 `ApiChanged`，都不当作未开播（问题 7）。
- **画质和线路照 v3**：每个地址一档，`HLS 原始线路`（id `hls:source`，排序 2）在前，`FLV 原始线路`（id `flv:source`，排序 1）在后，不发请求。取流直接读进房时的地址，不发请求，确认的画质就是请求的；恢复重新请求房间接口（1 个请求，v3）。每档一条线路：格式 HLS 或 FLV，线路编号是主机名（`pull0583d674.live.126.net`）；**不带请求头**（v3 的播放器没有 LOOK 分支，发的是自己的默认值）；地址没有签名和过期参数（`?netease=<主机>` 不是签名），没有 `PlayLease`；编码不写（接口不说，声音直播只有音频）。
- **不能播时在取流时报错**：列表卡片、刷新或搜索得到的房间（没有进房数据）、明确未开播、直播中没有地址（包括仅限 App）的房间报 `StreamUnavailable`，受限报 `NeedsLogin`，都不发请求；别的平台的房间、别的画质是调用方错误（`ArgumentError`），恢复时也在请求之前报。
- **没有 Cookie、登录和弹幕**：v3 的 LOOK 全部匿名，弹幕是 `EmptyDanmaku`，所以不注入 `CookieVault`，也不输出弹幕参数。
- **缓存有上限**：见过的房间最多记 2000 个，超出时丢最早的（问题 11）。

## 样本与 v3 的冻结输出

归档没有 LOOK 直播的 `expected.json`（归档的旧版对照工具只做了前五个平台，规格 §11 也写明没有旧版期望值）。本模块用 `fixtures/looklive/legacy_expected.dart` 生成，做法同京东直播、BIGO：

- 把 v3 的 `LookLiveLink`、`LookLiveApi`、`LookLiveSite` 原样搬进一个 Dart 程序（由一个只做下列改动的脚本拼接，每处改动都校验恰好生效一次）：去掉导入；只在网络路径上的 `_defaultRequest`、`_readBody` 不搬，传输因此必填；去掉 `extends LiveSite implements …`、`@override` 和弹幕 getter；站点的默认 api 必填。`i18n` 返回 3.x `zh.json` 的文字；Dio 的 CancelToken 是桩；v3 的 `LiveRoom` 等模型只搬用到的部分（与京东直播的相同，`toJson` 里有 v3 的 `HttpHeaderPolicy.normalize`）。
- v3 本来就把传输做成可注入的函数（`LookLiveRequest`），所以只换了它：解开 `weapi` 表单的两层 AES，按路径和明文载荷读样本；请求记成 `POST <地址> <明文载荷>`。没有样本的请求抛 StateError，v3 的 `_post` 把它记为 `transport`，程序另记在 `unmatched` 里。
- `LookLiveApi` 的加密用 PointyCastle，工作区不依赖它，所以用临时的包配置运行（v3 解析到的 4.0.0，文件头有命令）。
- 合成的回答都标明了：对录下的回答做合成修改，记下 v3 的结果（`variants`：列表 85 种、房间 39 种）；空的视频第 2 页（对照修好问题 1 之后的合并结果）；房间号 2162、99999999 用 `S03-room-notfound` 的正文作答（按号搜索和“不存在”的各种深度）；房间号 21623632 用 `S03-room-video` 作答（回答的房间号不对）。

**脱敏**：归档规则替换了响应的 `Set-Cookie: NMTID`（匿名 Cookie），但漏了响应头 `x-from-src`——网易网关回显的请求方出口 IP（6 个归档样本都是同一个真实地址）。已换成文档地址 `203.0.113.7`（RFC 5737，同 YouTube 的做法），记在各自 `meta.json` 的 `scrubbed`（规则 `ip`）。补录的 3 个样本用同样的规则：`NMTID` 换成同形的合成值，`x-from-src` 换成 `203.0.113.7`，原值还能找到就拒绝写入。另外查过访客编号、设备编号、token、Cookie 值：请求没有 Cookie，表单是公开常量加密的公开载荷；回答只有主播的公开信息；`x-traceid`、`x-traceid-v2`、`gw-thread` 是单次请求的追踪号，保留。`raw.sha256` 仍是原始正文的摘要。

## 与 v3 的有意差异

| # | 差异 | 原因 |
|---|---|---|
| 1 | 列表回答 `itemList: null`、`hasMore: false` 是空的最后一页（v3 `schema`）；合并目录和推荐因此能翻到第 2 页以后（声音列表），视频列表为空时第 1 页和搜索也不再失败 | 问题 1。v3 在这里只显示错误，没有别的内容可保留；修好后出现的是 v3 的合并逻辑本来就要给出的声音列表后续页，与 v3 在“视频第 2 页为空列表”时的输出相同。请求数不变 |
| 2 | 出错抛类型化错误；调用方错误是 `ArgumentError`，不是房间号是 `NotFound`，都不发请求；1 位、19 位房间号的卡片是 `ApiChanged`（v3 `FormatException`） | 问题 2、6 |
| 3 | 明确未开播的房间取画质报 `StreamUnavailable`（v3 空列表）；刷新和搜索得到的房间取流报 `StreamUnavailable`（v3 “identity”）；受限房间取流报 `NeedsLogin`（v3 `mediaUnavailable`）；别的画质是 `ArgumentError`，恢复时也不先发请求 | 问题 8、9、10。只在播放路径上，状态和分组不变 |
| 4 | 开播状态在受限、未知状态时分别报 `NeedsLogin`、`ApiChanged`（v3 都是 `access`） | 问题 7。仍然不当作未开播 |
| 5 | 别的网站的链接作搜索词时直接给空，不发请求 | 问题 15。结果相同 |
| 6 | 见过的房间有上限（2000） | 问题 11 |
| 7 | 不再有逐字节的流式读取和严格 UTF-8；解析前仍按 2 MiB 检查 | 问题 12。传输由 live_net 统一负责，20 秒时限相同 |
| 8 | 取流结果是线路：格式、线路编号（主机名），没有请求头和租期 | 见“做法”。地址与 v3 相同 |

## 保持 v3 行为、没有采用归档 v4 或上游做法的地方

- **分类和分区名照 v3**：分类 `LOOK 直播`，分区“视频直播”“语音直播”。归档 v4 是分类“分类”（id `look`）、“视频直播”“声音直播”。
- **推荐合并视频和声音两个列表**（v3、上游 TV）。归档 v4 的推荐只有视频列表，实测只有 3 场。
- **受限（-10）显示为未知并加公告，其他未知值显示为未知**（v3）。归档 v4 把 -10 当未开播、其他值整个房间 `ApiChanged`。
- **两档画质 `HLS 原始线路`、`FLV 原始线路`，HLS 在前**（v3）。归档 v4 是一档“原画”、两条线路 FLV 在前，会改变画质菜单和已存的画质 id。
- **拉流地址按白名单校验并改成 https**（v3、上游 TV）。归档 v4 不校验、保留 http。
- **线路不带请求头**（v3 的播放器没有 LOOK 分支）。归档 v4 带桌面 Chrome UA、`Origin`、`Referer`（站点根）；列为升级候选 3。
- **编码不写**。归档 v4 按一次实测给视频直播写了 AVC、声音直播留空；接口本身不说（同京东直播、LiveMe）。
- **有按房间号和列表过滤的搜索**（v3、上游 TV）。归档 v4 没有搜索。
- **名字、标题只去首尾空白，不解 HTML 实体，标题为空时不用主播名顶替**（v3）。归档 v4 解实体并顶替；样本里没有实体，也没有空标题。
- **下一页只看 `hasMore`**（v3）。归档 v4 另要求本页非空。
- **房间回答没有 `data` 时是结构不符**（v3 `schema`，现在 `ApiChanged`）。归档 v4 当作不存在。
- **开播时间 `startTime` 不读**：3.x 的房间模型没有这个字段。
- 上游 pure_live_TV 与 v3 相同，没有要采用的修复。

## 回归条目的覆盖

归档规格没有 REG-LOOKLIVE 条目。§10“踩过的坑”两条和 `spec/regressions.md` 里涉及本平台的通用条目，属于平台层的部分都有测试：

- **声音分区出现视频直播**（§10）：按 `liveType` 只保留本分区的卡片（S02-audio-p1 的插入卡片），测试覆盖两个方向。
- **声音直播黑屏**（§10）：线路不写编码，交给播放层的纯音频处理（M7）；测试断言编码为空。
- REG-COMMON-001（详情失败不等于下播）：所有失败都是类型化错误；开播状态在受限、未知状态时报错，不返回假；刷新缺人数时写空串，`mergeFrom` 保留存下的值。
- REG-COMMON-002（错误有类型）：v3 的 9 种失败逐一映射，测试覆盖 10 种 HTTP 状态、`code` 404/424/520/522/555/500 和各种结构错误。
- REG-COMMON-003（五态）：直播、未开播、未知三态按 v3 映射；受限不当作未开播。
- REG-COMMON-004（观众数分开）：`onlineNumber` 是在线人数、`popularity` 是热度，分开存；房间接口没有人数时留空。
- REG-COMMON-006（线路按身份识别）：线路编号是 CDN 主机名。
- REG-COMMON-008（请求头随取流结果走）：线路自带请求头（本平台为空，与 v3 的播放器一致），播放和录制共用。
- REG-COMMON-011（链接识别）：只认 `look.163.com/live?id=<房间号>`（唯一的 `id`，可带别的查询），仿冒域名、别的路径、带用户信息、别的端口、带片段、重复 `id` 的都不认；分享文本经 `LinkParser` 识别，不发请求。
- REG-COMMON-013（目录分页）：分区按平台的 `hasMore` 翻页，合并目录任一列表还有就继续，列表到头的回答是空的最后一页。
- REG-LEASE-005（恢复重新获取）：恢复重新请求房间接口，不复用旧地址。
