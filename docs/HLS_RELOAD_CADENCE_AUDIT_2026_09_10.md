# HLS 清单刷新周期与响应耗时（2026-09-10）

起点 `150e9646` / 生产 `270a71f4`。承接 [后台覆盖证据](HLS_REFRESH_COVERAGE_AUDIT_2026_09_10.md) 与 [初始读取](HLS_PREFETCH_PREPARATION_AUDIT_2026_09_09.md)。本批继续追查真实 TTing 后续 sequence-gap，而非重复录制直到偶然通过。

## 现有证据与归因边界

- 旧真实记录目标时长为 2 秒；native 在 53,949 ms 最后已提供视频序号 15182–15193，59,269 ms 仍是已保留前缀 15183–15193，60,182 ms 后台检测到序号缺口。该诊断没有保留成功后台请求的起止及失败输入首尾序号，单凭 native 发布记录不足以确认网络/服务器/刷新间隔各自贡献。
- 源码没有设置自定义每 host 连接上限；尚无证据把缺口归因于媒体挤占清单连接。不得以此猜测另开 HTTP owner 或更改 Cookie/代理路径。
- 独立发现：scheduler 每次请求完成后再等待固定半目标时长，既累积响应耗时，又未区分首次/变化与未变化清单。来源为维护分支 `fc0fa50e` 的调度设计，属于 `fork-regression`；当前冻结上游不含该组件，不合并上游。
- [RFC 8216 §6.3.4](https://datatracker.ietf.org/doc/html/rfc8216#section-6.3.4)规定首次或已变化清单下一次加载至少相隔目标时长，起算点是上次开始加载；未变化清单使用半目标周期。因此不是简单提高频率：快响应变化时应减少多余请求，慢响应已消耗周期时应消除叠加等待。

## 验证与设计

1. 定向验证先观察实际 scheduler 请求时刻：首次/相同文本/仅注释变化/再次相同，分别核对整目标或半目标周期；相同媒体段不等于相同清单字节。
2. 真实回环 HTTP：三片、每片一秒的移动窗口，响应在请求到达时生成并延迟 2.7 秒；显式 0.5 秒调度周期用于隔离计时基准。核对请求不重叠、无额外 0.5 秒等待、连续性和资源回收，而非用增加片数或放宽 sequence-gap 合同让测试通过。
3. 已用有界清单内容指纹判断变化，每 feed 的单调时钟计算剩余周期，不保存另一份原始正文、不进行并行重载、不引入失败重试。首次选择缺少原始加载起始时刻时以选择时刻保守起算，不伪造一个更早时间。
